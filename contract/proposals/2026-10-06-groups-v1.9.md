# Proposal: PROTOCOL v1.9 — groups (MLS)

**Status:** proposed by root on 2026-10-06 (Harsha's slice 2). It needs review by the **crypto**,
**server** and **android** roles before merge. It is additive: DMs are unchanged, and apps without
groups never see group events, because they're never members.

## 0. Principles
- **Groups are E2EE-only.** A group is one MLS group, and each device is a leaf, as in DMs (§10).
  Only users with at least one MLS device and no legacy app instance in 30 days can be added
  (`not_ready`).
- **The server knows membership and roles only.** It needs them to authorise operations and order
  commits.
  - **The group name and icon are encrypted.** They live in an MLS GroupContext extension
    (`risime.group_meta`: `{"name", "icon": {blob ref} | null}`), changed by a commit and delivered
    to new members in the Welcome. The server never sees them.
- **No history for new members** (decision 032). **Removal rotates keys:** the removal commit
  advances the epoch, so removed devices can't read new messages.
- **Cap: 256 members** (users) for the pilot.
- **Risi-ready:** a member has `"kind": "user"` now, and `"agent"` from 0.5 (Add Risi). An agent
  will be a member like any other, always visible in the member list.

## 1. Identity
- `conversation_id` = `"grp:<uuid>"`; the MLS group id = `"grp:<uuid>#<generation>"` (§10.0).
- `Group = {"id": "grp:…", "members": [Member], "my_role": "admin" | "member", "created_at", "epoch", "generation"}`
- `Member = {"user_id", "display_name", "phone", "role": "admin" | "member", "kind": "user", "joined_at"}`
  - The phone is shown only to members who are friends with that member; otherwise it is null.

## 2. REST
- **`POST /api/v1/groups`** `{"member_ids": ["uuid", …]}` → `201 {"group": Group}`.
  - The creator becomes admin. Every `member_id` must be **an accepted friend of the creator**;
    otherwise `not_friends`, and the request is all or nothing.
  - Size: 2–255 others (`too_many_members`). Each member must be MLS-ready (`409 not_ready
    {missing}`).
  - The creator's device then makes the epoch-0 commit (§10.2, using the `grp:` conversation id),
    adding all devices of all members, with `group_meta` set in the GroupContext.
- **`GET /api/v1/groups`** → `{"groups": [Group]}` (mine). **`GET /api/v1/groups/{id}`** → `{"group": Group}`.
- **`POST /api/v1/groups/{id}/members`** `{"user_ids": […]}` (**admin**) → `200 {"group": Group}`.
  - Each user must be a **friend of the acting admin** and MLS-ready, within the cap.
  - The server records them as `pending_add`. The admin's device then commits the adds (claim →
    commit plus Welcome); the server accepts only `added` devices of pending users.
- **`DELETE /api/v1/groups/{id}/members/{user_id}`** (**admin**) → `204`.
  - The member becomes `pending_remove`, and the admin's device commits removal of all of that
    user's devices.
  - An admin can't remove another admin unless they are the group creator.
- **`POST /api/v1/groups/{id}/leave`** → `204`.
  - The leaver is marked `left` at once: no more delivery to them, and their sends are refused.
  - A **named committer** commits the removal of their devices: an admin's device first, then any
    member after a random 5–30 s.
  - If the last admin leaves, the longest-standing member becomes admin.
- **`PATCH /api/v1/groups/{id}/members/{user_id}`** `{"role": "admin" | "member"}` (**admin**) →
  `200`.
- **Rename / icon:** an admin's device commits a GroupContextExtensions proposal with the new
  `group_meta` (the commit endpoint is unchanged); the server records only "metadata changed".
- **Errors:** `403 not_admin`, `404 not_found` (not a member, so membership isn't revealed),
  `409 not_ready`, `422 too_many_members`, `not_friends`.

## 3. Commits (extends §10.2)
- `POST /mls/groups/{grp:…}/commit` behaves as for DMs.
- **The server authorises each commit's declared `added`/`removed` against the group's pending
  operations and the caller's role:**
  - adds only of `pending_add` users, by admins;
  - removes of `pending_remove` / `left` users, by an admin (or by the named committer for
    leaves);
  - metadata changes by admins;
  - self-updates by anyone.

## 4. Messages and events
- **`msg:send`** takes **`"conversation_id": "grp:…"` instead of `"to"`**, with the ciphertext
  only.
  - `not_member` if the sender has left or been removed.
  - Same e2ee rules (`stale_epoch`, 24 KiB).
- **The `message` event** for groups carries `conversation_id` and **no `to`**. It goes to every
  current member user, including the sender (§10.3). The usual push wake-up.
- **Acks:** `msg:ack` is per member. **Each member's `delivered`/`read` creates a `status` event
  to the sender only**, with `by` = that member. Clients aggregate a "Read by" view, and the
  sender's ticks show ✓✓ when **all** current members have delivered (read shows when all have
  read).
- **The new event kind `group_event`** (stored, cursor-ordered, to every member, including the
  affected users):
  `{"group_id", "action": "created" | "added" | "removed" | "left" | "role_changed" | "metadata_changed", "actor": "uuid", "targets": ["uuid", …], "server_ts"}`
  - Clients render system lines: "Kamal added Nimal", "Nimal left", "Kamal made Nimal an admin",
    "Kamal changed the group name". For `metadata_changed`, the new name is read from the local
    MLS group context.
- **Reactions** work in groups unchanged (the envelope, §11).
- **Typing** in groups: the `typing` push takes `conversation_id` instead of `to`, and goes to
  online members. Presence stays per friend.

## 5. Server storage
`groups(id, created_by, created_at, generation)` and
`group_members(group_id, user_id, role, state: active | pending_add | pending_remove | left, joined_at)`,
which reuse the §10 MLS tables keyed by conversation id. Limits are counted in Postgres.

## Open points for review
- **Crypto:**
  - the GroupContext extension `risime.group_meta`: a custom extension type, and how
    validation hooks in;
  - admin enforcement inside MLS (a policy check on staged commits against the admin list held
    in `group_meta`) versus server-only;
  - a self-remove for leaves (a SelfRemove proposal) versus a named committer.
- **Server:** commit authorisation against pending operations, the fan-out cost at 256 members,
  per-member status volume.
- **Android:**
  - the group list and chat UI;
  - creating a group (picking friends, name, icon later with images);
  - the info screen with members, roles, add, remove, leave and rename;
  - the "Read by" sheet; system lines; the notification grouping.

## Review outcomes so far (crypto + server done; android pending)
Accepted edits to fold in at merge:
- Group commits are sent as MLS **PrivateMessage** (handshake encrypted), not PublicMessage.
- `grp:` size caps: commit ≤ 1 MiB, Welcome ≤ 2 MiB; anything over 64 KiB is uploaded as a blob
  and sent by reference.
- **Admin policy** is enforced both in the crypto core (staged-commit check against the admin
  list in `group_meta`) and on the server, from one shared `group_policy_cases.json` that both
  test suites run.
- **Successor rule** when the last admin leaves: the remaining member with the lowest
  `leaf_index` becomes admin.
- Role changes travel as `meta` commits (GroupContext extension update).
- Key packages: `replace: true` upload, and capability `0xFA01` for the `risime.group_meta`
  extension.
- A **reset endpoint** for a broken group: `generation + 1`, members re-join from scratch.
- Receipts: the server sends an aggregated `group_receipt` event, plus `GET …/receipts` for the
  "Read by" sheet.
- `msg:send` gains `conversation_id`; sending to a group you're not in returns `not_member`.
- Typing in groups is rate-limited (limits to be fixed at merge).
- Risi agent: excluded from admin and successor roles; agent keys never live on the chat server.
