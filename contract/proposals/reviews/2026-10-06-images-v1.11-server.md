# Review: PROTOCOL v1.11 encrypted images, server side

**Reviewer:** server role, 2026-10-06.
**Proposal:** `contract/proposals/2026-10-06-images-v1.11.md`; **decision:** 042.
**Verdict:** accept, provided the **required changes** below are made. The contract shape is
fine: one store, single-request upload, single-range download, and the removed-member read rule.
Most of the required changes are about the server and its operations: disk, backups and the read
check. A few need a sentence in the contract text.

## What I checked (facts this review relies on)
- **Code.**
  - `server/lib/risime/blobs.ex` and `blob_controller.ex` (v1.9):
    - the controller reads the **whole body into memory** (`read_all/3`, 256 KiB reads,
      `IO.iodata_to_binary`);
    - `write!/2` writes `<id>.tmp` and then renames it;
    - `readable?/2` knows only the owner, group `active`/`pending_add` members and
      `blob_readers`, and **has no `dm:` branch**.
  - `blobs.owner` is `on_delete: :delete_all`, so deleting a user drops the rows and **orphans the
    files**.
  - `expires_at` is `NOT NULL`. There is only an `expires_at` index, none on `owner`.
  - `Plug.Parsers` runs before auth with `[:urlencoded, :multipart, :json]` and `pass: ["*/*"]`.
    So octet-stream passes unread (good), but JSON and multipart bodies of up to about 8 MB are
    parsed **before authentication**, and multipart writes temp files.
  - `RateLimiter` (decision 001) is an in-node ETS sliding window, and **rejected hits count**.
  - `BlobCleanup` runs hourly at :41 on the `maintenance` queue (concurrency 1).
  - `group_members` has primary key `(group_id, user_id)`, so it **cannot hold history**: a
    re-add overwrites the row.
    - Members become `active` in `groups.ex` (creation) and `groups/commit.ex` (2 places).
    - They leave through `mark_removing/2` (`pending_remove`), `delete_member/2` and the
      `do_reset` cleanup.
- **Caddy** (`/etc/caddy/Caddyfile`, identical to `infra/caddy/Caddyfile`, Caddy v2.11.7):
  - There is **no `request_body` directive**. Caddy has no default body limit, so 16 MiB already
    passes. Nothing blocks it today, and nothing caps any other path either.
  - `reverse_proxy` streams request bodies by default (no request buffering).
  - `encode zstd gzip` is site-wide. Caddy's default encode matcher lists text, JSON, JS, XML and
    SVG types, not `application/octet-stream`, so blobs should pass uncompressed with their
    `Content-Length` and ranges intact. **The implementation must verify this** (test below).
- **Disk on spark2.**
  - Everything shares one NVMe root (`/dev/nvme0n1p2`): 916G total, 70G used, **799G free**.
    That covers the OS, the Docker volumes (Postgres, Cassandra), `~/risime-blobs`,
    `~/risime-backups`, releases and, later, model weights for vLLM.
  - `~/risime-backups` is already **3.0G**: 7 sets of about 440M each, all from today, because
    `scripts/run-server` backs up on **every deploy** with `--keep 7`.
  - Backups sit **on the same disk** (PROD.md item 4, the off-box host, is still open).
  - `~/risime-blobs/prod` is empty today.

## Required changes

### R1. Stream uploads to disk; never buffer 16 MiB in memory
`read_all/3` can't simply take a larger cap: 3 concurrent uploads × 16 MiB × N users would sit in
the BEAM heap. The upload path becomes:
1. **Validate before reading the body.**
   - Check `purpose`, the conversation and its rights, `Content-Type`, and `Content-Length`
     (required; missing → `400 bad_request`).
   - Check the purpose cap against `Content-Length` (`413 too_large`) and the quota against
     `Content-Length` (`413 quota_exceeded`).
   - Check the free-space guard (`507`), the rate (`429`) and a concurrency slot (`429`).
   - Look up idempotency: a completed `(owner, client_blob_id)` → `200` with the existing reply.
   - All of these respond **without reading the body**, with `Connection: close` so Bandit doesn't
     try to drain up to 16 MiB.
2. **Stream.**
   - Open `BLOB_DIR/.tmp/<random uuid>` with `[:write, :raw, :binary, :exclusive]`, mode 600.
     Use a unique name, not `<id>.tmp`, so two retries can't collide.
   - Loop `read_body(conn, length: 64 KiB, read_length: 64 KiB, read_timeout: 30_000)`.
   - Write each chunk and feed `:crypto.hash_update/2`.
   - Abort with `413 too_large` the moment the running total exceeds the cap or `Content-Length`
     (the header lied).
   - Treat a total below `Content-Length` (client gone, `{:error, _}`) as an abort.
   - Apply an overall deadline (for example 10 min per upload) so a slow-loris client can't hold
     one of its 3 slots forever.
3. **Commit.**
   - `:file.sync`, then rename to `BLOB_DIR/<2 hex>/<id>`.
   - Insert the row in a transaction that **re-checks the quota** under
     `pg_advisory_xact_lock(hash(owner))`; otherwise 3 concurrent uploads can each pass the
     pre-check and overshoot.
   - Reply `201` only after the commit.
   - On any failure after the rename, delete the file.
4. **Cleanup.**
   - The temp file is removed in an `after` clause.
   - Process death skips `after` (Bandit kills the handler when the socket closes). So
     `BlobCleanup` also deletes `.tmp/*` older than 1 hour, and `Application.start` clears `.tmp/`.
5. **Idempotency.**
   - Unique index `(owner, client_blob_id)`.
   - Two concurrent requests with the same id can both finish streaming. The loser's insert hits
     the unique index: it deletes its own file and returns the winner's row with `200`.
   - The same `client_blob_id` with a different `purpose` or `conversation_id` is
     `400 bad_request`.
   - A replay of a **deleted** blob's id is `404 not_found`, never a silent re-upload under an id
     the client believes it cancelled.
   - Contract text: add these two cases to §2.1.

### R2. A free-space guard that matches the real disk
10 GiB free is too late on spark2, because the same filesystem holds Postgres and Cassandra:
- a full disk makes Postgres PANIC on WAL writes;
- Cassandra stops accepting writes and needs free space for compaction (TWCS);
- the nightly backup writes several GiB at once.

Required:
- The **contract** says only "below a server-configured free-space guard" (`507 storage_full`).
  The numbers are server configuration, not protocol.
- Defaults:
  - `media` → `507` when free space is under **max(50 GiB, 10 % of the filesystem)**, or when the
    **total live `media` bytes** exceed a global cap `BLOB_MEDIA_MAX`
    (default **200 GiB**, `SUM(size)` cached for 60 s);
  - `mls` and `icon` keep working down to **20 GiB** free;
  - a `warning` log line and a `/health` detail at **100 GiB** free, so Harsha hears about it
    weeks early.
- **Measurement:**
  - A small GenServer runs `df -Pk BLOB_DIR` every 30 s and caches the free bytes in
    `:persistent_term`. OTP's `disksup` polls every 30 min by default, which is too coarse.
  - The guard compares *free − in-flight upload bytes* (the sum of `Content-Length` of open
    uploads) with the threshold.

### R3. Membership history in Postgres: `group_member_intervals`
- **Postgres, not Cassandra.**
  - The data is relational and tiny (a few rows per member per group).
  - It must change **in the same transaction** as `group_members.state`, and it is read by an
    indexed point lookup.
  - CLAUDE.md keeps Cassandra for message and event streams.
- **A separate table, not columns on `group_members`.** The `(group_id, user_id)` primary key
  allows one row per pair, and a remove followed by a re-add must keep both intervals.

```elixir
create table(:group_member_intervals) do            # bigserial id
  add :group_id, references(:groups, type: :string, on_delete: :delete_all), null: false
  add :user_id, references(:users, type: :binary_id, on_delete: :delete_all), null: false
  add :active_from, :utc_datetime_usec, null: false
  add :active_until, :utc_datetime_usec              # null = still active
end
create index(:group_member_intervals, [:group_id, :user_id, :active_until])
create unique_index(:group_member_intervals, [:group_id, :user_id],
         where: "active_until IS NULL", name: :gmi_one_open)
```

- **Writes.** All go through one `Groups.Membership.activate/close` pair, called inside the
  existing transactions.
  - **Open** where a member becomes `active`: creation (`groups.ex`) and the two
    `set: [state: "active", joined_at: now]` sites in `groups/commit.ex`.
  - **Close** (`active_until = now`) in `mark_removing/2` (when delivery stops), and defensively
    in `delete_member/2` and the `do_reset` cleanup (`UPDATE … WHERE active_until IS NULL`).
- **Migration.** Backfill one open interval per current `active` member with
  `active_from = coalesce(joined_at, inserted_at)`.
- **Invariant test.** After every group operation in the test suite, an open interval exists
  **if and only if** `state = 'active'`.
- **Read check.** One indexed probe:
  `EXISTS (… WHERE group_id = $g AND user_id = $u AND (active_until IS NULL OR active_until >= $uploaded_at))`.
  (`active_from ≤ now` is always true; drop it.)
  - With the blob primary-key lookup, that is two index lookups, well under a millisecond.
  - **No `(blob, user)` cache.** It would save nothing measurable, and it adds an invalidation
    bug for `icon`, which must be revoked at once on removal.
- **Readers per purpose.** `readable?` becomes one branch per purpose:

  | purpose | readers |
  |---|---|
  | `mls` | as today |
  | `media` | owner, **dm members**, or a member with an overlapping interval; `pending_add` is **not** a reader |
  | `icon` | owner, or a current `active`/`pending_add` member |

### R4. `dm:` needs its own upload and read checks
- Today `Groups.visible/2` and `Groups.member/2` return nothing for `dm:` ids. So DM uploads
  would be refused, and if that were patched, the **recipient would get `404`** on download.
- **Upload.**
  - `{:ok, [a, b]} = Mls.members(conv)`, the caller is `a` or `b`;
  - `Social.friends?(a, b)` and no block, else `404`;
  - `Mls.e2ee?(conv)` is true, else `409 not_e2ee`.
- **Read.** Caller ∈ `Mls.members(conv)`. That parses the conversation id with no DB lookup, and
  it is **independent of the current friendship or block state**, as the proposal says.
- `icon` with a `dm:` id is `400` before any of this.
- **Tests** cover both users reading, a third user getting `404`, read after unfriending, and
  upload to a plaintext DM getting `409`.

### R5. Range downloads
- Implement in `BlobController.show`. Plug.Static's range code is private, so write a small
  parser.
- **Requests.**
  - `bytes=a-b` or `bytes=a-` → `206` with `send_file(conn, 206, path, a, len)` (Bandit uses
    `sendfile(2)`; Caddy terminates TLS, so the upstream is plain TCP) and
    `Content-Range: bytes a-b/size`.
  - The proposal allows only `a-b` and `a-`. A suffix range (`bytes=-n`) is legal HTTP. I suggest
    the server accept it and the contract say "a single range".
  - Multi-range, `a > b` or `a ≥ size` → `416` with `Content-Range: bytes */size`.
- **Every `200` and `206`** carries `Accept-Ranges: bytes` and the **strong** ETag
  `"<sha256 hex>"` (from the stored digest, no file read).
- **Conditional requests.**
  - With `If-Range`, a mismatched ETag → full `200`.
  - `If-None-Match` matching → `304`.
- `HEAD` works through `Plug.Head`.
- **Expiry race.** A file deleted by the sweep between the check and `send_file` must become
  `404`, not a `500` (rescue `File.Error`/`:enoent`).
- **Edge test** (a release-checklist item, not unit tests):
  `curl -H 'Accept-Encoding: gzip, zstd' -r 0-99 https://risime.risicloud.ai/api/v1/blobs/<id>`
  must return `206` with `Content-Length: 100` and no `Content-Encoding`. If Caddy ever encodes
  blobs, the edge needs `encode { match header Content-Type text/* application/json* }`.

### R6. Concurrency limits bound to the process, not ETS counters
- A per-user counter incremented and decremented in `try/after` **leaks** when Bandit kills the
  handler (client disconnects mid-upload). The user would then be stuck at "3 concurrent"
  forever.
- Use a `Registry` with duplicate keys:
  - `{:blob_up, user}` (limit 3) and `{:blob_down, user}` (limit 8);
  - count with `Registry.count_match/3`;
  - unregister explicitly after the response, because HTTP/1.1 keep-alive reuses the process;
  - process death cleans up automatically.
- One node, so this is enough.

### R7. Schema, expiry and the sweep
- **`blobs` gains:**
  - `client_blob_id` (unique with `owner`);
  - `uploaded_at` (the existing `inserted_at` already is that; reuse it rather than adding a
    second column);
  - `deleted_at`.
- **`expires_at` becomes nullable** (`null` = the current group icon).
  - Making a new icon current sets the old one's `expires_at = now + 7 d`.
  - **Deleting or resetting a group** sets `expires_at = now` on all of that group's blobs.
  - The **one existing sweep** (`expires_at <= now`) then covers media, superseded icons and group
    deletion, with no special cases.
- **`DELETE`** sets `deleted_at` and removes the file at once. The row stays until its
  `expires_at`, so a `client_blob_id` replay gets `404` (R1). Quota and reads ignore rows with
  `deleted_at`.
- **Indexes:**
  - `(owner, purpose) INCLUDE (size) WHERE deleted_at IS NULL` for the quota sum;
  - `(conversation_id)` for group deletion.
- **Sweep.**
  - Delete in batches of 1000 (`LIMIT` in a CTE), so a busy day doesn't make one long
    transaction.
  - Delete the files after the rows commit.
  - A **weekly orphan pass** removes files with no row. This covers crashes between the commit and
    `File.rm`, user deletion (the `on_delete: :delete_all` cascade) and restores.

### R8. Incremental blob backups (the disk's biggest consumer)
- `scripts/backup --blobs` today runs `tar -czf` over the whole store on **every** run, and
  `run-server` runs a backup on **every deploy** (7 today) with `--keep 7`.
- Encrypted blobs don't compress, so gzip only burns CPU, and every set is a full copy:
  - realistic 30-day live set (40 users × 15 photos/day × 1.3 MiB) ≈ **23 GiB** → 7 sets
    ≈ **160 GiB**;
  - quota worst case (40 × 2 GiB = 80 GiB live) → 7 sets ≈ **560 GiB**, which together with the
    live set fills the 799 GiB that is free.
- Blobs are immutable, so: **`rsync -a --link-dest=<previous>/blobs BLOB_DIR/ <set>/blobs/`**.
  - Each set looks complete (restore = copy the directory), but stores only the blobs new since
    the previous set. Total backup size ≈ live set + one day of uploads, whatever the `--keep`.
  - `.tmp/` is excluded.
  - The manifest records the file count and total bytes. `SHA256SUMS` lists blob files by their
    stored digest (the filename is the id, and the DB has the sha256), so verification needs no
    second hashing pass. Alternatively, verify a sample.
  - Off-box copy (when PROD.md item 4 lands): the same `rsync --link-dest` to the remote, which
    is also incremental.
- The script is root-owned (`scripts/`). This is the server role asking for it before `media`
  ships.
- **Consistency note for `restore`.** Postgres and blob files are copied at slightly different
  moments.
  - A row whose file is missing serves `404`, which clients already handle as "no longer
    available".
  - A file without a row is removed by the orphan pass.
  - No ordering lock is needed.

### R9. The `mls` purpose needs a byte cap too
The free-space guard is the only thing that stops `mls` abuse: `mls` is unquota'd, so
60/h × 2 MiB × 30 days ≈ **86 GiB per user**. Count `mls` bytes in a per-user cap as well (for
example 512 MiB live; legitimate commits and Welcomes over 64 KiB are rare). Contract: one row in
the §2.5 table.

## Suggestions
- **S1. Caddy hardening (root/infra).** Add `request_body { max_size 17MB }` for
  `/api/v1/blobs*` and about `1MB` for the rest of `/api/*`.
  - Today an **unauthenticated** client can push 8 MB JSON or multipart bodies into
    `Plug.Parsers`, and multipart spills to temp files.
  - On the server side, drop `:multipart` from `Plug.Parsers` (nothing uses it) and set
    `length: 1_000_000` for JSON and urlencoded. Server role, separate chunk.
- **S2. Rate counting.**
  - Rejected hits count in `RateLimiter`. A client that retries every 60 s during a `429` keeps
    itself locked out.
  - The proposal already says clients honour `Retry-After`. Additionally:
    - the blob buckets should count only **accepted** attempts (check, then increment);
    - an idempotent `200` replay should not count.
  - `Retry-After` for the daily bucket can be up to 24 h. That's correct, and the client UI
    should say "later today", not spin.
- **S3. Malicious and abusive uploads.** The server can't scan E2EE content, by design.
  Mitigations are structural:
  - Files are stored as mode 600 under server-generated UUID paths (no client names, so no path
    traversal) and served only as `application/octet-stream` with `nosniff`. Add
    `Content-Disposition: attachment` for defence in depth.
  - Readers are members only, and blobs live 30 days.
  - The quota and the global cap bound "free encrypted file hosting".
  - Add an operator script, `scripts/blob-purge --user <id>`, that expires all of a user's blobs,
    for the day someone has to be removed. It needs a decision note, not protocol.
- **S4. Icon bound.** `icon` isn't counted in the quota. The worst case per admin is
  10/h × 24 × 7 days × 512 KiB ≈ 840 MiB of superseded icons per group. That's acceptable, but
  lower it to 3/h (nobody changes an icon more often).
- **S5. Logs.** Caddy's access log records `conversation_id` and `client_blob_id` from the query.
  The server knows them anyway, but the pilot's log retention (`roll_keep 10`) then holds a
  who-uploaded-where trail. Either drop the `query` for `/api/v1/blobs` in the log filter, or
  accept it and mention it in the §9 privacy note.
- **S6. Upload size reply.** Return `size` and `sha256` from the stream's own count and hash. That
  is already the plan; just don't stat or hash the file again.
- **S7.** `GET /blobs/usage`: compute it with the same quota query (the R7 index); no cache needed
  at pilot scale.

## Answers to the server open points
1. **Streaming 16 MiB under Plug/Bandit.**
   - Yes. `Plug.Parsers` already passes octet-stream through unread (`pass: ["*/*"]`), so the
     controller streams with `read_body` loops into a temp file (R1).
   - Bandit has no body limit of its own; the limit is ours, enforced on the stream.
   - Caddy needs **no change** to allow 16 MiB: it has no `request_body` limit configured and
     streams to the upstream. A cap is optional hardening (S1).
2. **`group_member_intervals` vs extending `group_members`.**
   - A separate Postgres table (R3); `group_members`' primary key can't hold a re-add.
   - The read cost is two indexed point lookups. **Don't cache per `(blob, user)`.**
3. **Quota and rate numbers vs spark2's disk.**
   - 799 GiB free is ample for a pilot, **if** backups are incremental (R8) and the guard is sized
     for a disk shared with Postgres and Cassandra (R2: 50 GiB / 10 %, plus a 200 GiB global
     media cap).
   - Keep 2 GiB per user, 120/h, 1000/day and 3 concurrent.
   - Add a cap for `mls` (R9).
   - With full tarballs, the quota worst case fills the disk; with `--link-dest` it doesn't.
4. **Range with `send_file` offsets, ETag and `If-Range`.**
   - Yes: `send_file/5` with offset and length, and a strong ETag from the stored SHA-256.
   - `If-Range` mismatch → `200`; `If-None-Match` → `304`; `416` carries `bytes */size`.
   - Verify Caddy's `encode` leaves blobs alone (R5 edge test).

## Contract text changes requested (for root)
- §2.1:
  - a missing `Content-Length` → `400 bad_request`;
  - `client_blob_id` reused with a different purpose or conversation → `400`;
  - a replay of a deleted blob → `404`.
- §2.2: a single range includes the suffix form; `Accept-Ranges: bytes`; `416` carries
  `Content-Range: bytes */size`; `If-None-Match` → `304`.
- §2.5:
  - the `507` threshold is "server-configured" (defaults in a decision note, not the protocol);
  - an `mls` byte cap row;
  - the icon rate (S4, optional).
- §8:
  - intervals are in Postgres, with the schema from R3;
  - `expires_at` is nullable for the current icon;
  - group deletion expires the group's blobs;
  - backups use incremental `rsync --link-dest` (R8).
