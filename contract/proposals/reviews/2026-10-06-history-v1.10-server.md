# Review: PROTOCOL v1.10 history (sender copy + gap marker), server side

**Reviewer:** server role, 2026-10-06.
**Proposal:** `contract/proposals/2026-10-06-history-v1.10.md`; **decision:** 043 (proposed).
**Verdict:** accept, provided the **required changes** below are made. The sender copy is a
small, safe change to `Messaging.deliver/3`. One server point in §2 is wrong as written: the
`first_seen_at` backfill goes the wrong way (R1). This review also specifies the `mls` blob byte
cap (R5), so it can ship in the same release.

## What I checked (facts this review relies on)
- **Code.**
  - `server/lib/risime/messaging.ex`:
    - `deliver/3` writes `message_index` first, then publishes.
    - A plaintext body goes only to `req.to`, with the default `push: true`.
    - The e2ee and reaction branches already publish to the sender with `push: false`.
    - The recipient is always published before the sender.
  - `ack/3`:
    - A DM advances only on `recipient_id: ^user_id`.
    - A group ack is routed to `GroupReceipts.ack/3` only for `kind: nil, recipients: [_ | _]`.
    - Everything else is a no-op.
  - `messaging/group_receipts.ex`:
    - `apply_ack/4` returns `{e, nil}` (no write, no event) for a user who is not in
      `e.recipients`.
    - `recipients` is written by `deliver_group/3` as `members -- [sender_id]`, so it never
      contains the sender.
  - `store/cassandra.ex` and `priv/cql/001_messaging.cql`:
    - `inbox_events` is `PRIMARY KEY ((user_id), event_id)`, with a 30-day default TTL and TWCS

    - `append_event` is a plain `INSERT`, so the same `(user_id, event_id)` overwrites the row.

    - The store already has a paged full-scan helper (`conversation_pairs/3`) that runs without

  - **Nothing deletes `app_instances` rows**: no `DELETE` anywhere in `lib/`, only the
    `users` `on_delete: :delete_all` cascade. The "30-day census window" is a **read filter**
    (`last_seen_at > now - 30 d` in `readiness/1` and the claim), not a prune.
  - `devices.ex`: `devices` rows are **deleted and re-inserted** by:
    - the 60-day prune;
    - eviction beyond 10 devices;
    - `DELETE /me/devices`;
    - dev logout (`delete_for_token`);
    - a push token moving to another install, or FCM invalidation (push-only rows are deleted).
  - `inbox_channel.ex`: `page/2` builds the join and `sync` replies. Live events pass through
    `visible?/2` only. There is no server-side unread or notification state per event.
- **Pilot data** (read-only; `risime_dev` is the pilot's data, per `infra/pilot/pilot.env`).

  - Postgres:

## Required changes
### R1. `first_seen_at`: do not backfill existing rows with `last_seen_at`. Leave them null.
§2 says a backfilled `last_seen_at` "only makes fewer messages count as 'before this install'".
**That is backwards.** Rule 1 marks every e2ee message with `server_ts < history_before` as
pre-install and **skips it without decrypting**. So a value that is too late makes *more*
messages pre-install, including messages the device holds keys for.
- **Concrete case:** an existing device has events parked in `mls_pending` (waiting for a
  Welcome or an epoch). It updates to v1.10 and reprocesses them. With
  `history_before = last_seen_at` (its latest connect), those parked events are older and are
  dropped as "pre-install", even though the Welcome may still arrive and they were decryptable.
  Events in a lagging cursor window hit the same problem.
- **Required:**
  - `first_seen_at` is **nullable** and has **no backfill**: existing rows stay null, so their
    `history_before` is null.
  - Only rows inserted after the migration get a value, set to the insert time.
  - Clients treat null as "unknown": rule 2 only, never rule 1.
  - Every real reinstall from v1.10 on gets an exact value.
  - The cost is that installs reinstalled before the deploy (in practice Harsha's phone) get no
    rule-1 marker for earlier generations. Rule 2 still covers messages from their current
    generation.
  - If root wants those devices covered too, set their `first_seen_at` by hand from known
    reinstall times. That is safe because the time is exact, not estimated.
- **Contract text:** replace the backfill sentence in §2 with "Rows that existed before v1.10
  have no first-seen time; `history_before` is then null." Also say that **null means rule 2
  only**.

### R2. Publish the sender copy before the recipient's event
`deliver/3` publishes to the recipient first and then to the sender (the e2ee branch does the
same today). In between, the recipient can receive the event live and `msg:ack` it.
- The `status` event is then broadcast to the sender's other online devices **before** the copy.
  A device that drops a `status` for an unknown message loses that tick: its cursor moves past
  the status, so a replay never brings it back.
- The order inside Cassandra is still correct, because the status `event_id` is a later
  TimeUUID. Only the live order is affected.
- **Required:** for both the plaintext and the e2ee DM branches, publish
  `{sender_id, event, push: false}` first and then the recipient's event, so a status can never
  overtake the copy.
- The sending device may then see its copy before the `msg:send` reply. §1.3 already allows this:
  the outbox row exists before the send.

### R3. The backfill sits behind the store boundary and copies only real users
- **Placement:** add a store callback in `RisiMe.Messaging.Store.Cassandra`, next to
  `conversation_pairs/3`, run from a `RisiMe.Release` task. CLAUDE.md says no other module
  touches Cassandra for messages.
- **What it does:**
  - It scans with `SELECT user_id, event_id, kind, payload, TTL(payload), WRITETIME(payload)`,
    paged.
  - It copies only rows where:
    - `kind = 'message'`;
    - the payload has `body`;
    - `from` ≠ the partition's `user_id`;
    - **both `from` and the partition's user exist in `users`** (one id set loaded from Postgres
      at the start).
  - It writes `INSERT … USING TTL ? AND TIMESTAMP ?` with the source TTL and write time:
    - it never outlives the original;
    - it never overwrites a row the live v1.10 code wrote later;
    - it stays in the source's TWCS window.
  - It skips rows with a TTL under 60 s.
  - It logs counts only (scanned, copied, skipped), never payloads.
- **Why the filter:** without it, the pilot run writes **934 233** copies into partitions of
  deleted load-test users, which nobody can ever read. With it, it writes **120**.

### R4. Tests (server gate)
- **Sender copy:**
  - the sender's and recipient's inboxes both hold the event, with the same `event_id` and an
    identical payload;
  - `RisiMe.Push.Test` records a notify for the recipient only;
  - an idempotent resend with `message_index` missing rewrites both rows (still one row each).
- **Self-acks, which are not tested today:**
  - a sender's `delivered`/`read` ack of their own DM produces no `status` event and leaves
    `message_index.status` at `sent`;
  - a sender's ack of their own group message produces no `group_receipts` row and no
    `group_receipt` event.
- **`history_before`:**
  - it is set on the first connect of a `device_id`;
  - it is stable across reconnects and logout/login with the same `device_id`;
  - it is null without a `device_id` and for pre-migration rows (R1);
  - it is the same on the join and every `sync` page.
- **Backfill:**
  - it copies only plaintext DMs of existing users;
  - it is idempotent when run twice;
  - its copies carry the source TTL (±2 s).
- **Contract:** the two new examples, plus `error_quota_exceeded.json` (R5).

### R5. A per-user byte cap for `mls` blobs (the v1.9 §12.6 gap). Ship it in v1.10.
Today: 60 uploads/h × 2 MiB × 30-day TTL ≈ **84 GiB of live `mls` blobs per user**, with no
quota at all. The v1.11 review's R9 covers only the `media` purpose.
- **Limit:** at most **256 MiB of live `mls` blobs per user**: the sum of `size` over the
  caller's unexpired `purpose = 'mls'` blobs, across all conversations.
  - A legitimate maximum-size op is one commit (≤ 1 MiB) plus one Welcome (≤ 2 MiB) = 3 MiB, so
    256 MiB allows **about 85 maximum-size ops a month per user**.
  - Anything ≤ 64 KiB is inline and never uses a blob.
  - The pilot holds 0 `mls` blobs today.
  - Worst case for the whole server: 256 MiB × users, so 2.5 GiB at today's 10 users and 50 GiB
    at 200, instead of 84 GiB for **one** user today.
  - At the 60/h rate an abuser hits the cap in about 2 hours and then stays there.
- **Error:** **`413 quota_exceeded`**, as a standard §0 REST error extended with the numbers:
  `{"error": {"code": "quota_exceeded", "message": "…", "used": n, "limit": 268435456}}`.
  - This is exactly the code and shape that v1.11 §2.5 defines for `media`, so it is **one
    additive code for both releases**. v1.10 introduces it; v1.11 reuses it for `media` with its
    own 2 GiB limit.
  - Old apps (v1.9) treat any non-201 from a blob upload as a failed commit attempt, and the op
    stays pending. No new client behaviour is needed to stay correct.
  - Do not reuse `413 too_large`. It means "this blob is over the cap" and never clears, while a
    quota clears as blobs expire or are deleted.
- **Check order** in `Blobs.upload/3`: membership (`404`) → `too_large` (from `Content-Length`)
  → **quota** (`Content-Length + used > limit`) → rate limit (`429`) → read the body.
  - Check the quota before reading the body, and again on the actual size after reading it.
  - Concurrent uploads may overshoot by at most (concurrent uploads × 2 MiB). That is
    acceptable; v1.11's 3-per-user concurrency limit bounds it to 6 MiB.
- **Server:**
  - `used` = `SELECT COALESCE(SUM(size), 0) FROM blobs WHERE owner = ? AND purpose = 'mls' AND
    expires_at > now()`.
  - It needs an index on `(owner, purpose)`, which v1.11 adds anyway. Whichever release ships
    first creates it.
  - The limit is configurable (`:risime, :mls_blob_quota`), defaulting to 256 MiB.
- **Contract text:** one bullet in §12.6, "At most **256 MiB** of live `mls` blobs per user
  (`413 quota_exceeded {used, limit}`)", plus the example and the changelog line.

## Suggestions
- **G1. Compute `history_before` once per socket.**
  - Have `record_instance/4` use `insert_all(…, returning: [:first_seen_at])`. Postgres returns
    the stored value on upsert too, because `first_seen_at` is not in the replace list.
  - Put it in the socket assigns, so join and `sync` need no extra query.
  - Use the app clock (`DateTime.utc_now()`), the same clock as `server_ts`, not the DB's
    `now()`.
- **G2. A crash window that already exists, unchanged.** `put_message` runs before both
  publishes. If the node dies between them, a resend sees the index, does not re-deliver, and
  one copy (or both) is missing.
  - This is the same as the e2ee DMs today.
  - Moving the index write last would make early acks fail (`get_message` returns
    `:not_found`), so leave it as it is and record it as a known limit.
- **G3.** Clients should `DELETE` the `mls` blobs of a commit that failed (`409`), so they stop
  counting against the quota.
- **G4. Order of operations for the backfill:** deploy v1.10 first, then run the backfill
  (`bin/risime eval`, with `ERL_EPMD_ADDRESS=127.0.0.1`), after the `scripts/run-server`
  backup. That way no plaintext DM falls between the backfill and the live sender copy.

## Answers to the open points
- **S1. Yes, `GroupReceipts.ack/3` ignores a sender's ack of their own message.**
  - `recipients` is written as `members -- [sender_id]`, and `apply_ack/4` returns `{e, nil}`
    for anyone not in `recipients`: no row, no event.
  - A DM self-ack matches neither `recipient_id: ^user_id` nor `recipients: [_ | _]` (DM rows
    have null `recipients`), so it falls through to `:ok`.
  - Neither case has a test yet; R4 adds both.
- **S2. Yes, run the backfill on the pilot, filtered to real users (R3).**
  - The scan takes **about 15 s** over 2.27 M rows (274 MB).
  - There are **120 real plaintext DMs** inside the TTL (8 senders, 10 users), against
    **934 233** load-test ones, whose users are already deleted.
  - So the run is a 15 s read plus 120 writes, and it is idempotent. It restores Harsha's own
    sent plaintext for 30 days.
  - The load-test rows expire on their own by about 2026-11-04.
- **S3. Use `app_instances.first_seen_at`, not `devices.inserted_at`.**
  - Nothing prunes `app_instances`: the 30-day window is a read filter, so the value cannot reset.
    Any future prune must keep rows of instances seen in the last 30 days.
  - `devices.inserted_at` is worse on every count:
    - the row exists only after `PUT /me/devices`, which comes after the first connect, so the
      value is too late;
    - it is deleted and re-inserted by the 60-day prune, eviction, logout, token moves and FCM
      cleanup;
    - push-less legacy installs have no row at all.
  - The one fix needed is R1 (null, not `last_seen_at`, for old rows).
- **S4. The cost is small.** Each plaintext DM gains one plain `INSERT` into `inbox_events`
  (about 120 B on disk at the current average) and one PubSub broadcast. There is no push and no
  LWT.
  - Today the send path does a `get_sent` read, an LWT `IF NOT EXISTS`, the `message_index`
    insert and the recipient's insert. Each ack adds a CAS LWT and a status insert.
  - The LWTs dominate Cassandra CPU (`docs/status/loadtest.md`). A plain insert is about ¼ of an
    LWT's round trips.
  - So: +1 of about 6 mutations per message lifecycle, and well under 10% of the Cassandra CPU.
  - It adds one sequential insert (about 0.3–0.5 ms through `docker-proxy`) before the reply,
    against a p50 of 4.3 ms.
  - Pilot volume is 120 messages in 30 days, so storage is negligible. At load-test rates it
    means +200 inserts/s at the standard run and +3.2 k/s at the stress run.
  - **Gate:** rerun `mix risime.loadtest` at 200×1/s for 180 s and at 2000×1/0.6 s for 60 s.
    Accept with 0 errors, 0 missing pushes, and a send→reply p99 no more than 20% above the
    `docs/status/loadtest.md` figures.
- **Also checked:**
  - **Idempotency:** the copy uses the same `event_id`, and the payload is deterministic (the
    resend reuses `prior.server_ts`; Jason sorts the keys of small maps). A rewrite overwrites
    the row and creates no duplicate.
  - **No push for your own copy:** guaranteed by `push: false` in `publish/3`; R4 asserts it.
  - **Status and ticks are unaffected:**
    - `status`/`group_receipt` events keep fresh TimeUUIDs later than the `message_id`, so they
      replay after the copy;
    - self-acks are ignored (S1);
    - live ordering is fixed by R2.
  - **Old apps:** the server change is wire-additive, an extra stored event of an existing kind
    plus one new reply field, so nothing on the server is version-gated. The client-side dedupe
    claims in §1.3 are for the android review to confirm.
