# Review (android): contract proposal v1.10, history after a reinstall

**Reviewer:** android role, 2026-10-06.
**Proposal:** `contract/proposals/2026-10-06-history-v1.10.md`. **Decision:** 043.
**Verdict:** approve with the required changes below. The wire change is fine for Android: one
optional reply field, and sender copies that v1.9 apps already handle correctly. Most of the
work, and every finding below, is on the client.

Code read: `MlsPipeline.kt`, `ChatEngine.kt`, `PhoenixRealtimeClient.kt` (join/sync loop),
`Daos.kt`, `Entities.kt`, `SessionStore.kt`, `GroupStore.kt` (system lines and receipts),
`ChatsViewModel.kt`/`ChatsScreen.kt`, `ChatScreen.kt`/`ChatItems.kt`, `PushLogic.kt` and
`AppContainer.notifyFromLocal`, `Reactions.kt`, and the tests in `MlsPipelineTest`/`ChatEngineTest`.

## What already works (verified in code)
- **Plaintext sender copies on a fresh install.** `ChatEngine.applyMessage` sets
  `outgoing = from == me` and status `SENT`, and it returns `false` for outgoing rows, so they
  are never acked. `unackedIncoming()` also filters `outgoing = 0`. The replayed `status` events
  then advance the ticks. `applyStatus` looks the row up by `client_msg_id`, then `message_id`,
  and moves it forward only (`MessageStatus.advance`). TimeUUID ordering puts the copy
  (`event_id = message_id`) before its `status` events, so the ticks land on an existing row.
- **Dedupe against the outbox.** `applyMessage` checks `byMessageId`, then `byClientMsgId`. A
  live copy that arrives before the `msg:send` reply hits the PENDING outbox row by
  `client_msg_id` and is skipped. An idempotent resend overwrites the same Cassandra row, and
  `seen_events` plus the `message_id` unique index absorb the second delivery.
- **Groups.** Group messages are e2ee-only (§12.9), so there is no plaintext group copy. Own
  group messages from another *current* device decrypt as outgoing, and `group_receipt` replays
  through `GroupStore.applyReceipt` (`outgoing = 1` only). Group `group_event` system lines
  replay as today.
- **Reactions.** Plaintext reactions already reach the sender's inbox (§11.2).
  `ReactionStore.applyConfirmed` stores my own replayed reactions as confirmed (not pending), and
  reactions on restored copies now find their target. Reactions on pre-install e2ee targets
  become orphan rows that are never rendered, which is harmless.
- **Marker storage.** `GroupStore.insertSystemLine` is the pattern to reuse: `kind = system`,
  `outgoing = false`, `message_id = null`, `status = READ`. With those values it is excluded from
  `unreadCounts`, `unreadIncoming` (notifications), `unackedIncoming` (acks) and
  `markIncomingRead`.

## Required changes
**R1. `MlsResult.BeforeInstall(conversationId, serverTs)` at three sites, not one (A1).**
Today pre-install events are lost in three different ways, and the proposal names only one:
1. **No group, so parked** (`MlsPipeline.kt:132`, and `:134` for a newer generation). These
   rows may never be replayed: if no Welcome ever comes (a DM whose peer is offline, a group
   I've left, an ex-friend), they sit in `mls_pending` for ever. Rule 1 goes here: when
   `server_ts < history_before`, return `BeforeInstall` instead of parking. The same applies to
   `gen < g.generation` at `:133` (today `Dropped("stale generation")`).
2. **Parked, then replayed after the Welcome.** The message has `gen == g.gen` and
   `epoch < g.epoch`, so it falls through to `decrypt`, which throws, and it becomes
   `Dropped("decrypt")` (`:152`). Rule 2 goes here, and it needs no stored "join epoch". By
   inbox order, every message below the Welcome's epoch precedes the Welcome, so it is already
   in `mls_pending` when the Welcome applies. Classify it during the Welcome's replay: pass
   `(w.generation, w.epoch)` into `replay()`, and any parked message with `gen == w.gen` and
   `epoch < w.epoch` is `BeforeInstall`.
3. **`pending.dropOlderGenerations` (`:92`)** deletes parked older-generation messages
   silently. Read them first and emit one `BeforeInstall` per conversation (max `server_ts`),
   then delete.

**Safety rules for rule 1:**
- (a) Apply it only where the pipeline would otherwise park or drop. When a local group exists
  at that generation and the epoch is ≥ ours, always try to decrypt first. A device can publish
  key packages (REST) before its first census connect, so a decryptable message could have
  `server_ts < history_before`.
- (b) Apply it only to events first seen from the inbox, never in `replay()`. Existing devices
  get `first_seen_at` backfilled with `last_seen_at`, which is later than events they parked
  before the upgrade. Those must stay parked and recoverable.

**Own messages from the old install** (`from = me`, `from_device ≠ mine`) go through the same
rules, as proposed. The `fromDevice == mine → Ignored` check (`:129`) stays first. The
`engine() == null → Ignored` path (`:83`) is unchanged: no MLS core, no marker.

**R2. Plumbing for `history_before`.**
- `EventsPage` gets `@SerialName("history_before") val historyBefore: String? = null`.
- `RealtimeListener` gets `onHistoryBefore(ts: String?)` (default no-op), which
  `PhoenixRealtimeClient` calls for the join reply and every `sync` page **before**
  `onEvents(page.events)`.
- `ChatEngine` keeps it in memory and passes it to `MlsPipeline.apply`. There's no persistence
  and no Room change: every join returns it, and live events only come after a join.
- Compare the timestamps as `Instant`, not as strings.
- Bump `PROTOCOL_VERSION` to `"1.10"`.

**R3. Marker row and its upsert, in the event's transaction.**
- `client_msg_id = "sys:history:<conversation_id>"`, `kind = system`, `outgoing = false`,
  `status = READ`, `acked_status = READ`, `message_id = null`, `from_id = ""`.
- `system_json = SystemLine(action = "history_gap", actor = "")`, and `body` = the line's text,
  so the chat list and old code paths read it.
- New DAO method: `INSERT OR IGNORE`, then
  `UPDATE … SET server_ts = :ts, local_ts = :localTs WHERE client_msg_id = :id AND (server_ts IS NULL OR server_ts < :ts)`.
  That is forward-only, so there is one line per chat across replays, restarts and duplicate
  deliveries.
- `ChatEngine.applyMls` handles `BeforeInstall` without setting `incoming` (no ack flush) and
  without calling `onIncomingFrom` (no typing reset, no "new message" signal).

**R4. Position comes from `local_ts`, not `server_ts`.** Every list (`conversation()`,
`lastMessages()`, the day separators, bubble times, chat-list order) sorts and stamps by
`local_ts`. As written, "position = latest pre-install `server_ts`" does nothing on Android.
Set the marker's `local_ts = epochMs(latest pre-install server_ts) + 1`, together with R5.

**R5. Restored history needs a real `local_ts`.**
- `applyMessage` stamps `localTs = clock()`. After a reinstall, 30 days of restored messages,
  now including both sides, show under "Today" with the replay time, in replay order. v1.10
  makes this far more visible, and R4 needs it.
- Rule: for inbox rows that are clearly historical (`server_ts < history_before`, or more than
  about 5 minutes older than `clock()`), use `localTs = epochMs(server_ts)`. Live rows keep
  `clock()`, so ordering against my own outbox rows (device clock) doesn't change.

**R6. UI for the marker.**
- **DM chat screen.** `ChatScreen` doesn't render `kind = system` today. A marker would show as
  an incoming bubble. Render it with `SystemLineText`: centred, no bubble, no ticks, no
  long-press reactions, no reply.
- **Text.** `systemText` maps unknown actions to "The group changed". Add branches for
  `history_gap` and `undecryptable` (R8), so the group screen shows the right text.

**R7. A fresh-install replay must never notify.**
- `notifiedUpTo` lives in DataStore, so it is 0 after a reinstall. On the first background
  push, `notifyFromLocal` then posts every replayed unread incoming message. It also posts every
  replayed reaction "on my message" in `reactionAdds`. That one is **new** with v1.10, because
  my restored copies are now outgoing targets.
- Fix: after the first `Live` that followed a `since: null` join, set
  `notifiedUpTo = max(notifiedUpTo, now)`. The marker itself is already safe, because its status
  is `READ`.

**R8. A3: decrypt failures get their own line** (see the answer below).
- `client_msg_id = "sys:undecryptable:<conv>"`, the same row shape as R3, with
  `action = "undecryptable"`.
- It covers `Dropped` from a decrypt exception, a sender mismatch, a missing
  `generation`/`epoch`, and a rejected Welcome.
- It doesn't cover `Unrecoverable` for groups: §12.8 already shows "Encryption was reset; some
  messages may be missing".

**R9. Cross-role: `history_before` is too early after logout and login on the same phone.**
- `SessionStore.deviceId()` survives sign-out, but logout wipes `mls_kv` and the server removes
  the device. The next login is a new leaf with the old `device_id`, so the old `first_seen_at`
  is too early.
- R1.2 and R1.3 still catch same-generation and older-generation messages once a Welcome
  arrives. Chats that never get a Welcome would still park silently.
- Ask server/root: reset `app_instances.first_seen_at` when that device is removed (logout or
  `DELETE` device). The alternative, rotating `device_id` on a logout wipe, is an android
  change. I'd rather not do that, because push and census keep the id stable on purpose.
  **Root to decide**; please add this to S3.

**R10. Tests** (all JVM; listed in the chunk order below).

## Suggestions
- **S-a.** When an own copy matches a PENDING outbox row by `client_msg_id`, fill
  `message_id`/`server_ts` and advance it to SENT, instead of skipping it outright. A lost
  `msg:send` reply then no longer leaves the row PENDING until the next resend. This is safe:
  the resend is idempotent.
- **S-b.** Insert restored *received* history (`server_ts < history_before`) as `READ` with
  `acked_status = READ`, so it sends no acks and shows no badges. Otherwise a reinstall lights
  up every chat with a month of unread messages. The old install already showed them.
- **S-c.** Exclude `kind = system` from `search()`. Group lines and markers are noise in
  results.
- **S-d.** Don't park pre-install `mls_commit` events whose `server_ts < history_before` (if the
  event carries one). They are always ignored after the Welcome, and on a fresh install they
  bloat `mls_pending`.
- **S-e.** A message parked with no group for more than 24 h (by server time) should count
  towards the R8 line, so "parked for ever" is never silent either.
- **S-f.** Tapping the marker could open a short sheet: "Messages sent before this device joined
  the chat can't be read here. They're still on your other or previous device. Encrypted
  backup is coming." It must not claim E2EE while the dev banner is up (§10.4).
- **S-g.** Log per-conversation counts of `BeforeInstall`/`undecryptable` (ids only, never
  content) for debugging pilot reports.

## Answers
**A1. Yes, with the changes in R1.** The new result is
`MlsResult.BeforeInstall(conversationId, serverTs)`, applied at the park, Welcome-replay and
drop-older-generation sites. The marker is upserted in the same Room transaction as the cursor
(`applyMls` already runs inside `tx.run`). Rule 1 never pre-empts a decryptable message and
never runs on replayed `mls_pending` rows.

**A2. Use neutral wording: "Earlier messages aren't available on this device".**
- The client can't tell a reinstall from a second device. The old install stays listed for 60
  days (decision 043), so "your other device" would often be false, and "previous install" is
  false on a second phone.
- The neutral line is true in both cases and doesn't claim E2EE while the dev banner is up. The
  detail goes in S-f.

**A3. Yes.** Silent loss is exactly what Harsha objected to.
- Use a distinct, deduplicated line: **"Some messages couldn't be decrypted"**, one per chat,
  forward-only position, local, never unread or notified (R8).
- It is distinct from the gap marker because it signals a bug or tampering, not expected
  history loss. Testers should report it.
- §12.8's reset line stays the only line for `Unrecoverable`.

**A4. No Room migration is needed.** `kind` (a free text column, default `'text'`) and
`system_json` already exist since v5, so `AppDatabase.VERSION` stays as it is. In the chat list:
- Keep `lastMessages()` as it is. With R4 the marker is the latest row only when nothing
  readable came after it. In that case "Earlier messages aren't available on this device" is
  the honest preview, timed at the real last activity.
- The group-row code already drops the sender prefix for system rows (`lastSender`). Do the same
  for DM rows: no "You:" prefix and no ticks for `kind = system`, in a muted style.
- A chat whose only row is the marker stays listed:
  - a friend always is;
  - a former friend is listed because a row exists (`buildChatRows`);
  - a group is listed because the `groups` row exists once a group event or Welcome arrives.
    If neither ever comes (a group I left), the marker row alone doesn't create a group row,
    and that's acceptable.
- Unread and notifications are unaffected (status `READ`).

## Chunk order (android, after root merges v1.10)
1. **Protocol.**
   - Code: `EventsPage.historyBefore`, `RealtimeListener.onHistoryBefore`,
     `PROTOCOL_VERSION = "1.10"`.
   - Tests: `ContractExamplesTest` parses `inbox_join_reply_v110.json` and
     `event_message_sender_copy.json`. `PhoenixRealtimeClientTest` checks that the value reaches
     the listener before `onEvents`, on join and on sync pages, and that null is tolerated.
2. **Marker storage and UI.**
   - Code: the DAO upsert (R3), the `SystemLine` actions and `systemText` branches, DM
     `ChatScreen` system rendering, the DM chat-list preview (A4), and (S-c) search.
   - Tests: a Robolectric in-memory Room test of the upsert SQL (forward-only, one row) plus
     `lastMessages`/`unreadCounts`/`unreadIncoming`/`unackedIncoming` exclusions. A Robolectric
     Compose test that a DM system row renders without a bubble or ticks.
3. **Pipeline (R1).** `MlsPipelineTest`:
   - no group and `ts < hb` → `BeforeInstall`, nothing parked;
   - `ts ≥ hb` → parked;
   - an existing group with `ts < hb` at our epoch → decrypts;
   - parked rows are not re-judged by rule 1 on replay;
   - Welcome replay: `gen == w`, `epoch < w` → `BeforeInstall`;
   - `dropOlderGenerations` rows → one `BeforeInstall`;
   - the old device's own sends (`from = me`) → `BeforeInstall`.
4. **ChatEngine wiring, R8 (the A3 line) and R5.** `ChatEngineTest` **"fresh install replays
   the inbox"** with empty fakes and `since = null`. The DM inbox holds:
   - plaintext received;
   - a plaintext own copy, then its `status` delivered → read;
   - a peer reaction on the copy and my own reaction;
   - pre-install e2ee messages both ways;
   - the Welcome for the new device;
   - readable e2ee messages.

   Assert:
   - the copy is outgoing READ and never acked; `realtime.acks` holds only incoming ids;
   - there is exactly one marker, below the readable messages and above the older plaintext;
   - restored rows carry `local_ts` from `server_ts`;
   - replaying the whole list again, and a fresh `ChatEngine` over the same fakes (a restart),
     leave one marker.

   Also:
   - a corrupted ciphertext gives one "couldn't be decrypted" line;
   - the `GroupChatEngineTest` variant: `grp:` marker keyed by the group id, `group_event`
     lines intact, a new member (no prior events) gets no marker, and a copy from my other
     current device gets ticks from `group_receipt`;
   - a live copy before the `msg:send` reply is skipped (and S-a if taken).
5. **No notifications on replay (R7)**, plus S-b if accepted. `PushLogicTest`: a fresh-install
   plan after the replay is empty, both chat lines and reaction adds.
6. **Interop.**
   - `LiveInteropTest` (opt-in):
     - A sends plaintext to B and B acks read;
     - a second client for A with a new `device_id` and `since = null` replays A's own copy with
       the same `event_id` as B's event, followed by delivered/read `status` events;
     - `history_before` is present, stable across a rejoin and on `sync` pages, and null
       without a `device_id`.
   - Device run (emulator + USB phone, real MLS core). User A has a plaintext chat and an e2ee
     DM, plus a group, with B. Then:
     - **(i)** A signs in on a **second fresh device** while the first stays active: both sides
       of the plaintext history are restored with the correct ticks, the e2ee DM and the group
       each show one marker, new messages after the Welcome decrypt on both of A's devices, and
       there are no notifications or badges from the replay;
     - **(ii)** A reinstalls on the first device and gets the same result;
     - **(iii)** A logs out and back in on the same device (R9).
   - Results go in `docs/status/android.md`.

Chunks 1–2 can land before the server ships, since the field is optional. The server's copy
can ship before any app update (§1.3 confirmed above).
