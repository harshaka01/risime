# Android review: contract proposal v1.12 (delete messages and chats)

**Reviewer:** android role, 2026-10-06. **Proposal:** `contract/proposals/2026-10-06-delete-v1.12.md`
(decision 047, proposed). Read together with the server and crypto reviews of the same day; where
they already cover a point (rollout R1 server, hidden-tombstone authorisation R3 crypto, own echo
R4 crypto, admins per epoch R2 crypto) this review only adds what the app needs.
**Verdict:** feasible without new frameworks. Merge after the **required changes** R1–R10. Most of
them are places where the proposal assumes app behaviour that this app doesn't have (a
conversations table, a server-clock offset, an "attempted" flag on the outbox, silent notification
updates) or where a local action would be undone by an existing replay path.

How the current app does things (facts this review relies on):
- **Room is at v5** (`AppDatabase.VERSION = 5`), schemas 1–5 committed, no destructive fallback,
  `EveryReleasedSchemaUpgradeTest` walks every released schema. **v1.11 images are not implemented
  on Android yet**: no `media` table, no blob cache files, no image envelope type.
- `messages` (PK `client_msg_id`, unique `message_id`) is ordered by **`local_ts`** (device clock
  for live rows; `server_ts` for restored history, §13.3 R5). `kind` is `text` or `system`
  (history/undecryptable markers `sys:history:<conv>`, `sys:undecryptable:<conv>`, group lines).
  `body` is `NOT NULL`. Search is `LIKE` over `body` with `kind != 'system'` (decision 009, no FTS).
- `ChatEngine.onEvents` applies each event in one transaction with `seen_events` + cursor; unknown
  kinds hit `else -> false`, are **marked seen and the cursor moves past them**. `seen_events` is
  never pruned. `MlsPipeline` only understands `message`/`mls_*` events; a decrypted payload goes
  through `MlsPayload.decode` (`text`, `reaction`, else `Ignored`). A group change replays
  `mls_pending` in arrival order.
- The outbox is the `messages` table itself (`status = 'PENDING'`). A row that was pushed but whose
  reply was lost is indistinguishable from one never pushed. Reactions have their own flush under a
  **different mutex** (`reactionLock` vs `outboxLock`).
- **The chats list has no conversations table.** `buildChatRows` lists **every friend** (DM row
  always present) plus former friends only while a message exists, plus every row of `groups`.
- **Notifications** are planned from unread incoming rows newer than `notifiedUpTo`, posted only in
  the background (`InboxStyle` for DMs, `MessagingStyle` for groups, one per chat + summary),
  `setAutoCancel`, no `setOnlyAlertOnce`. Push wake-up = `InboxSyncWorker` → `syncAndNotify`.
- The join reply's `server_time` is parsed (`Protocol.kt`) but **no clock offset is kept**.
- Long-press opens the v1.8 reactions sheet (quick reactions + Copy/Retry/Delete, where "Delete"
  today means "discard a FAILED message"). DM chat (`ChatScreen`) and group chat (`GroupScreens`)
  are separate screens.
- After process death an OIDC session is **locked** until a fingerprint unlock (Keystore key with
  per-use auth); a push wake-up while locked only posts "Open RisiMe to read them".

## Required changes (blocking)

**R1. Rollout: say what old apps show, and plan a receive-first rollout (no `required` update).**
Agree with server R1 (decision 016: `required` only when a protocol is dropped). From the app side,
what a ≤ v1.11 app (every app in the pilot today) does with a deleted message:
- **Keeps it**: bubble, ticks, reactions, chat-list preview and search hit. A notification already
  posted for it **stays in the shade** until the chat is opened.
- The `delete` event is skipped by `else -> false`, **marked seen and passed by the cursor**. When
  that device later updates to v1.12 it never sees the event again (`seen_events` blocks any
  replay), so **the message stays on that device for good**. For E2EE the skipped control can't be
  decrypted later either: with the core's `out_of_order_tolerance` 5 the key is gone after a few
  more messages from that sender.
- Old-app reinstall/login: the message does **not** come back (the server rows are gone).
- A plaintext reaction to it gets `unknown_target` and the existing code reverts it (no error
  shown). An E2EE reaction is stored by the server and dropped by v1.12 receivers. Acks are
  ignored. Nothing crashes and MLS state is unharmed.

**Acceptable for the pilot**, provided:
1. The deleter is told honestly. When any device of any member lacks the new capability (see A4),
   the dialog's small print says "Some people use an older RisiMe and may still see it". Never
   block the action on it.
2. **Receive first.** Ship the receive path (chunks 1–4 below: tombstones, hidden tombstones,
   notification withdrawal) in a nightly **before** the send UI is enabled, so most devices
   understand `delete` events by the time anyone can send one. The send UI is behind a local flag
   that a later nightly turns on.
3. §0 bullet "rollout is a `required` update", §9 and decision 047 §5 are rewritten accordingly,
   and §9 states the "stays for good on a device that skipped the event" residual.

**R2. A pending message can't be "cancelled locally" once it may have reached the server (§5.1).**
§5.1 says that for a message without a `message_id`, both options "just cancel the send locally".
On this app a `PENDING` row may already be stored on the server (reply lost; §13.1 S-a fills it in
later). A local cancel would then leave a message the peer sees and the sender doesn't.
Required rule:
- A PENDING row that was **never pushed** is cancelled locally (no request).
- A row that **was pushed** at least once becomes "cancel after send": the outbox resends it with
  the same `client_msg_id` (the server's dedupe returns the original `message_id` without
  re-delivering), then sends `msg:delete` `everyone` for it. Shown as the tombstone meanwhile.
- "Delete for me" on such a row does the same (the user meant "don't send it").
- Android: `messages` gains `send_attempts` (or an `attempted` flag) set before the first push.

**R3. Clear chat needs a local watermark, not just a server job (§5.7, §6).**
Rows removed locally can come back through paths the proposal doesn't mention:
- `mls_pending` rows of that chat (parked at a newer epoch) are replayed after the next commit and
  inserted as new messages.
- A parked or late reaction recreates reaction state.
- A `history_before` replay recreates the §13.3 marker at its old position.
- `chat:clear` runs as a background job; a wipe-and-login before it ran replays the whole chat.

Required: Clear/Delete chat store a per-conversation watermark `cleared_upto` (the TimeUUID time
of `upto`) in the same transaction as the local purge. Every apply path drops `message`,
`reaction`, `delete`, `call_end` (v1.13) and marker rows whose `server_ts` is ≤ the watermark.
Normative text for §5.7: "clients ignore any event of that conversation at or before `upto`".
`upto` is the **global cursor** read in that same transaction (the app has one cursor, not one per
chat). Say that the server compares `upto` by TimeUUID time, not as a string. TimeUUID strings
don't sort by time, as `MlsPendingEntity.seq` already documents.

**R4. Clear/Delete chat must not cancel a pending delete-for-everyone (§5.7).**
"Both cancel the conversation's … unsent outbox rows" must exclude `msg:delete` requests. The user
asked for those to happen for everyone, and clearing my view doesn't withdraw that. Only unsent
messages and reactions are cancelled, with R2's never-pushed/pushed split. Pushed messages still
complete. Their own copies are newer than the watermark, so they appear after the clear. That's
correct: they were sent.

**R5. Pre-install, undecryptable and parked `delete` events never create §13.3 lines.**
§5.5 says pre-install deletes are "skipped silently". In this code every `BeforeInstall`/`Dropped`
result upserts a history/undecryptable marker. Make the rule normative for every **control** kind:
- a `delete` (and in v1.13 a `call_signal`) that is pre-install or undecryptable produces **no
  marker and no tombstone**;
- it is logged only;
- a parked `delete` is replayed through the same path as a parked message.

Test: a fresh-install replay with only `delete` events before `history_before` shows no marker.

**R6. One encrypt-and-push lane per conversation covers deletes too.**
The `delete` envelope consumes a generation of the device's sender ratchet, like a text or a
reaction. Today texts (`outboxLock`) and reactions (`reactionLock`) already encrypt under
**different** mutexes. Adding a third sender (the delete outbox) widens the window in which
generation `n+k` reaches the server before `n`. With `out_of_order_tolerance` 5 that loses
messages (crypto calls-review R2). Required on Android, stated once in §10.4 for all types: one
serial lane per conversation for encrypt + push. A ciphertext that wasn't accepted before a later
one was pushed is re-encrypted on retry, never resent.

**R7. Notification withdrawal needs silent updates and an explicit refresh (§5.5).**
"Cancel or rebuild" isn't enough with the current notifier:
- **Rebuild must not alert again.** Re-posting a chat notification without
  `setOnlyAlertOnce(true)` (and `setSilent(true)` on API 26+) plays the sound and heads-up again
  for a delete. Required wording: "rebuild silently".
- **The planner skips it today.** `planChatNotifications` only includes chats with a row newer
  than `notifiedUpTo`, so after a delete the conversation would be dropped from the plan, not
  rebuilt. The refresh path must re-plan **every chat that currently has a posted notification**
  (`NotificationManager.getActiveNotifications()` by id), using all unread rows. Empty → cancel.
  When no chat notification is left, cancel the group summary as well.
- **Reaction lines** about a deleted target vanish because the reactions rows go in the purge;
  the same refresh rebuilds that chat.
- **Every path does it.** The refresh runs for a live delete in the foreground too: a notification
  can still be in the shade while the app is open on another chat.
- **The push is needed.** A delete for a notified message must wake the device. Android answers
  S6: **always** send the data-only push for `delete` events.

**R8. The client needs the server clock offset and an admin source for eligibility (§5.1).**
- Keep `offset = server_time − device_now` from every join/sync reply (in memory and in DataStore
  for a cold start). Eligibility of "for everyone" = `server_ts + 48 h − 1 min > now + offset`.
- **Admin rights**:
  - The UI uses `groups.my_role` (server truth, refreshed by `GET /groups/{id}`).
  - Receivers use the core's `sender_is_admin` at the delete's epoch (crypto R2). The app keeps
    **no** per-epoch admin table. Decision 047's android consequence "per-epoch admin lists" goes
    away.

**R9. The positioned tombstone needs a defined `client_msg_id` and position (§4.4, §5.2).**
- For a target never stored, `client_msg_id` is unknown, but `messages` has it as primary key.
  Specify a deterministic local id `del:<message_id>`.
- Position: `local_ts` = the target's `server_ts` (as §13.3 R5 restored rows). The real message, if
  it arrives later, is then rejected by the existing `byMessageId` check, which already gives
  idempotency.
- The e2ee DM `delete` event must list `from_device` among "the e2ee fields" (§2 says only "`to`
  and the e2ee fields"); the leaf check needs it.

**R10. File deletes can't be "in one transaction" (§5.2, images).**
Room transactions don't cover files.
- **Order:**
  1. In the transaction: the row, the sealed key, nonce and thumbnail, and the transfer rows.
  2. After commit: unlink the cached ciphertext and any temp plaintext (viewer or share copy),
     cancel the WorkManager download/upload by `client_msg_id`, and evict in-memory bitmaps.
- **Crash:** without the key the file is useless. A start-up sweep deletes cache files that have
  no `media` row.
- **Own image still uploading:** cancel the upload, then `DELETE` the blob (§14.2).
- **Missing blob ids:** a target whose envelope this device never stored (undecryptable, or
  pre-install) contributes no `blob_ids`, so that blob lives until its expiry. Say this in §10.

## Suggestions

- **S-a. Tombstones as `kind = 'deleted'`.** Add the new kind to the existing column, plus
  `deleted_by`, `deleted_by_admin` and `deleted_at`. Then `body = ''` and `system_json = NULL`. Search moves to
  `kind = 'text'` (so captions and call lines can opt in later), unread and acks exclude it
  (`status = READ`, `acked_status = READ`), and `LastMessage.kind` renders the preview.
- **S-b. A separate "deleting" column**, `delete_state` (null | `deleting` | `cancel_after_send`).
  Don't overload `status`: the tick state must survive a restore after `too_old`.
- **S-c. Own echo completes the outbox** (crypto R4): match by `client_msg_id` from the event's
  cleartext fields. This is the same pattern as §13.1 S-a for messages.
- **S-d. Multi-select UX.** Keep long-press → the existing sheet and add **Delete** and **Select**
  to it. Select mode: tap toggles, and a contextual top bar shows the count, Copy and the bin.
  Quick reactions stay in the sheet, so v1.8 doesn't change. Rename today's FAILED-row "Delete" to
  "Discard" so the two never mix. The same composable serves `ChatScreen` and `GroupScreens`.
- **S-e. Admin wording.** "Deleted by Kamal (admin)" instead of "by an admin". Admins are visible
  members anyway, and naming them fits "visible agents/actors". Optional.
- **S-f. Logout flushes the delete outbox** (best effort, inside the existing 5-s bound). Otherwise
  "Delete for me"/Clear chat done just before a logout come back with the login replay.
- **S-g. One-time catch-up after upgrading to v1.12 (optional; root and crypto decide).** Replay
  the last 30 days, apply only `delete` events and ignore `seen_events` for them:
  - plaintext: apply;
  - E2EE: try to decrypt and apply on success; otherwise skip (never apply on server metadata
    alone).

  This recovers most plaintext DMs and the odd E2EE one. It is cheap, because the recovery replay
  already exists.

## Answers to the android open points

- **A1.** Use "**You deleted this message**" on the deleter's own devices (`deleted_by` = me,
  whoever sent it). Use "**This message was deleted**" for everyone else. When `D ≠ S` in a group,
  use "This message was deleted by an admin" (or S-e).
- **A2.** Use a **separate table** `deleted_ids(message_id PK, conversation_id, deleted_by,
  deleter_is_admin, delete_server_ts, scope, at)`, pruned after 30 days. A `hidden` flag on
  `messages` would have to be excluded in about 10 existing queries (list, unread, preview, search,
  outbox, acks, notifications), and one missed filter leaks a deleted body. Per crypto R3, a
  message that arrives for a hidden tombstone is decrypted first, then judged: tombstoned or shown.
  "Delete for me" writes `scope = 'me'` (always honoured locally).
- **A3.** **Hide "for everyone"** when any selected message is ineligible, as proposed (WhatsApp
  does the same). The error path (`failures`) still drops the failing targets and offers "Delete
  for me", for races at the 48-h edge.
- **A4.** Yes, add a hint, because there is no required update.
  - Advertise `"deletes"` in the MLS device capabilities.
  - Return `deletes_ready`/`missing_deletes` with `GET /mls/groups/{conv}` (DM) and per member in
    `GET /groups/{id}`, like `images_ready`.
  - It only adds the R1 small print and never disables the action.
  - Plaintext legacy DMs: use the device census's `app_version` if the server has it, else no hint.
- **A5. Derived stores to purge in the tombstone transaction:**
  1. `messages.body`/`system_json`, which also covers search (LIKE, no FTS);
  2. `reactions` rows with that `target_message_id`;
  3. group receipt columns on the row;
  4. the `deleted_ids` bookkeeping;
  5. any `mls_pending` row whose decrypted result turns out to target it (handled at replay
     through `deleted_ids`);
  6. with v1.11: the `media` row (sealed key, nonce, thumbnail), transfer jobs and cached files
     (after commit, R10), and in-memory bitmap caches.

  Outside the database:
  - **posted notifications** (R7);
  - **ViewModel state** (selection, open reactions sheet, image viewer): close it if it shows a
    purged id.

  The behaviour log holds only peer hashes and lengths: nothing to purge. The clipboard and
  screenshots are out of reach (the §10 small print covers them).
- **A6.** Agree to keep it local for v1.12. Later, an own-inbox-only `delete` with `scope: "me"`
  (and a `chat_clear` event) would let my other devices follow. Note it in §10 so pilot users
  aren't surprised.

**Clear chat vs the chats list (UX facts the proposal should know):**
- DM rows for **friends are always listed**, so "Clear chat" leaves the row with an empty preview.
  "Delete chat" needs a local `chat_state(conversation_id PK, cleared_upto, hidden)` table to hide
  the row until a new message arrives.
- A **former** friend's DM row exists only while it has messages, so Clear chat removes it (same
  as Delete chat). That's acceptable; say so in §5.7.
- Groups hide via the same table.

## Room migration (v5 → v6, or v6 → v7 if images land first)
Additive only, as every previous step:
- `messages`:
  - ADD `delete_state TEXT`, `deleted_by TEXT`, `deleted_by_admin INTEGER NOT NULL DEFAULT 0`,
    `deleted_at INTEGER`, `send_attempts INTEGER NOT NULL DEFAULT 0`;
  - `kind` gains the value `deleted`, with no DDL.
- New `deleted_ids` (A2), plus an index on `at`.
- New `delete_outbox(client_msg_id PK, conversation_id, scope, targets_json, blob_ids_json, state,
  attempts, next_at, created_at, last_error)`, with indexes on `(state, next_at)` and
  `conversation_id`. It also holds `chat:clear` requests as `scope = 'clear'` with `upto`.
- New `chat_state(conversation_id PK, cleared_upto INTEGER, hidden INTEGER NOT NULL DEFAULT 0)`.
- `WipeDao.allChatData` wipes all three new tables.
- `EveryReleasedSchemaUpgradeTest` gains the new schema.
- `scripts/upgrade-test` passes before the nightly ships.

## Chunk order (android)
0. **Prerequisite:** the core changes from the crypto review (`sender_is_admin`, own echo,
   `maximum_forward_distance`), and the serial encrypt-and-push lane (R6), which also protects
   reactions today.
1. **Protocol:** types for `msg:delete` (push, reply, `failures`), the `delete` event, the
   `delete` envelope (strict decode, 1–100 distinct lowercase TimeUUIDs), `chat:clear`; parse
   every new example; the server-clock offset (R8).
2. **Room migration** + WipeDao + the upgrade test.
3. **Receive path:**
   - `delete` events through `ChatEngine`/`MlsPipeline` (binding check, §4.3 with
     `sender_is_admin`, 48 h + 5 min);
   - the tombstone purge in the cursor transaction;
   - positioned tombstones (R9) and hidden tombstones (A2 / crypto R3);
   - no markers for controls (R5);
   - tombstone rendering in DM and group chat, preview, unread and search.
4. **Notification refresh** (R7). → **Ship chunks 1–4 as a nightly (receive first, R1).**
5. **Send path:**
   - the delete outbox (retries with the same `client_msg_id`, `stale_epoch` re-encrypt, split
     at 100);
   - the deleting state and restore;
   - own-echo completion;
   - pending-message cancel semantics (R2);
   - the long-press Delete, the dialog with eligibility, multi-select (S-d) and the capability
     hint (A4).

   Behind a flag until most devices run chunk 4.
6. **Delete for me, Clear chat, Delete chat:**
   - local purge plus the `scope: "me"` and `chat:clear` outbox;
   - the `cleared_upto` watermark (R3);
   - the hidden row and the reappear rules;
   - chat-list long-press and the chat overflow menu;
   - R4.
7. **Images** (once v1.11 is in): `blob_ids` from stored envelopes, file unlink after commit,
   orphan sweep, cancelling transfers (R10).
8. **Live interop** (`scripts/interop`):
   - e2ee DM delete both ways;
   - group admin delete;
   - an image delete answered by `404`;
   - a reinstall after Clear chat;
   - an old-app peer (the R1 behaviour).

   Then `READY` in `docs/status/android.md`.
