# Review: encrypted backups v1.22, server side

**Reviewer:** server (root acting as reviewer), 2026-10-08.
**Proposal:** `contract/proposals/2026-10-08-backups-v1.22.md`.
**Verdict:** accept with S1–S8 (folded into §22.1, §22.3, §22.8).

## Required changes
- **S1. Parts, not one huge upload.** A 512 MiB single request over mobile data fails and restarts
  from zero. Upload ≤ 16 parts of 33 562 624 bytes through the existing streamed, idempotent §14.2
  path, then one commit that lists them. Downloads use the existing ranges.
- **S2. The commit is the unit.** Parts are unreferenced (24 h TTL) until `POST /backups` names
  them; the commit checks each part is the caller's, `purpose = backup`, the same `backup_id`,
  unexpired, with the server's size and hash; sizes add up. The whole-file `sha256` is the
  client's (the server doesn't re-read 512 MiB).
- **S3. Retention under the per-owner lock**, in the commit transaction: newest 2 current, the
  dropped one replaced for 7 days, at most 5 replaced, replaced pruned oldest first before a quota
  refusal. The quota (1.5 GiB) counts current backups and unreferenced parts, so a third backup can
  be uploaded while two 512 MiB ones are current.
- **S4. No silent key change.** `PUT /backup_key` with a different `bk_id` while backups exist →
  `409 backup_key_conflict`; the commit also checks `bk_id`. Otherwise a fresh install that "turns
  on backup" would orphan every existing backup.
- **S5. One backup device.** Without it, two phones alternate and the newest 2 may both come from
  the phone with fewer chats. `409 backup_device_mismatch` unless `replace_device` or the old
  device can no longer receive (§12.1), which covers the reinstall without a prompt.
- **S6. Switch semantics.** `BACKUPS=off` stops writes only; reads, downloads and `DELETE` keep
  working, so turning it off never strands a user's backup.
- **S7. Rates from Postgres** (6 commits per 24 h from `backups` rows); part uploads use the
  existing limiter (60/h, 200/day). Free-space guard: counted with `media` (`507`).
- **S8. Storage:** `backups`, `backup_keys`, `blobs.backup_id`; no Cassandra; the existing sweep;
  logs with counts and sizes only. Pilot scale: ~50 users × at most 1.5 GiB live + replaced.

## Notes
- `GET /backup_key` hands out the offline-attackable record; it is the user's own data behind the
  bearer token, limited to 30/h. The real protection is the 120-bit recovery key.
- Account deletion removes backups and the key record with the user.
