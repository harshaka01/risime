# Review: PROTOCOL v1.13 voice calls (1:1), server side

**Reviewer:** server role, 2026-10-06.
**Proposal:** `contract/proposals/2026-10-06-calls-v1.13.md`; **decision:** 046 (coturn).
**Verdict:** accept, provided the **required changes** below are made.

The design suits the server well:
- no call table and no call state machine;
- ciphertext-only signalling with a cleartext `call_id` and `ring` flag;
- a durable `call_end` through the normal path;
- the standard coturn REST scheme.

The required changes:
- TURN credentials must outlive the longest relayed call;
- short-lived signals must not sit in the 30-day inbox table;
- the "within MLS's forward tolerance" claim must be made true;
- signals must stay out of `message_index`/`sent_dedupe`;
- ringing must survive a half-dead socket.

## What I checked (facts this review relies on)
- **Push.**
  - `RisiMe.Push.payload/0` is one fixed map.
  - `RisiMe.Push.FCM.message/2` hard-codes
    `android: %{priority: "high", collapse_key: "inbox", ttl: "3600s"}`.
  - `Push.Dispatcher.notify/1` is **user-level**: it skips users with any live channel (5 s
    grace) and coalesces to one push per 10 s.
  - `Devices.push_tokens/1` returns tokens without device ids.
  - So a call push needs a new device-level path and per-type FCM options. This is
    implementation only; the contract is fine.
- **Presence.** `Presence.device_online?/1` already exists: ETS `{:device, device_id}`, set at
  inbox join, **no grace**, one node. This answers S3: yes, it is tracked per device.
- **Delivery filter.**
  - `InboxChannel` filters `grp:` events per socket (`visible?/2`), both live and in
    `filtered_page/3`.
  - `filtered_page/3` re-pages when a whole page filters away.
  - The `:groups` assign is set at join and updated by `{:device_groups, …}`. `calls` can copy
    this.
- **Messaging.**
  - `ack/3` acts on any `message_index` row whose `recipient_id` is the acker (status CAS plus a
    `status` event).
  - `sent_dedupe` is an LWT (`IF NOT EXISTS`, 24-hour TTL) shared by every push.
  - `check_e2ee/2` reads `MLS.group/1` and `check_recipient/2` reads `Social.friends?/2`: two
    Postgres reads per send, before the rate limit.
- **Rate limiter** (decision 001): ETS sliding window. `hit/4` counts rejected hits;
  `hit_if_allowed/4` doesn't; `retry_after_s/1` exists.
- **Capabilities.** `Devices` keeps `@known_capabilities ~w(groups images)`. `calls` must be
  added, or it is silently dropped. `RisiMe.MLS.Images` computes `images_ready` and is the
  template for `calls_ready`.
- **Crypto core.**
  - `crypto/risime-mls` builds groups with `MlsGroup::builder()` and sets **no**
    `SenderRatchetConfiguration`.
  - So openmls defaults apply: `out_of_order_tolerance = 5` and
    **`maximum_forward_distance = 1000`**.
- **Old apps.** `ChatEngine.onEvents` skips unknown kinds (`else -> false`) and advances the
  cursor.
  - A v1.13 `call_end` reaching an old app is an e2ee `message` with an unknown envelope type.
  - §10.3 says it is stored invisibly. An old app shows nothing: no ring and no missed-call line.
  - Old apps get no `call_signal` (the filter) and no `{"type":"call"}` push (calls devices
    only).
- **coturn 4.7** with `use-auth-secret`:
  - It validates the timestamp prefix of the REST username on **every authenticated request**,
    including `Refresh`, `CreatePermission` and `ChannelBind`, not only `Allocate`.
  - An expired username gets `401`, so the allocation can't be refreshed and lapses.
  - Decision 046 also sets `max-allocate-lifetime=3600`.
  - To confirm with `scripts/turn-smoke` (R1).

## Required changes

**R1. TURN credentials must cover the longest relayed call (§16.7, §16.4).**
- The credential lives 3600 s, and clients may reuse a cached one until `expires_at − 5 min`.
  So a relayed call can start with about 5 minutes of credential left.
- coturn refuses the next `Refresh`/permission/channel refresh once the username's timestamp has
  passed, so **the relay drops mid-call**: at the latest after about an hour, against a 4-hour max
  call length.
- Pick one (I prefer **a**):
  - **a.** `ttl` = **5 h** (18 000 s). Clients fetch fresh credentials at each call start or
    answer, or reuse a cached one only while `expires_at − now ≥ 4 h 5 min`.
  - **b.** Keep 1 h, and make clients do an ICE restart with fresh credentials
    (`setConfiguration` + `restartIce`) 10 minutes before `expires_at`, which adds an
    Android-side timer and state.
- Either way, `scripts/turn-smoke` gains a check: with a 60 s TTL, a `Refresh` after expiry is
  refused. That confirms the coturn behaviour this relies on.
- `max-allocate-lifetime=3600` limits one refresh's requested lifetime, not the total, so it is
  fine.

**R2. Store `call_signal` rows in their own table, not in `inbox_events` (S2).**
This is a storage change with no wire impact; §16.3 should drop "Cassandra `USING TTL`, TWCS as
today".
- Rows with a 60/120 s TTL in `inbox_events` (TWCS, 1-day windows, 30-day TTL, default
  `gc_grace_seconds` = 10 days) become **tombstones on expiry**. They sit in the same window
  SSTables as 30-day messages, so those SSTables can't be dropped early.
  - Each call writes about 30–60 signal rows per side, to two partitions each.
  - A user with 10 calls a day accumulates thousands of expired cells per partition. Every sync
    that crosses them scans tombstones, and a fresh install (`since: null`) scans all 30 days of
    them. Heavy callers would cross `tombstone_warn_threshold` (1000) routinely.
  - The SDP/ICE ciphertext would also physically outlive its "120 s" by up to 30 days.
- Instead, one table per query:
  ```sql
  -- Q9: SELECT event_id, kind, payload FROM call_signals WHERE user_id = ? AND event_id > ? LIMIT ?
  CREATE TABLE IF NOT EXISTS call_signals (
    user_id uuid, event_id timeuuid, payload text,
    PRIMARY KEY ((user_id), event_id)
  ) WITH CLUSTERING ORDER BY (event_id ASC)
    AND default_time_to_live = 120
    AND gc_grace_seconds = 0
    AND compaction = {'class': 'TimeWindowCompactionStrategy',
                      'compaction_window_unit': 'MINUTES', 'compaction_window_size': 10};
  ```
  - A ring row is written `USING TTL 60`.
  - `gc_grace_seconds = 0` is safe on one node; revisit for a multi-node cluster.
  - Whole SSTables expire and are dropped within minutes, so physical deletion matches the
    contract.
  - Same TimeUUID space as the inbox.
- **Join/sync** for a `calls` socket reads both partitions with `event_id > since LIMIT n+1`,
  merges them by `event_id`, takes `n` and sets `has_more` from the merged length. The cursor
  semantics are unchanged.
  - A non-`calls` socket never queries `call_signals`, which also answers S4.
  - Live delivery is the usual PubSub broadcast, filtered by a `:calls` socket assign.
- This lives behind `RisiMe.Messaging.Store`: a new `append_call_signal/2` callback, and
  `list_events/4` gains an `include_calls?` flag.

**R3. Make the MLS forward-distance claim true (§16.3 "the gap is within MLS's forward tolerance").**
This is cross-role; crypto decides.
- The tolerance is **cumulative**. A receiver can derive a sender leaf's key at most 1000
  generations past the last message it decrypted *from that leaf* (openmls default, which our core
  doesn't override).
- Several receivers skip **every** call signal:
  - devices without `calls` (filtered);
  - a calls device offline for more than 60/120 s (rows expired);
  - the caller's own other devices.
- Only durable messages move their ratchet position forward, and the durable `call_end` comes
  only from whoever ends the call.
- Example: A calls B repeatedly and B always declines or hangs up. Every signal from A's leaf
  (offer, about 1 ICE batch per 250 ms, restarts) is skipped by B's old tablet, and A's leaf sends
  no durable message.
  - After about 25–30 such calls (≈ 35–40 signals each), the tablet **can't decrypt A's next
    text**. It sees an undecryptable line, with no recovery short of a new epoch.
- Options (crypto chooses; the contract must state the result):
  - **a.** Set `SenderRatchetConfiguration::new(out_of_order_tolerance, 10_000)` (or more) for
    DM groups. This is the simplest. Forward derivation is a hash chain, so 10 000 steps is cheap,
    and nothing is retained except within `out_of_order_tolerance`.
  - **b.** The calling client sends a cheap durable message (e.g. its own `call_end`, always) from
    its leaf after each call. This is not enough alone, because a crashed caller sends nothing.
  - **c.** Server-side: none possible. The server can't see generations it doesn't parse.
- I recommend **a**, plus a contract sentence: "a receiver tolerates N skipped generations per
  sender leaf and epoch". The rate limits (60 signals/10 s) bound how fast the gap grows; the 4 h
  max call length doesn't.

**R4. Call signals never touch `message_index` or `sent_dedupe` (§16.3).**
- No `message_index` row. Otherwise `ack/3` treats the callee as `recipient_id` and emits
  `status` events for signals, and reactions or deletes could target them.
  - Without a row, acks naming a signal hit `:not_found` and are ignored, as the proposal wants,
    for free.
  - v1.12 `msg:delete` naming a signal then gets `gone`.
- **Idempotency in memory**, not via the `sent_dedupe` LWT:
  - an ETS map `{sender, client_msg_id} → reply` with a 5-minute expiry. That is one Paxos round
    less per ICE batch, at up to 6/s per user.
  - A duplicate after a node restart is harmless. It gets a new `event_id` with the same
    ciphertext, the second decrypt of an already-consumed generation fails, and the receiver
    drops it as a replay.
  - The contract can keep "same `client_msg_id` within 5 min returns the original reply" and
    add "best effort (lost on a server restart)".

**R5. Ring delivery must survive half-open sockets, and never use the inbox push (§16.8).**
- "No live inbox channel" is judged by `Presence.device_online?/1`. A phone that lost its network
  without closing the socket (Wi-Fi to mobile hand-over, Doze, tunnel) still counts as live until
  Phoenix's websocket timeout, about 60 s.
  - The offer goes into a dead TCP connection, and the phone never rings: the 45 s ring window
    passes first.
- Rule: push at once to `calls` devices without a live channel. Then, **if no `call:signal` with
  that `call_id` has arrived from the callee's user within 3 s** (no `call_ringing`/`busy`; the
  server sees `call_id` in cleartext), push to the callee's remaining `calls` devices too.
  - This is per-call state in memory only (an ETS entry or a timer, dropped after 45 s), not a
    call table.
- **State that `call_signal` events never call `Push.notify/1`** (the user-level inbox push).
  `ring: true` gets only the device-level `{"type":"call"}` push. Otherwise every ICE batch would
  also feed the 10 s inbox coalescer and wake idle devices.
- FCM: `RisiMe.Push.FCM` needs per-type android options (`collapse_key: "call"`, `ttl: "45s"`,
  priority high). The unregistered-token cleanup and the retry are reused.

## Suggestions
- **Order of checks for `call:signal`.**
  - Put the total rate limit (60/10 s, `hit/4`, cheap ETS) **first**, then idempotency, then
    `not_friends`, then e2ee (`not_e2ee`, `stale_epoch`), then the ring limits, then store.
  - As proposed, a limited or abusive client still costs two or three Postgres reads per signal
    (`friends?`, `messageable?`, `MLS.group`).
  - A retry that is itself rate-limited simply retries; signals are short-lived anyway.
- **Abuse limits per pair** (add to S7's set):
  - `ring: true` at most **20 per (caller, callee) per hour**, as well as 6/min per caller and 1
    per callee per 5 s. A friend who rings someone every 10 s all day is harassment; the per-5 s
    limit doesn't stop it.
  - `ring: false` signals to a callee at most 30/10 s per pair. ICE batching needs ≤ 4/s per call.
  - Every refused ring is logged with the pair (ids only), so a block can be suggested later.
  - Blocking stays the user's remedy, and `not_friends` already covers blocks.
- **`calls_ready` (§16.1): require one `calls` device per user, not all instances.**
  - For images every instance must render the image. For calls, a device without `calls` simply
    doesn't ring while another one does.
  - The all-instances rule would disable calling for anyone with an old tablet.
  - Keep `missing_calls` as information ("Your tablet won't ring until it updates").
- **TURN endpoint hygiene.**
  - Read `TURN_SECRET`, `TURN_URLS` (comma-separated) and an optional `TURN_TTL` in
    `runtime.exs`.
  - Treat a secret shorter than 32 bytes as unset, with a boot warning.
  - Compute the credential as `:crypto.mac(:hmac, :sha, secret, username) |> Base.encode64()`.
  - Never log the username → user mapping, not even at debug level, since dev logs at debug.
  - Use `hit_if_allowed/4`, so polling while limited doesn't extend the lockout, and set
    `Retry-After` from `retry_after_s/1`.
  - Return `503 {"error":"calls_unavailable"}` when either variable is missing, in the
    `ApiError` shape.
  - Optionally mint only for users with at least one `calls` device. That is one query, and it
    keeps the public relay to users who can actually call.
- **Rotation note (decision 046).** coturn takes one `static-auth-secret`. Rotating it
  invalidates every outstanding credential, and with R1a every relayed call in progress, so rotate
  at night.
- **Old apps, in the contract's words.** v1.12 and older apps never ring and show no call lines.
  - The `call_end` is an e2ee message with an unknown envelope type, which §10.3 says is stored
    invisibly.
  - Their users see nothing until they update. That is acceptable for an additive capability, and
    no `required` update is needed (decision 016).
- **v1.12 interplay.** `chat:clear` removes `call_end` messages like any `message`, so call lines
  are cleared with the chat. `call_signal` rows are never `msg:delete` targets (R4: `gone`).

## Answers to the server open points
- **S1 Separate push.** Agree. A `call:signal` push keeps status, history, the sender-copy
  backfill and the 30-day TTL out of signalling, and lets R2/R4/R5 apply cleanly.
- **S2 Per-row TTL in `inbox_events`.** No. Use the separate `call_signals` table (R2), merged
  into join/sync by `event_id`.
- **S3 Per-device liveness.** Yes, already tracked: `Presence.device_online?/1`, per device, no
  grace, one node (a multi-node cluster would need `Phoenix.Tracker`). Half-open sockets need the
  3 s fallback (R5).
- **S4 Filter cost.** It is negligible. With R2 a non-`calls` socket simply doesn't query
  `call_signals`. The live path is one assign check per broadcast, like the `groups` filter.
- **S5 `TURN_SECRET`/`TURN_URLS`.** Yes:
  - `.env` on spark2 and `pilot.env` for the release, never committed;
  - `.env.example` already has the placeholder;
  - `503 calls_unavailable` until both are set;
  - HMAC-SHA1 is coturn's scheme, which is fine.
  - The TTL needs R1.
- **S6 Refuse `ring: true` without a `calls` device.** Yes. Reply error **`calls_not_ready`**
  when the callee has no device with `calls` and a signature key. It is one Postgres query, done
  only for `ring: true`.
  - The client's `calls_ready` can be stale (a downgrade, a removed device). Without the check,
    the caller rings for 45 s into nothing.
  - Add it to the error list and the order of checks (after e2ee, before the ring limits).
- **S7 Rate limits.** 60/10 s total, 6 rings/min and 1 ring per callee per 5 s are fine for ICE
  restarts.
  - A restart is one `ring: false` offer plus a few ICE batches, well under 60/10 s, even with
    two restarts close together.
  - Add the per-pair hourly ring cap above. ICE restarts don't count toward ring limits, because
    restart offers use `ring: false`.

## Tests to add (server, on top of §16.13)
- A credential minted with TTL 18 000 s; `turn-smoke` refuses a refresh after expiry with a short
  TTL: R1.
- Signals land in `call_signals` with TTL 60/120 s, join/sync merge them in `event_id` order with
  a correct `has_more`, and a non-`calls` socket never sees them: R2.
- No `message_index`/`sent_dedupe` row for a signal; an ack naming one is ignored: R4.
- `ring: true` never calls `Push.notify/1`; the 3 s fallback push fires when no signal with that
  `call_id` comes back and doesn't fire when one does: R5.
- `calls_not_ready`: S6.
- The per-pair hourly ring cap.
