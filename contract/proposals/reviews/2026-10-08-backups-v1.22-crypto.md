# Review: encrypted backups v1.22, crypto side

**Reviewer:** crypto (root acting as reviewer), 2026-10-08.
**Proposal:** `contract/proposals/2026-10-08-backups-v1.22.md`.
**Verdict:** accept with C1–C9 (all folded into §22.2, §22.4, §22.9, §22.10). Needs a core
release: Argon2id, the wrap/stream functions, the FFI and the vectors.

## Required changes
- **C1. Fixed KDF parameters.** Read `m`/`t`/`p` from the record but accept only (65536, 3, 1) in
  v1; anything else `Malformed`. A server must not be able to make a client derive with weak
  parameters, even though unwrap with weak parameters gains an attacker nothing today; future
  changes bump `v`.
- **C2. Domain separation.** Never use the Argon2 output directly: `Kw` and `check` via HKDF with
  distinct `info`; `Kd` (DEK wrap) and `Ks` (stream) likewise from `BK`/`DEK`. Labels all start
  with `risime-backup-v1`, distinct from `risime-media-v1` and `risime-history-v1`.
- **C3. Bind context in every AEAD.** Wrap AAD = label ‖ user_id ‖ kind ‖ bk_id (cross-account and
  kind swaps fail); DEK AAD = label ‖ backup_id ‖ user_id; chunk AAD = label ‖ header_hash ‖ index ‖
  flag. A header edit (e.g. `created_at`, `user_id`) fails every chunk.
- **C4. Key commitment for the password wrap.** AES-GCM isn't key-committing; a crafted wrap could
  open under several candidate KEKs (partitioning oracles). The holder of the record can already
  brute-force it offline, so the gain is small, but the 16-byte `check` costs nothing, gives a
  clean "wrong key" vs "corrupted" signal, and is compared in constant time before decrypting.
- **C5. STREAM rules as §14.3.** Index and final flag in the nonce **and** the AAD; no empty last
  chunk; the last ciphertext chunk ≥ 17 bytes; trailing data rejected; verify every chunk before
  importing anything (a verify-only pass over an app-private copy, because a picked file can change
  under us).
- **C6. Compression before encryption** leaks the compressed size once per backup to whoever sees
  the ciphertext. No attacker-chosen plaintext is compressed together with a small secret in an
  interactive loop (CRIME/BREACH need many adaptive observations; we allow 6 per day), and Padmé
  blurs the length. Accept, document (§22.2).
- **C7. Randomness inside the core.** `BK`, `R`, `DEK`, salts and nonces from the OS CSPRNG inside
  Rust; deterministic forms only in test builds for the vectors. A failed writer is discarded,
  never resumed with the same `DEK` (no nonce reuse).
- **C8. Recovery key format.** 120 bits is right for a key the server can attack offline with
  Argon2id on top. A 20-bit checksum catches typos before a 1-second derivation; Crockford base32
  avoids O/0 and I/1/L confusion. Store `R` only in `mls_kv`; the display string is the only form
  that crosses the FFI.
- **C9. Passphrase floor.** Argon2id at 64 MiB/t 3 costs a GPU attacker roughly 10–100 guesses per
  second per GPU; the floor (14 characters or 4 words, not common, not the phone number) is a
  floor, not a guarantee. The UI must say the recovery key is the stronger option.

## Questions answered
- *Why a per-backup DEK instead of encrypting with BK?* A fresh key per file makes deterministic
  chunk nonces safe and lets a file be re-wrapped or shared later without re-encrypting.
- *Can the server forge or alter a backup?* No (no `BK`). It can withhold, delete or serve an older
  one; the date shown after the verify pass is authenticated (header hash).
- *Does `bk_id` leak anything?* 64 bits of a hash of a 256-bit secret: no.
- *Keystore wrap:* `BK` sits in `mls_kv`, under the DB key wrapped by a Keystore key without user
  authentication (§10.4), which is what unattended daily backups need. Same exposure as the
  messages themselves on an unlocked, rooted phone.
- *New dependency:* RustCrypto `argon2` (pure Rust, no C). Record in decision 059.
