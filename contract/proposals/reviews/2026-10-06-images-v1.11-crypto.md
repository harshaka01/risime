# Crypto review: contract proposal v1.11 (encrypted images)

**Reviewer:** crypto role, 2026-10-06. **Proposal:** `contract/proposals/2026-10-06-images-v1.11.md`,
decision 042 (proposed). Read against PROTOCOL v1.9 §10, §11, §12 and `crypto/risime-mls{,-ffi}`.

**Verdict:** the two-layer design is sound: a fresh random key per image, the key and ciphertext
digest inside the MLS message, no plaintext fallback, and an opaque store. Merge after the
**required changes** R1–R6 below. Most of them fix the **blob format**. That is the one thing that
can't be changed cheaply later:
- icons never expire;
- clients cache ciphertext and keep keys in the database indefinitely;
- video will reuse the format.

So it should be right in the first release.

---

## Where media encryption lives: the Rust core, exposed via UniFFI

**Decision:** media encryption goes in `risime-mls` (a new `media` module), exposed through
`risime-mls-ffi`. Kotlin `javax.crypto` is not used for it.

Why:
- **One implementation for every client.** iOS and desktop come later. The same code produces the
  test vectors (R6), so Android can't drift from the reference.
- **Key reuse is ruled out by the API shape** (R3). The core generates the key inside the encrypt
  call and never takes one from the caller. In Kotlin, an encrypt helper that takes a key is one
  refactor away from a retry path that re-encrypts new pixels under a stored key and nonce.
- **Streaming without the Java heap.**
  - Android's `AES/GCM/NoPadding` (Conscrypt and BouncyCastle) buffers the whole input on
    decrypt until `doFinal`, so single-shot GCM in Kotlin always holds 16 MiB of ciphertext plus
    16 MiB of plaintext on the heap.
  - The segmented format (R1) in Rust streams file to file with 64 KiB buffers.
  - Across the FFI, only paths and the final plaintext cross. Passing a 16 MiB `Vec<u8>` through
    UniFFI and JNA costs two extra copies.
- **No new dependencies.**
  - `aes-gcm 0.10.3`, `aes 0.8.4`, `ghash 0.5.1`, `hkdf 0.12.4`, `sha2`, `zeroize` and
    `getrandom` are already in `crypto/Cargo.lock` through `openmls_rust_crypto`. Add them as
    direct dependencies **at the same versions** so nothing is duplicated.
  - On aarch64, `aes` and `ghash` use the ARMv8 AES and PMULL instructions, so 2 MiB takes a few
    milliseconds. **Benchmark on the oldest pilot phone** before release.
- **The laptop's no-Rust debug build** can't send or open images. That is consistent with
  "images are E2EE-only": that build has no MLS either.

API sketch (names are android's call; the shape is the requirement):
```rust
// Encrypt: reads the re-encoded image file and writes the blob file. The key is generated inside.
media_encrypt_file(src: String, dst: String) -> SealedMedia { key: Vec<u8>, alg: String,
    plain_size: u64, cipher_size: u64, sha256: Vec<u8> }
// Decrypt: checks size and SHA-256, verifies every segment and the final flag, strips the
// padding, and returns the plaintext.
media_decrypt_file(src: String, key: Vec<u8>, alg: String, plain_size: u64,
    cipher_size: u64, sha256: Vec<u8>) -> Result<Vec<u8>>   // MediaError::{Integrity, Format, Unsupported}
```
`media_encrypt_with_key` (the deterministic form needed for vectors) exists only under `#[cfg(test)]`
or a non-default `test-vectors` feature. It is **never** exported from the Android `.so`.

## Required changes (blocking)

**R1. Use a segmented AEAD (STREAM construction) now. Don't ship single-shot GCM.**

Single-shot AES-256-GCM over 16 MiB is **cryptographically fine**:
- per invocation the limit is 2^39 − 256 bits (about 64 GiB);
- with one key per image, the 2^32 random-nonce bound is irrelevant.

The problems are elsewhere:
- **Memory.** It needs the whole ciphertext and plaintext in memory on decrypt (see above).
- **Range resume can't be verified.** Nothing can be verified until the last byte arrives, so a
  resumed download that splices in a bad range is only detected after 16 MiB.
- **A second format later.** It forces a second format for video, and the first format can never
  be retired, because icons and cached blobs live on.

The segmented format costs about 100 lines of Rust. Replace `"A256GCM"` with this exact
definition:

- **`alg`: `"A256GCM-S64K"`.** Receivers accept exactly this string. Any other value means
  "Couldn't open this photo" (no fallback, no negotiation).
- **Content key** `K`: 32 bytes from the OS CSPRNG (`getrandom`), fresh for every blob (R3).
- **Payload key** `Kp = HKDF-SHA256(salt = empty, IKM = K, info = "risime-media-v1 A256GCM-S64K", L = 32)`.
  This gives domain separation and room to derive a key-commitment value later (S2) without
  changing the format.
- **Padding before encryption** (R2): `P' = P ‖ 0x00 × (Padmé(L) − L)`, where `L = |P|` and
  `1 ≤ L`.
- **Segments:**
  - `P'` is split into segments of **65 536 bytes** (64 KiB) of plaintext. The last segment holds
    1 to 65 536 bytes.
  - `n = ceil(|P'| / 65536)`, and `n ≥ 1`.
  - A plaintext that is an exact multiple of 64 KiB has **no** empty trailing segment: its last
    full segment is the final one.
- **Nonce of segment `i`** (0-based), 12 bytes:
  `0x00 × 7 ‖ uint32_be(i) ‖ flag`. The flag is `0x00` for every segment except the last, which is
  `0x01`.
  - A fixed prefix is safe because `Kp` is unique per blob. It also removes the `nonce` field.
  - `i < 2^32`; the 16 MiB cap gives at most 256 segments anyway.
- **AAD of every segment:** the ASCII bytes `risime-media-v1` (no length prefix, no NUL).
- **Blob** = `C_0 ‖ C_1 ‖ … ‖ C_{n−1}`. Each `C_i = GCM-Encrypt(Kp, nonce_i, AAD, segment_i)` is
  the ciphertext followed by its 16-byte tag. There is no header, version byte or prefix.
  - `cipher_size = |P'| + 16·n`.
  - Ciphertext segment `i` starts at offset `i · 65552`.
- **Parsing the blob:** from `C = cipher_size`, `n = ceil(C / 65552)`. The last ciphertext segment
  is `C − (n−1)·65552` bytes, and it must be **≥ 17** (else `Format`).
  - Decrypt segment `i` with flag `0x00` for `i < n−1` and `0x01` for `i = n−1`. Any tag failure
    is `Integrity`.
  - This rejects:
    - truncation at a segment boundary (the new last segment has flag 0);
    - extension and reordering (nonce index);
    - a segment spliced in from another blob (another key).
- **After decrypting:**
  - `|P'|` must equal `Padmé(plain_size)`;
  - the bytes after `plain_size` must all be `0x00`;
  - the output is the first `plain_size` bytes.
- **Release of plaintext:** in v1.11, nothing is decoded or displayed until **every** segment and
  the final flag have verified. Progressive display of a verified prefix is a later option for
  video (S8). Never show bytes from a segment whose tag hasn't verified.
- **Envelope `enc` becomes:**
  `{"alg": "A256GCM-S64K", "key": "<b64 32 bytes>", "plain_size": n}`. The `nonce` field is
  removed. `blob.size` is `cipher_size`, as before.
- **Caps:**
  - The 16 MiB `media` cap applies to `cipher_size`. The largest plaintext that fits is
    **16 515 072 bytes**, after Padmé and tags. Senders check this after encrypting, which never
    triggers after the 2048 px re-encode.
  - For `icon`, 512 KiB of ciphertext.
- **Same format for icons:** `group_meta.icon.enc` is the same object.

**R2. Pad sizes to Padmé buckets (part of the R1 format).**
- **Why.** The server sees the exact ciphertext size. The re-encode pipeline is deterministic for
  a given source, device and library (2048 px, q85). So an honest-but-curious operator who holds a
  candidate photo can re-encode it and **confirm "user X sent this picture"** from the exact byte
  size. Exact sizes also fingerprint the same photo across conversations.
- **What Padmé gives** (Nikitin et al., PURBs, PETS 2019):
  `E = ⌊log2 L⌋, S = ⌊log2 E⌋ + 1, b = E − S, mask = 2^b − 1, Padmé(L) = (L + mask) & ~mask`,
  with `Padmé(L) = L` for `L < 2`.
  - It leaks only O(log log L) bits.
  - The overhead is at most about 6% at photo sizes, and typically 1–2%. For example, 1 300 000
    pads to 1 310 720, a multiple of 32 KiB near 1 MiB.
  - Power-of-two buckets would cost up to 100% for little extra privacy.
- **Later costs a new `alg`.** Adding padding later is a new `alg` and a second code path forever.
  It is required now only because it is part of the format.
- **What it doesn't hide.** Timing and the upload↔message link stay visible (see the answers on
  metadata). Document that, don't fix it.

**R3. Key and nonce generation rules: reuse impossible by construction.**
- The content key is generated **inside** `media_encrypt_file`, from the OS CSPRNG. No production
  API accepts a caller-supplied key.
- **No convergent or derived keys.** Nothing derived from the image content: it would leak
  equality and enable confirmation attacks.
- **The ciphertext is the unit of retry.** Retries (network, `5xx`, `429`, size or SHA mismatch)
  re-upload the **same stored blob file**.
  - If the local blob file is lost, the client re-encrypts with a **new key** (a new
    `media_encrypt_file` call) **and** a new `client_blob_id`, and it rewrites the stored envelope.
  - Re-encrypting under a stored key is forbidden, and the API makes it impossible.
- **Local values in the envelope.** The envelope's `blob.size` and `blob.sha256` are the
  **locally computed** values. The server's reply is only compared with them.
  - On a mismatch the reference is never sent. That includes an idempotent `200` that returns an
    older blob for a reused `client_blob_id`.
  - `blob_id` is the only value taken from the server.
- **Icons:** a fresh key per icon version, including when an admin re-sets the same picture.
- The core zeroizes `K`, `Kp` and plaintext buffers it owns (`zeroize`). Kotlin can't zeroize
  reliably, so it holds the key only as long as it must.

**R4. Strict receive-side validation and decode hardening.**
- **Why.** Every member's device decodes an attacker-chosen image **with no user action**: the
  thumbnail always, and the full image on auto-download. That is the classic 0-click surface
  (for example, the WebP heap overflow CVE-2023-4863 / BLASTPASS). MLS authenticates the sender;
  it doesn't make the bytes benign.
- **Envelope checks.** Before anything is fetched or decoded, the receiver checks:
  - `alg` is exactly `A256GCM-S64K`;
  - `key` decodes to exactly 32 bytes;
  - `1 ≤ plain_size`, and `Padmé(plain_size)` plus tags equals `blob.size`;
  - `blob.size` is at most the cap;
  - `sha256` decodes to exactly 32 bytes;
  - `1 ≤ w, h ≤ 2048`;
  - `thumb.data` decodes to at most 4096 bytes.

  If any check fails, the message is dropped as malformed (§3.1 rule).
- **Decode order:** size → SHA-256 → AEAD (all segments and the final flag) → padding check →
  decode. Never hand unverified bytes to a decoder.
- **Decoders:**
  - **Sniff the format from the bytes** and accept only JPEG, PNG and WebP. The sniffed format
    must match `mime`; otherwise "Couldn't open this photo".
  - Never route to HEIF, GIF, DNG or video decoders. Use `ImageDecoder` with an
    `OnHeaderDecodedListener` that rejects a header size larger than 2048×2048 (or 128×128 for the
    thumbnail), or one that differs from the envelope `w`/`h` by more than rounding, **before**
    pixel allocation.
  - Use a software allocator, so there are no hardware bitmaps from untrusted input.
  - Decode off the main thread, with a per-image timeout.
- A decode failure is "Couldn't open this photo", logged with no bytes.

**R5. Generate the thumbnail from the re-encoded pixels, never from embedded thumbnails.**
- **Why.** JPEGs from cameras and editors often carry an EXIF/JFIF **embedded thumbnail of the
  original**. That is the known "cropped photo leaks the uncropped original" bug.
  `ImageDecoder`/`ThumbnailUtils`/`MediaStore.loadThumbnail`/`ExifInterface.getThumbnail` may
  return it.
- **Rule.** The thumbnail is a downscale of the **same oriented, scaled bitmap** that was
  re-encoded for the blob. The source's embedded thumbnail, the MediaStore thumbnail and the
  Photo Picker's preview are never used.
- **Add a test** that re-encodes a fixture that has EXIF (with GPS and an embedded thumbnail),
  XMP and ICC. It asserts that the output and the thumbnail carry no APP1, APP2 or APP13 segment
  (JPEG), no `eXIf`, `iTXt`, `tEXt` or `iCCP` chunk (PNG), and no `EXIF`, `XMP ` or `ICCP` chunk
  (WebP).
- **Receivers must not rely on the claim** "decrypted bytes are already metadata-free" (§7.5).
  It holds only for honest senders.
  - Save to gallery should write the bytes as received; they're the sender's metadata, not the
    receiver's.
  - **Or** re-encode on save. This is android's call; document it.

**R6. Test vectors cover the format edges and the failures.**
- **Vectors.** `image_crypto_vector.json` becomes `media_crypto_vectors.json`, generated by a Rust
  test (`cargo test -p risime-mls media_vectors -- --ignored` writes it). Each vector carries `K`,
  `Kp`, `plain` (hex), `plain_size`, the padded length, `cipher` (hex) and `sha256`.
- **Positive cases:**
  - `L = 1`;
  - `L = 100`;
  - a length whose Padmé is exactly 65 536 (one full final segment);
  - a length padding to 65 537+ (two segments, last ≥ 1 byte);
  - a length padding to 196 608 (exactly three full segments).
- **Negative cases** (must all fail with `Integrity` or `Format`):
  - the last segment dropped (truncation at a boundary);
  - two segments swapped;
  - a segment appended from another vector;
  - the final flag on a non-final segment (encrypted that way on purpose);
  - a last ciphertext segment of 16 bytes;
  - one bit flipped in a tag;
  - a nonzero padding byte (a correctly encrypted P' with a bad pad);
  - a `plain_size` inconsistent with the blob size;
  - the wrong key.
- **Who runs them.** The Rust tests and the Android JVM tests (the host `libuniffi_risime.so`
  already loads in unit tests) run every vector. The contract gate gains this file.

## Suggestions (non-blocking)

**S1. Pad MLS application messages.**
- `risime-mls` sets no `padding_size`, so every PrivateMessage leaks the exact envelope length:
  - text length;
  - image versus text, because an image envelope with a thumbnail is 4–6 KiB;
  - caption length.
- Set OpenMLS `padding_size` (for example 256 bytes) in the group configs for DMs and groups. It
  still fits the 24 KiB cap with the 22 KiB envelope bound.
- This affects text too, so it is a separate small core change, not part of v1.11's format.

**S2. Key commitment before "report message".**
- GCM is not key-committing (the "invisible salamanders" problem). Today that can't be exploited:
  every recipient gets the same key in the same MLS message, and the envelope binds the
  ciphertext's SHA-256.
- When abuse reporting or franking arrives, add `enc.kc = HKDF(K, info = "risime-media-v1 commit")`
  and check it. The HKDF step in R1 makes this an additive field, not a new `alg`.

**S3. Forwarding re-encrypts.** A future "forward" re-encrypts the image with a new key and
uploads a new blob. Reusing `blob_id` and `key` across conversations would show the server the
link and would need cross-conversation read rights.

**S4. Crypto-shredding on delete.** When a message, or a whole chat, is deleted on the device,
delete the key row and the cached ciphertext in the same transaction. A later "delete for
everyone" can then rely on keys being gone, not on blob deletion.

**S5. Device removal should revoke that device's session token.**
- A removed device (lost phone) still holds the keys of old images.
- The interval read rule is per **user**, so a stolen device with a live user token can still
  fetch every blob the user may read.
- This is broader than images, so it's a note for the server and root.

**S6. Document the metadata model in the privacy note (§9):**
- padded sizes;
- upload time (which links blob to message, since upload is followed by `msg:send`);
- download times and downloader identity (a read signal similar to receipts);
- auto-download as an "opened the chat" signal;
- joiners being able to fetch pre-join blobs. They can't name them, because `blob_id`s live
  inside encrypted envelopes, and they would learn sizes only.

**S7. The ciphertext `sha256` is a corruption check, not a security boundary.** Keep it: it
detects a bad resume early and matches §12.6. Say so in the text, so nobody "optimises" the AEAD
check away because "the hash already matched".

**S8. Later, progressive display of a verified prefix** (useful for video). Segments verified in
order may be shown before the final flag. The UI must then treat "final segment never verified" as
a failure and discard what it showed. Not needed for v1.11 photos.

## Answers to the crypto open points

1. **Single-shot versus chunked:** chunked, now (R1). GCM's limits aren't the reason; 16 MiB is
   far inside them. The reasons are:
   - streaming encrypt and decrypt with bounded memory;
   - per-segment verification of `Range`-resumed downloads;
   - one permanent format shared with video, given that icons and cached blobs outlive any
     transition.

   Exact spec: `A256GCM-S64K` in R1.
2. **Nonce:** with a fresh key per blob, the nonce carries no security weight. R1 uses a
   deterministic STREAM nonce `0^7 ‖ BE32(i) ‖ final` and **drops `enc.nonce`**.
   **Key reuse is never allowed**, and R3 makes it impossible through the API.
3. **AAD binding `blob_id`, the conversation or the MIME type:** **no**, keep the constant
   `risime-media-v1`.
   - **The binding already runs the other way.** The MLS-authenticated envelope commits to the
     blob by `sha256` and `size`, and to the key. MLS binds the envelope to the group, the epoch
     and the sender's leaf.
   - **The server can't substitute.** A swapped, replayed or older blob fails the SHA-256 check
     and the GCM tag, because it was encrypted under another key.
   - **`blob_id` would force a reserve-then-encrypt round trip** and gain nothing.
   - **Binding the conversation adds nothing.** The key only ever exists inside that
     conversation's MLS group.
   - **Binding `mime` adds nothing either.** `mime` is already authenticated by MLS, and a
     malicious sender controls both anyway. The real defence is R4: sniff the format, use an
     allowlist, and require a match.
4. **No plaintext digest:** **agree.**
   - GCM authenticates the plaintext under a key only members hold, and the envelope binds the
     ciphertext digest.
   - A plaintext hash would add a stable cross-chat fingerprint, and would enable
     confirmation-of-file against a leaked envelope.
5. **Inline thumbnail with no second layer:** **agree.**
   - It lives in the MLS PrivateMessage, with exactly the protection of the caption and of text.
   - A second layer would put its key in the same message, so it adds nothing.
   - Conditions:
     - R5: generate it from the re-encoded pixels;
     - R4: it is a 0-click decode, so validate and harden it;
     - S1: its size leaks through unpadded MLS messages.
6. **Downgrade and substitution:**
   - **Plaintext downgrade** is impossible: there is no plaintext path, and `not_e2ee` blocks
     uploads for legacy DMs.
   - **`alg` downgrade:** the server can't change `alg`, because it sits in the MLS-authenticated
     envelope. Receivers accept one exact value (R1).
   - **Blob swap or replay:** the server can only make an image fail to load (denial of service),
     never show a different one (answer 3).
   - **Upload reply substitution:** a forged `blob_id` or digest in the upload reply is caught by
     R3's local digest rule.
   - **Replayed MLS messages:** rejected by the MLS secret tree (consumed generation keys) and by
     `message_id` dedupe.
   - **A member re-sending an old envelope** is equivalent to forwarding a picture they already
     have. It is acceptable.
   - **The icon reference** sits in the GroupContext, so it is epoch-authenticated and can't be
     rolled back by the server.
7. **Group icons and removal:**
   - **No re-encryption on member removal.** The icon is current, shared state that the removed
     member has already seen. Re-keying it would cost an upload per removal and protect nothing.
   - Server-side denial of reads after removal is fine as housekeeping. It is not a cryptographic
     guarantee, so don't describe it as one.
   - Any icon **set after** the removal gets a fresh key (R3) in a commit that the removed member
     can't decrypt, so they can never read it.
8. **Removed members keep old images: acceptable.**
   - This matches MLS semantics: removal gives secrecy for later messages, not retroactive
     revocation.
   - They received the keys while they were members and could have downloaded at that moment.
   - The interval read rule only spares them from a race. The rule should be stated in
     user-facing terms in the privacy note ("people removed from a group keep what was shared
     while they were in it").
9. **Metadata and sizes:**
   - Pad sizes with Padmé (R2) and the MLS messages (S1).
   - Timing and who downloads what stay visible to the server. Document them (S6) rather than add
     cover traffic, which is out of proportion for a corporate pilot whose server is ours.

## Summary of format changes to fold into §3
```json
"enc": {"alg": "A256GCM-S64K", "key": "<b64 32 bytes>", "plain_size": 1300000}
"blob": {"blob_id": "…", "size": 1311040, "sha256": "<b64 SHA-256 of the ciphertext>"}
```
(1 300 000 bytes pad to 1 310 720 and are encrypted as 20 segments of 64 KiB; adding 16 × 20 bytes
of tags gives a ciphertext of 1 311 040 bytes.) The same `enc` is used in `group_meta.icon`.
Example and vector files: `media_crypto_vectors.json` replaces `image_crypto_vector.json`.
