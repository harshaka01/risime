# Android review: contract proposal v1.9 (MLS groups)

**Reviewer:** android role, 2026-10-06. **Proposal:** `contract/proposals/2026-10-06-groups-v1.9.md`,
including its "Review outcomes so far" (crypto and server).
**Verdict:** feasible on the current app. Merge after the **required changes** (R1–R12) below.
Most of them are wire-level gaps that would otherwise get filled in by guessing on both sides.

How the current app does things, which this review is based on:
- `MlsPipeline` / `MlsUpgrader` / `MembershipExecutor` (`data/mls/`) are written for DMs.
- `ChatEngine`, `ChatViewModel`, `ChatsViewModel` and the push planner (`PushLogic`) are keyed by
  **peer id**, and derive `dm:` ids with `dmConversationId`.
- `MessageData.to` and `MessageEntity.to_id` are non-null.
- `mls_kv` values are read through a `Cursor` (`MlsDbKey.queryBlob`).
- Room is at v4.

---

## Required changes (blocking)

**R1. "Group-ready" must mean a groups-capable app, not just MLS.**
- The current v1.8 app is MLS-capable, so §0 lets it be added to a group. But it would:
  - fail to decode a `message` event with no `to` (`MessageData.to` is non-null), skip it, and
    move the cursor past it, so the message is lost on that device;
  - join `grp:` Welcomes and act on `grp:` `mls_membership` with the DM rules;
  - have key packages without capability `0xFA01`.
- Required:
  - `not_ready` (and `missing[].reason`) must also cover "an app instance seen in 30 days is older
    than v1.9", using the census `app_version` or a capability flag sent on the socket connect;
  - a member is added with **all** their devices or not at all;
  - add a `missing` reason value, e.g. `"no_groups"`, so the UI can say "<name> needs to update".

**R2. Key-package claim for co-members.**
- §10.2 `claim` is "friends and yourself" only, but group members are often not friends.
- Every path below needs to claim a non-friend's key packages:
  - the named committer adding a member's new device;
  - a re-add after reinstall;
  - a reset rebuild (R7).
- Required: `claim` accepts `"conversation_id": "grp:…"` and then allows any **active** member of
  that group (the caller must be an active member). `not_friends` becomes `not_member` in that mode.

**R3. Commit authorisation for device churn in groups.**
- §3 lists `pending_add`/`pending_remove`/`left`, meta and self-update. It doesn't cover:
  - adding a **new device of an existing active member** (from `mls_membership added`);
  - removing a **no-longer-current device** of an active member.
- Both happen whenever someone gets a new phone, and adds are "admins only" today.
- Required, for any member's device:
  - it may add only current MLS devices of active members that aren't already in the group;
  - it may remove only devices that are no longer current, as in DM §10.2;
  - the crypto staged-commit policy must allow the same.

**R4. Name exactly one committer in groups (no 255-way race).**
- In a 256-member group, "any member after a random 5–30 s" for leaves and `mls_membership` means
  up to 255 devices each doing claim → commit → `409` → catch-up. That burns key packages (claims
  consume them) and battery.
- Required: the server names the committer in the event, as
  `"committer": {"user_id", "device_id"}, "fallback_after_s": 30`.
  - The order is: the admin device or the user's own other device first, then one server-chosen
    online member.
  - Only the named device acts. A fallback device is named by a **new** event if nothing has
    landed by the deadline.
- This applies to `group_event` `left`/`removed` and to `mls_membership` for `grp:` conversations.

**R5. Pending operations must be visible and finishable.**
- `POST …/members` and `DELETE …/members/{id}` create `pending_add`/`pending_remove`. If the admin's
  device dies before committing, nobody knows the commit is owed.
- Required:
  - `Member` gains `"state": "active" | "pending_add" | "pending_remove"`;
  - any admin device, including the same admin's other devices, may complete a pending operation;
  - pending operations expire after a stated time (proposal: 24 h), with a `group_event`
    `add_expired`, or by being silently dropped, but stated either way;
  - `GET /groups/{id}` is how a client finds owed work after a restart.

**R6. `group_event`: shape, timing and ordering.**
- Each event that comes from a commit (`created`, `added`, `removed`, `left`, `role_changed`,
  `metadata_changed`) is written **in the same critical section as the commit's events** (the §10.2
  ordering rule), not at REST time.
- It carries `"generation"` and `"epoch"` (the new epoch). Then the client can show the system line
  only once its MLS state reaches that epoch, and members, keys and UI stay in step.
- `role_changed` carries `"role"`. `created` carries the full `members` (the creator is the actor).
- State whether the affected user gets `removed` before or after their `removed_self` commit. The
  client copes either way, but the order should be fixed.
- `created` is emitted only when the epoch-0 commit lands. A group whose creator never committed
  must not appear in anyone's list. Say what happens to it: proposal, the server deletes it after
  10 minutes.

**R7. Reset (`generation + 1`) must be specified end to end.** The outcome names an endpoint only.
- **Who** may call it (proposal: any active member, rate-limited to 1 per hour per group).
- **Endpoint:** `POST /api/v1/mls/groups/{grp}/reset` `{"generation": current}` → `200
  {"generation": n+1}`, with `409` if the generation has already moved.
- **Event:** `group_event` `action: "reset"` with the new `generation` and a named rebuilder
  (the caller's device).
- The rebuilder makes epoch 0 of the new generation, claiming via R2. It copies `group_meta` (name,
  icon, admin list) from **server roles plus its last local meta**.
  - State that the server's role list wins if they differ, because the local state may be what's
    broken.
- **Clients** drop the old group, park new-generation events (the existing pipeline already does
  this), and show a system line "Encryption was reset; some messages may be missing".
  - The outbox re-encrypts on `stale_epoch`.
  - Old-generation messages that were never decrypted are lost; that is acceptable, but state it.
- **Client trigger:** a client may call reset only after a commit is `Rejected` by its core, or the
  commit log is gone (R8). It never does so on a transient error.

**R8. Commit catch-up for groups.**
- `GET …/commits?since_epoch=e` has no paging. In groups:
  - commits can be up to 1 MiB (or blob references);
  - 1000 epochs is a lot more data than in a DM.
- Required:
  - add `limit` (default 50) and `has_more`;
  - define the reply when `since_epoch` is older than what's retained: proposal `410
    commits_expired`, after which the client calls reset (R7).
- Today the app parks a commit whose epoch is ahead of its state, and it fetches commits only after
  a send fails with `stale_epoch` or `e2ee_required` (`catchUpCommits`). The app will add a
  catch-up when it parks a commit; the server must not mind that extra call.

**R9. Blob references for commits and Welcomes over 64 KiB.**
- The outcome says "uploaded as a blob and sent by reference", but no blob API exists yet, because
  images come later.
- Required: define it in v1.9:
  - upload `POST /api/v1/blobs` → `{"blob_id"}`;
  - `GET /api/v1/blobs/{id}`, authorised for the group's members and the Welcome's `to_devices`;
  - its TTL;
  - the event fields: `commit_ref`/`welcome_ref` **instead of** `commit`/`welcome`, with exactly
    one of the two present.
- The app must fetch the blob before it can process the event. That is a network call inside
  strictly ordered processing, so the client fetches it first and then applies the event in a
  transaction.

**R10. Receipts: define `group_receipt` and `GET …/receipts`.**
- §4 says that each member's ack creates a per-member `status` to the sender. The outcome says it
  is aggregated. Pick one: the app wants **aggregated only** for `grp:`, and no per-member `status`
  events.
- Proposed `group_receipt`:
  `{"conversation_id","message_id","client_msg_id","delivered":n,"read":n,"of":n,"all_delivered":bool,"all_read":bool}`.
  - It is sent to the sender's user (all their devices), and at most once per message per change
    of `all_*` (or coalesced).
  - `of` counts the members at send time who are still active.
- `GET /api/v1/groups/{id}/messages/{message_id}/receipts` →
  `{"receipts":[{"user_id","delivered_at"|null,"read_at"|null}]}`, for the sender only (`404`
  otherwise).

**R11. `msg:send` / `typing` / reaction fields for `grp:`.**
- Give the exact shapes:
  - `msg:send` `{"client_msg_id","conversation_id","ciphertext","generation","epoch","client_ts"}`;
  - `to` and `conversation_id` are mutually exclusive (`bad_request` if both);
  - `typing` `{"conversation_id","typing"}`, with the error `not_member`.
- For the `typing` signal, `data.from` is the typist and `conversation_id` is the group.
- The idempotent-resend check comes **before** `not_member`. Otherwise a member who has just been
  removed and retries a message the server already accepted gets `not_member`, and the app marks it
  failed even though it was delivered.
- Add a `contract/v1/examples/` file for each new shape: Group, the `group_event` actions,
  `group_receipt`, the group `message`, and the group typing signal.

**R12. Leaf cap, not just a user cap.**
- 256 users × up to 10 devices = 2,560 leaves. Each leaf is about 0.7–0.9 KB with the attestation
  JWS, so the ratchet tree is about 3–4 MB.
- That breaks the 2 MiB Welcome cap. It also breaks Android's **2 MB `CursorWindow` limit**:
  `mls_kv` reads use `Cursor.getBlob`, and a tree value bigger than that throws
  `SQLiteBlobTooBigException`.
- Required:
  - cap **leaves per group** at 768 (proposal; about 3 devices per user at the full cap);
  - add `422 too_many_devices`;
  - the app will chunk large `mls_kv` values anyway (see the Risks section), but the wire cap must
    exist.

## Suggestions (non-blocking)
- **S1.** `POST /groups` should take `"client_group_id": "uuid"` for idempotency, so a retry after a
  timeout doesn't create a second group. Leave, remove and role changes should be idempotent
  (`204` when repeated).
- **S2.** `Member.display_name` for non-friends: say whether it's live or a snapshot. The app caches
  it in `group_members`, and a `group_event` `profile_changed` is unnecessary if `GET` is
  refreshed when the chat is opened.
- **S3.** Removal or leave: the leaver's device should keep the history read-only and show "You
  left" / "You were removed". `GET /groups/{id}` then returns `404`, which is fine because the app
  keeps its local snapshot.
- **S4.** Being added to a group should notify ("Kamal added you to <name>"). The name comes from
  the Welcome's `group_meta`. Leaves, renames and role changes don't notify.
- **S5.** Rate-limit group typing to at most 1 `true` per 3 s per member per group, sent only to
  members who are **online and have that chat open**. The app will only send while the composer
  has focus.
- **S6.** Admin policy disagreements: for display, the app shows **the server's roles** (Group /
  `group_event`). The crypto admin list decides what the core accepts. If they disagree, the app
  logs it and asks for a reset only if commits are being rejected.
- **S7.** Successor rule (lowest `leaf_index`): the server can't see leaf indices if commits are
  PrivateMessage. Either clients declare the index, or the rule becomes "longest-standing member"
  (as in §2), with the successor's role written into `group_meta` by the leave-removal commit.
- **S8.** Per-group mute is local-only for now. It needs no wire change.

## Answers to the Android open points
- **Group list and chat.**
  - One chats list mixing DM and group rows, sorted by last activity.
  - A group row shows the decrypted name (or "New group" until the Welcome is processed), the last
    line prefixed with "Kamal: ", unread count, and a "typing" line ("Kamal is typing…", or
    "2 people are typing…").
  - The group chat shows sender names above incoming bubbles, coloured per member and grouped for
    runs by the same sender, and the same e2ee strip/lock as DMs.
  - The DM-only header items are hidden: presence, Call, and the friend check.
- **Create group.**
  - FAB → "New group" → a multi-select of **accepted friends** (searchable; non-ready friends are
    greyed with "needs to update").
  - Then the name (required, 1–100 graphemes) → Create. The flow is `POST /groups` → claim → an
    epoch-0 commit with `group_meta` → open the chat.
  - It runs from a persisted `group_ops` outbox, so it survives process death.
  - The icon comes later, with blobs and images.
- **Info screen.**
  - Header with name and member count. Members are listed with an "Admin" chip; the Risi agent
    shows later with an "Agent" chip and can't be made admin.
  - Admins see "Add members" (friends picker), and a member's menu offers "Remove" or
    "Make/Dismiss admin".
  - Everyone sees "Leave group", with a confirmation. Leaving is immediate locally and makes the
    chat read-only.
  - Admins can rename; the name is shown from the local `group_meta`.
  - Pending adds and removes show as "Adding…" / "Removing…" until their `group_event` lands.
- **"Read by" sheet.**
  - Long-press your own message → "Info" → two lists, "Read by" and "Delivered to", with times, from
    `GET …/receipts` (R10), fetched on open and not stored.
  - Ticks in the chat come from `group_receipt`: ✓ sent, ✓✓ when `all_delivered`, accent ✓✓ when
    `all_read`.
- **System lines.** These are local rows in the message list, rendered as centred grey text:
  - "Kamal created the group", "Kamal added Nimal and 2 others", "Nimal left", "Kamal removed
    Nimal", "Kamal made Nimal an admin", "Kamal changed the group name to …", "You were added",
    "Encryption was reset".
  - Names come from `group_members`, with "You" for me. There is no unread count, no notification
    (except S4), and no reactions.
- **Notifications.**
  - One notification per conversation (as today), using `NotificationCompat.MessagingStyle` with
    `setGroupConversation(true)` and the group name as the conversation title.
  - Each line has a sender `Person`.
  - The notifications stay in the existing `GROUP_MESSAGES` bundle.
  - The open-chat intent and the "open chat" suppression move from peer id to **conversation id**.
    Today a DM open with Nimal would also suppress Nimal's group messages.

## Room migration v4 → v5
These are additive, so there is no table rebuild:
- **`groups`**:
  - `conversation_id` (PK, `grp:…`), `name`, `my_role`, `state` (`active`|`left`|`removed`),
    `created_at`;
  - `generation`, `epoch_seen` (the last `group_event` epoch);
  - `meta_updated_at`, `last_refreshed_at`.
  - The name is a cached copy of the encrypted `group_meta`; it is kept for the list and for
    notifications.
- **`group_members`**:
  - `(conversation_id, user_id)` PK, `display_name`, `phone` (nullable), `role`, `kind`, `state`
    (`active`|`pending_add`|`pending_remove`|`left`|`removed`), `joined_at`;
  - an index on `user_id`.
  - Rows for former members are kept, so old bubbles keep their names.
- **`group_ops`**: the outbox for REST plus commit work.
  - Columns: `id`, `conversation_id`, `type` (`create`|`add`|`remove`|`leave`|`role`|`rename`|
    `reset`), `payload_json`, `state`, `attempts`, `created_at`, `client_group_id`.
- **`messages`**:
  - `kind TEXT NOT NULL DEFAULT 'text'` (`text`|`system`), with `system_json TEXT` for system lines;
  - `receipt_delivered INTEGER`, `receipt_read INTEGER`, `receipt_of INTEGER` (group sender side).
  - `to_id` stays NOT NULL: for groups it holds the conversation id. This avoids a SQLite table
    rebuild; Kotlin code reads `to` only for `dm:` conversations.
- Unchanged: `mls_kv`, `mls_pending`, `reactions`, `seen_events`, `contacts`.
- `wipeDb()` clears the three new tables.
- Migration tests: run from v4 with fixture rows, as for 3→4.

## Risks
- **Large group state on a phone.**
  - At 256 users and about 1.3 devices each, there are about 340 leaves, a tree of about 300–400 KB,
    and about 9 path nodes. That's fine.
  - Worst cases:
    - **Join from a Welcome:** about 340–768 Ed25519 attestation verifies plus tree validation. That
      is about 0.2–0.6 s on a mid-range phone, which is acceptable in the background.
    - **Creating a 256-member group:** about 340 HPKE seals plus 255-user claims (the claim rate
      limit allows it in one call). About 1–2 s.
  - Both run on the IO dispatcher inside one transaction, and the inbox waits behind it. It is not
    on the main thread.
  - **Every message decrypt** loads the group from `mls_kv`: about 0.4 MB unsealed with AES-GCM and
    deserialised. The FFI should keep an in-memory group cache (invalidated on rollback). That is a
    crypto/FFI task; the app measures it with a 256-member benchmark test.
- **`CursorWindow`.** The app will split `mls_kv` values over 512 KB into chunk rows (the
  namespace/key schema gets a `part` suffix, sealed per chunk) as a safety measure, alongside R12.
- **Multiple devices.**
  - The user's own other device commits their new device's add at once. That is allowed only
    with R3.
  - Each device processes every group commit, so cost scales with groups × devices, which is fine.
  - Removal of a user removes **all** their leaves in one commit.
  - Devices in the same group that belong to the same user must skip their own `from_device` (as
    now).
- **Never merge before the `200`.**
  - With group churn, a pending commit is more likely to lose. The pipeline already drops the
    pending commit (`discardedOwnPending`) and the executor redoes it only if it's still needed.
  - The new rule: a pending group op is **re-derived from server state** (R5) after a `409`, never
    replayed blindly.
  - The process can die between the `200` and the merge, leaving a commit the server accepted but
    the device never merged. On restart, the device sees its own commit in `GET …/commits` (or as
    `mls_commit` from its own device, which the pipeline skips today).
    - The fix: persist the pending commit's epoch in `group_ops`. If the server epoch is past it and
      the commit at that epoch has our `from_device`, merge the staged commit instead of skipping.
    - This needs `commitAccepted` to survive a restart, which is a crypto/FFI point. It also
      matters for DMs today.
- **Peer-keyed code.** `ChatEngine.sendText/react`, `conversationPeer()`, `ChatViewModel`,
  `buildChatRows`, `planChatNotifications` and `openChatPeer` all assume `dm:`. The refactor to
  conversation ids is the first chunk below, and it has no behaviour change for DMs.

## Proposed android chunk order
Each chunk ends with green `./gradlew assembleDebug testDebugUnitTest`.
1. **Conversation-id refactor.** The engine, view models, push planner and open-chat state are keyed
   by conversation id. `grp:` events are guarded: they are ignored until chunk 4. No UI change.
2. **Protocol models.**
   - Group, Member, `group_event`, `group_receipt`, `msg:send` with `conversation_id`, typing,
     optional `MessageData.to`, and the blob refs.
   - Tests that parse every new example file.
3. **Room v5.** The migration above, plus the `mls_kv` chunking and migration tests.
4. **Receive path.**
   - `group_event` → `groups`/`group_members` plus system lines.
   - Group Welcome/commit through the existing pipeline, with catch-up on park (R8) and blob fetch
     (R9).
   - Group messages with sender names. `group_receipt` → ticks.
5. **Engine API** (with the crypto FFI): `createGroup(meta)`, multi-user add/remove, `updateMeta`
   (rename/role), `groupMeta()`, and the 0xFA01 key packages (re-upload with `replace: true`).
6. **Group ops outbox:** create, add, remove, leave, role and rename, plus the named-committer
   handling (R4) and the R5 recovery.
7. **UI.** Group rows, the New group flow, group chat (names, typing), the info screen, and the
   Read by sheet.
8. **Notifications:** MessagingStyle groups, "added you" (S4), and suppression by conversation id.
9. **Reset (R7)** and the 256-member benchmark (fake server, real core on device); interop-gate
   cases for groups.
