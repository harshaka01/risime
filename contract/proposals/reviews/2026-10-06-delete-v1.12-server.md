# Review: PROTOCOL v1.12 delete messages and chats, server side

**Reviewer:** server role, 2026-10-06.
**Proposal:** `contract/proposals/2026-10-06-delete-v1.12.md`; **decision:** 047 (proposed).
**Verdict:** accept, provided the **required changes** below are made. The overall shape is good:
one push, one event kind, `gone` counts as success, targets authorised from `message_index`, and
point deletes keyed by `event_id = message_id`. The required changes fix these:
- the rollout (root's no-required-update constraint);
- one crash-recovery hole;
- an ordering bug that makes the rate limit too late;
- metadata leaking to members who joined later;
- several existing code paths that would resurrect or re-announce a deleted message.

## What I checked (facts this review relies on)
- **`messaging.ex`.**
  - `message_id = TimeUUID.generate()` and `server_ts = now()` are **two separate clock reads**
    (TimeUUID: `System.system_time` in 100 ns, strictly increasing; `server_ts`: ms-truncated
    `DateTime.utc_now`). They differ by microseconds to a few milliseconds, so §4.1's "one clock
    read" is not literally true. That is harmless with the receivers' 5-min grace.
  - **Group sends take no lock.** `send_group_new/2` checks the epoch against Postgres and writes,
    outside `Groups.locked/2`. Only commits, REST group changes, ops and timers hold the advisory
    lock (`pg_advisory_xact_lock(hashtext("mls:" <> conv))`). DM commits use the same lock in
    `mls.ex`.
  - **Code paths that read `message_index` and would act on a deleted message:**
    - `ack/3`: a DM recipient ack calls `advance` → CAS status → a new `status` event.
      Group acks call `GroupReceipts.ack`.
    - `check_reaction/2` accepts any row with `kind: nil` and the same conversation.
    - `resend/3` re-delivers only when the index row is missing.
    - `GroupReceipts.list/3` serves the receipts endpoint.
- **`GroupReceipts`** keeps a per-message cache in partitioned GenServers, with a **coalescing
  timer** that emits a `group_receipt` event up to 10 s after the last ack.
- **Cassandra** (`priv/cql/001–003`):
  - `inbox_events ((user_id), event_id)`: TWCS, 1-day windows, 30-day TTL, default
    `gc_grace_seconds`.
  - `message_index` (PK `message_id`): 30-day TTL, no TWCS.
  - `group_receipts ((message_id), user_id)`: TWCS.
  - `sent_dedupe`: 24-hour TTL, LWT `IF NOT EXISTS`, **shared by every push that has a
    `client_msg_id`**.
- **Status events** (`publish_status`): sender's partition only, a fresh TimeUUID, **pushed**.
  **`group_receipt`**: sender only, not pushed. **Plaintext reactions:** both partitions,
  `event_id` = the reaction's own `message_id`, with a `message_index` row of `kind = 'reaction'`.
- **Blobs** (the images agent's work in progress, uncommitted):
  - `Blobs.remove/1` is the internal delete by reference, idempotent: it sets `deleted_at`, keeps
    the row until expiry and removes the file at once.
  - `Blobs.delete/2` is the owner-only REST delete.
  - `BlobCleanup` sweeps expired rows and orphan files.
  - `delete for everyone` can reuse `remove/1` as it is.
- **Old apps:** `android/.../data/ChatEngine.kt` `onEvents`. An unknown `kind` hits
  `else -> false`. It is marked seen and **advances the cursor**, with no decrypt and no UI.
- **Backups:** `scripts/backup` snapshots Cassandra (`nodetool snapshot`) and keeps 14 sets by
  default. Blobs use `rsync --link-dest` sets.

## Required changes

**R1. Rollout: no `required` update (root's constraint, decision 016).**
- §0 ("rollout is a `required` update"), §9 and decision 047 §5 must say: deploy the server, then
  a **normal (optional)** app update.
- `required` is reserved for the server dropping a protocol (016 amendment), and v1.12 drops
  nothing.
- Spell out what an old (≤ v1.11) app shows. I verified this in the code above.
  - **The deleted message stays on screen** (text, or the image bubble), with its notification
    and chat-list preview.
    - The `delete` event is skipped by `else -> false` and advances the cursor.
    - In E2EE chats it is never decrypted. Skipping one generation of the deleter's sender
      ratchet is within MLS's forward tolerance.
  - **An image that was not yet downloaded** gets `404` once the blob is removed, so it shows
    the existing "This photo is no longer available" state. A downloaded or cached image stays.
  - **A reinstall of the old app doesn't bring the message back**, because the server rows are
    gone. Old status/receipt events for it are no-ops (no row to update).
  - **Acks** from old apps for a deleted message are ignored (R5).
  - **A plaintext reaction** to it gets `unknown_target`, the same path as reacting to an expired
    message.
  - **Receipts** for it return `404`.
  - Nothing crashes, nothing blocks, and no MLS state is harmed.
- Suggested dialog small print: "People on an older app may still see it" (see the `deletes`
  capability under Suggestions).

**R2. Crash recovery must finish targets that were never tombstoned (§7.3).**
- The recovery rule only recognises targets "tombstoned with `deleted_by` = caller and
  `deleted_at` = claim ts".
- A crash **between step 2 (claim) and step 3** leaves a claim and no tombstones. The retry then
  reports every target as `gone`, stores no event and deletes nothing, while the claim says the
  delete happened.
- Rule: on a claim hit, run steps 1 and 3–6 again with the claim's `message_id`/`server_ts`:
  - a target tombstoned by the caller at the claim ts is `deleted`;
  - a target not yet tombstoned is authorised again, measuring 48 h against the **claim's
    `server_ts`** (the first attempt was judged then; the 24-hour dedupe window bounds it), then
    tombstoned;
  - a target tombstoned by someone else is `gone`.
- Also enqueue the step-6 Oban job **right after the claim**, carrying the targets and the event
  data, so the server finishes the delete even if the client never retries (uninstall, logout).
  Only the reply needs the client.

**R3. Rate limit before the per-target reads (§1.5, order of checks).**
- As written, `rate_limited` comes after up to 100 `message_index` reads and a blob query. A
  limited client can still force about 100 Cassandra reads per push.
- Order: idempotent resend → membership/participant → e2ee → shape → **rate limit** →
  per-target authorisation → blob checks → delete + store.
- An authorisation failure still counts against the limit (`RateLimiter.hit/4` counts every hit).

**R4. Per-target metadata only to users who had the target (§2, §4.4).**
- The `delete` event goes to the *current* active members, with `targets[].from`/`server_ts`.
- A member who joined after the message never had it, yet would insert a **positioned "This
  message was deleted"** before their join. That leaks that a message existed, who sent it and
  when (§13.3 hides even that), and it is confusing.
- Rule: for each recipient user `u` and each `deleted` target, include `from`/`server_ts` only if
  `u` is the target's `sender_id` or in its `recipients` (DM: either participant). Otherwise send
  nulls, which gives a hidden tombstone (§5.3).
  - The ciphertext is identical for all; only the per-target metadata varies.
  - `publish_batch` already writes per user, so this costs nothing.
  - The DM payload is unchanged.

**R5. Every path that reads `message_index` must treat a tombstoned row as absent.**
List these in §7.3 and make them part of the server test list:
- `ack/3`: no status CAS, no `status` event, no `GroupReceipts.ack`;
- `check_reaction/2`: `unknown_target`;
- `GroupReceipts.list/3`: `404`;
- `resend/3`: the row exists, so no re-delivery. Keep this behaviour, and keep it covered by
  R6.

In addition:
- The delete job must **evict the `GroupReceipts` cache entry and cancel its timer**
  (`{:drop, message_id}`). Otherwise a pending coalesced timer emits a `group_receipt` for the
  deleted message up to 10 s later, after its refs partition is already gone.
- `Store.get_message/1` must return `deleted_at`.
- An ack and a delete can still race: an ack that read the row just before the tombstone can
  append a `status` after the step-6 job ran Q7. Schedule the job about 15 s after the commit
  point (`schedule_in`), and accept the remaining window. A leftover `status` is content-free and
  expires with its TTL.

**R6. Write the `message_index` tombstone with the row's remaining TTL (§7.2 last bullet).**
- "May" must become "must". Q3 reads `TTL(sender_id)`, and Q3d is
  `UPDATE … USING TTL <remaining> SET deleted_at, deleted_by`.
- Otherwise, after the original cells expire, a zombie row survives with only `deleted_at` and
  `deleted_by`, and with `sender_id`/`conversation_id` null for up to 30 more days. Every reader
  would then have to handle a row without a sender.
  - `Store.Cassandra.conversation_pairs/2` (friendship migration) would yield `{nil, nil}` pairs.

**R7. Index the `delete` event itself (§2/§4.1 step 1 assume it; §7.3 doesn't write it).**
- Step 5 must also `put_message` the `delete` event's `message_id` with `kind = 'delete'`, the
  sender, `recipient_id` (DM) or `recipients` (group), and the 30-day TTL. This gives:
  - §4.1 step 1 (`kind = delete` → `gone`) and reaction targeting (`unknown_target`) work;
  - `ack/3` can skip it alongside `reaction`. Without this, a DM recipient's ack of a `delete`
    event with `recipient_id` set would advance a status and emit a `status` event;
  - a claim hit can tell a `msg:delete` claim from a `msg:send` claim, because `sent_dedupe` is
    shared. A client reusing a `msg:send` `client_msg_id` for `msg:delete` must get
    `bad_request`, not the message's reply.

**R8. Blob mismatches must not fail an otherwise valid delete (§1.5 `bad_request`, §4.1 Blobs).**
- The rule "a `blob_id` … owned by the sender of one of the **`deleted`** targets, else
  `bad_request`" breaks idempotency.
  - When two of my devices delete the same image concurrently, or when the original target
    expired, the second request has `deleted = []`. Its `blob_ids` then fail the check, and it
    gets `bad_request` instead of success.
- Check blobs against the senders of the `deleted` targets **and** of the targets that are `gone`
  because already tombstoned (the tombstone keeps `sender_id`, R6).
- **Skip and log** any other mismatch rather than refusing the request. The check is
  housekeeping: an owner can already `DELETE` their own blobs (§14.2), and an admin can delete
  those messages anyway.
- Implementation: one query in `RisiMe.Blobs`, e.g.
  `media_ids_owned_by(ids, conv, owner_ids)`, using
  `SELECT id FROM blobs WHERE id = ANY($1) AND conversation_id = $2 AND purpose = 'media' AND owner = ANY($3)`.
  Then `Blobs.remove/1` per id in the job. No new blob code beyond that; it reuses the images
  agent's `remove/1`.

**R9. `scope: "me"` may only delete `message`/`reaction` rows of the named conversation (§1.3).**
- "Deletes `(me, target)` if its payload's `conversation_id` matches" must also require
  **`kind ∈ {message, reaction}`**, read in the same point read.
- Otherwise a client can name the `event_id` of its own `mls_commit`/`mls_welcome`/`group_event`
  rows, whose payloads carry the `conversation_id` too. That breaks its own fresh-install replay,
  which §6 explicitly protects for `chat:clear`.

**R10. Say plainly what "the server removes its copies" means on disk (§0, §10).**
- Point deletes in a TWCS table are **logical**. The tombstone lands in today's window, while the
  shadowed data sits in an older window that TWCS doesn't recompact. The bytes (ciphertext; for
  legacy plaintext DMs, plaintext) therefore stay in SSTables until their window's TTL expires,
  at most 30 days.
- Backups keep them for up to 14 days after that (`BACKUP_KEEP`), and a restore resurrects them
  in inbox partitions. Devices with (hidden) tombstones drop them again; fresh installs would show
  them.
- §10 should say: "removed from every API response at once; physically purged within 30 days;
  backups expire after 14 days."

## Suggestions
- **No conversation lock** (answer S4). Group sends don't hold it today, and holding a Postgres
  transaction across 100 reads plus an N-member fan-out would block commits.
  - Plain idempotent writes are enough.
  - Two concurrent deleters of one target (a sender and an admin) both announce it. Receivers
    are idempotent, and the second's crash recovery reports it as `gone`, which is success.
  - If we want a single announcer later, a per-target LWT
    `UPDATE … SET deleted_at = ?, deleted_by = ? WHERE message_id = ? IF deleted_at = null AND sender_id = ?`
    also guards against expiry between Q3 and Q3d. It costs one Paxos round per target, which
    is not needed for the pilot.
- **`message_refs` only for plaintext reactions.** `status` and `group_receipt` events carry no
  content (ids, ticks, counts), and clients ignore them for unknown or tombstoned messages.
  - Dropping their refs removes an extra write from the ack path, the hottest write path, and
    shrinks the partition to the reactions.
  - If the refs stay, write the refs row **before** the event it describes, never in a
    cross-partition unlogged batch. A crash then leaves a dangling ref (a harmless no-op delete),
    never an unreferenced event.
- **`message_refs` sizing (as proposed) is fine.**
  - DM: ≤ 2 status rows.
  - Group: `group_receipt` rows are bounded by the 10 s coalescing plus the two "all" flips, in
    practice tens and at worst about 2 × members.
  - Plaintext reactions: 2 rows per toggle, bounded by 20 sends/10 s and only in legacy DMs.
  - Rows are about 60 bytes, so even a 256-member group stays well under 100 KiB per partition.
- **`chat:clear` without reading payloads.** Add a non-key column `conversation_id text` to
  `inbox_events`, written on every append. It is one more cell in the same row: no extra write,
  no index, no new table. The Q1s scan then reads `event_id, kind, conversation_id` only and
  falls back to decoding the payload for older null rows. Without it, the scan reads up to 30 days
  of payloads (e2ee rows up to 24 KiB each) to find one conversation.
  - Run the job with `Xandra.stream_pages!` (page 500).
  - Delete per page in one unlogged batch (single partition).
  - Make it Oban-unique on `(user, conversation_id, upto)`.
- **Group fan-out of the deletes (step 4):** group the target events by partition across targets,
  so there is one unlogged batch per user partition, not one per target.
- **Error reply shape.** `InboxChannel` replies `%{reason: …}` today. `msg:delete` needs a reply
  path that carries `failures`. That is fine; it is listed here so the channel change isn't
  forgotten.
- **`deletes` capability (answer to A4, server view).** It is cheap: add `deletes` to
  `@known_capabilities`, plus `deletes_ready`/`missing_deletes` computed like `images_ready` in
  `RisiMe.MLS.Images`. It lets the dialog warn without forcing an update, which is the natural
  pair to R1. It is not needed for safety.

## Answers to the server open points
- **S1 `gc_grace_seconds`.** Yes. Set `gc_grace_seconds = 86400` on `inbox_events` and
  `message_refs` (and on `group_receipts`): a single node has no repair to protect. Know its
  limit, though:
  - It speeds the purge of **expired TTL cells**, which become tombstones on expiry and today
    linger 10 days in closed TWCS windows.
  - It does **not** purge the point-delete tombstones early. A tombstone can only be dropped when
    the SSTable with the data it shadows is compacted with it, and TWCS doesn't do that, so those
    tombstones live until the shadowed data's TTL.
  - The scan cost therefore falls on `since: null` joins (fresh installs) of users who cleared
    big chats. That is fine at pilot volume, far under the 100 000 tombstone failure threshold.
    Watch the `tombstone_warn` lines in the Cassandra log.
  - Revisit both settings with a multi-node cluster.
- **S2 E2EE reaction ciphertext.** Accept the limit. Letting the client list "its" reaction ids
  would let any member name *any* `kind = null` message of the conversation (the server can't
  tell a reaction from a text). That turns `delete for everyone` into deleting other people's
  messages. The ciphertext reveals nothing new and every v1.12 client drops it.
- **S3 `chat:clear` scan.** No index table. Scan the single partition, with the
  `conversation_id` column above. A per-conversation table costs a write on every append for a
  rare action.
- **S4 Lock.** No conversation lock and no LWT for the pilot; see Suggestions. The proposal text
  "the one used for group sends/commits" is wrong for sends; drop the sentence.
- **S5 Delete after block/unfriend.** Agree. Deleting only removes data, and the `delete` event
  must still reach the blocked user's inbox, or their copy stays. Keep `not_friends`/blocks
  unchecked for `msg:delete` in DMs. The e2ee checks still need the DM's MLS group, which unfriend
  doesn't remove.
- **S6 Push.** Always push the normal coalesced `{"type":"inbox"}` to the other members (the
  dispatcher already caps it at one per 10 s per user). A receipt lookup per member costs more
  than the push, and a stale notification is exactly what the wake-up fixes.

## Tests to add (server, on top of §12)
- A crash between the claim and the tombstones, then a retry: R2.
- The rate limit is hit before any `message_index` read: R3.
- A member added after the target gets null metadata: R4.
- A `group_receipt` timer pending at delete time emits nothing, and acks of a deleted DM message
  produce no `status`: R5.
- The tombstone TTL equals the remaining TTL: R6.
- A `delete` event's id is not ackable or reactable, and a `msg:send` `client_msg_id` reused for
  `msg:delete` gets `bad_request`: R7.
- A concurrent duplicate delete with `blob_ids` succeeds as all `gone`: R8.
- `scope: "me"` naming an `mls_commit` `event_id` deletes nothing: R9.
