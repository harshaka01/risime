# Android review: contract proposal v1.11 (encrypted images)

**Reviewer:** android role, 2026-10-06. **Proposal:** `contract/proposals/2026-10-06-images-v1.11.md`
(decision 042, proposed).
**Verdict:** feasible on the current app without new frameworks. Merge after the **required
changes** (R1–R8) below. Most of them correct statements about the client that aren't true of this
app, or close gaps where Android behaviour would otherwise leak metadata or lose images.

How the current app does things, which this review is based on:
- **The Room database is not encrypted.** `risime.db` is plain SQLite. Only `mls_kv` values are
  sealed (`KvSealer`, AES-256-GCM under the Keystore-wrapped `MlsDbKey`). Decrypted text bodies sit
  in `messages.body` in the clear, inside the app sandbox.
- `MlsPayload.decode` knows `text` and `reaction`; anything else is `Ignored` (decision 039), so
  v1.9 apps already drop `image` envelopes silently.
- The outbox (`ChatEngine.flushMessages`) walks `status = 'PENDING'` rows in `local_ts` order. It
  **stops at the first** `Unavailable`/`rate_limited`, and skips only `WAITING_FOR_GROUP`. The chat
  list, notifications (`PushLogic.preview`) and search all read `messages.body`.
- The blob client (`ApiClient.uploadBlob/downloadBlob`) is `purpose=mls` only and holds whole
  bodies in a `ByteArray`. OkHttp uses its default timeouts.
- WorkManager 2.12 is already a dependency. `InboxSyncWorker` sets the expedited +
  `getForegroundInfo` pattern (a foreground service only before API 31).
- `minSdk 26`, `targetSdk 37`. The manifest has `INTERNET` and `POST_NOTIFICATIONS` only, with no
  storage permission. Room is at **v5**.

## Required changes (blocking)

**R1. The image key is not in an "encrypted database" on Android: say how it is stored.**
- §7 (Receiving 3) says "the key lives in the encrypted database (§10.4)". On this app it doesn't:
  `messages` is plain SQLite (see above). If the ciphertext cache and the key both sit unsealed in
  the same sandbox, "no plaintext image on disk" is only cosmetic.
- Required wording, for any client: the per-image `enc.key` and `enc.nonce`, and the inline
  `thumb` bytes, are stored **sealed with the client's database key**.
  - On Android that is `KvSealer` with the existing `MlsDbKey`, with AAD =
    `"media" ‖ client_msg_id` so rows can't be swapped.
  - The ciphertext file is the blob as served. A copied-out `files/` directory plus `risime.db` is
    then useless without the Keystore key.
- Also state the residual honestly in §9: captions, like text bodies, are stored in the clear in
  the app sandbox until the database itself is encrypted (a later decision, not v1.11).

**R2. "No EXIF, GPS, XMP or ICC" needs three more Android rules, or the re-encode leaks metadata.**
`Bitmap.compress` on its own doesn't guarantee a clean file:
- **ICC.** On API 26+, compressing a bitmap whose `ColorSpace` isn't sRGB embeds an ICC profile
  (PNG writes `iCCP`). Display P3 is the default on most current cameras. Required: decode with a
  target colour space of sRGB:
  - `ImageDecoder.setTargetColorSpace(SRGB)`;
  - `BitmapFactory.Options.inPreferredColorSpace` on API 26–27.
- **Ultra HDR gain maps.** On API 34+, a decoded Ultra HDR JPEG carries a `Gainmap`, and
  `compress(JPEG)` writes it back with MPF and an XMP `hdrgm` block. Required: clear it before
  encoding (`bitmap.gainmap = null`, or `setDecodeGainmap(false)` where available).
- **Hardware bitmaps.** `ImageDecoder` may return `HARDWARE` bitmaps. Required:
  `setAllocator(ALLOCATOR_SOFTWARE)` and `ARGB_8888`.
- Spec text proposal for §0 / §7 step 2: "re-encode from a software sRGB 8-bit bitmap with no gain
  map; the output contains no APP1 (EXIF/XMP), APP2 (ICC/MPF) or PNG `iCCP`/`eXIf`/`tEXt` chunks".
  The Android test asserts exactly that on the output bytes (chunk 3).

**R3. Receivers must not trust `w`/`h`, and must validate the envelope before storing it.**
- Any member can send a 16 MiB PNG that declares `w: 100, h: 100` but decodes to 20 000 × 20 000
  pixels, a decompression bomb that crashes every recipient's chat screen.
- Required in §3.1 / §7 Receiving 2:
  - **Decode bounds.** Read the real dimensions first (`inJustDecodeBounds` /
    `ImageDecoder.OnHeaderDecodedListener`). Refuse anything over 4096 px per side or 16 MP ("Couldn't
    open this photo"). Otherwise, always decode with a target size (an `inSampleSize` power of two,
    then a scale) no larger than the display slot.
  - **Envelope field checks.** Before the envelope is persisted, check:
    - `key` decodes to 32 bytes and `nonce` to 12;
    - `blob.size` is between 17 and 16 777 216 + 16;
    - `w`/`h` are 1–2048;
    - `mime` is one of the three;
    - `thumb.data` is at most 4096 bytes.
    Anything else is "malformed → dropped and logged" as §3.1 already says. This only makes the
    rule concrete.

**R4. Cache eviction must never silently destroy the last copy.**
- §7 Receiving 3 says "evicted images are fetched again while the blob lives". After 30 days the
  blob doesn't live, so an LRU that evicts by access time permanently deletes old photos. That
  includes the **sender's own photos**, whose only copy is the local ciphertext.
- Required rule:
  - the LRU (≈500 MiB) may evict only images whose blob is still fetchable, estimated as
    `server_ts + 29 days`;
  - images past that point are **kept**, and are removed only by an explicit user action
    (Settings → Storage → "Remove photos older than 30 days", later), not by the cap;
  - outgoing images are never evicted before their `msg:send` is accepted.
- Receivers learn `expires_at` only from the message time. State in §2.5 that the TTL counts from
  upload, and that a client may treat it as `server_ts + 30 d − 1 d` margin.

**R5. Outbox semantics for image rows: no head-of-line blocking, and the picker grant is temporary.**
- §7 step 5 says text isn't held back. It also needs to state that the image row **does not
  block** the outbox while it uploads or after its upload fails. Today one stuck `PENDING` row
  stops everything behind it. The app will skip image rows without a stored blob ref (like
  `WAITING_FOR_GROUP`).
- **Order:** on the **sender** the bubble keeps its pick position (`local_ts`; no jump on accept),
  with the upload ring and then the normal ticks. **Recipients** order by arrival. The two views
  can differ by the text sent during an upload, which is the WhatsApp behaviour and acceptable. Say
  so, so nobody "fixes" it.
- **The Photo Picker URI grant dies with the process.** Step 4 must say that decode, re-encode,
  encrypt and persist (the ciphertext file plus the sealed envelope) complete **in-process, before
  the row is committed as sending**. The background job only uploads and never touches the source
  URI. If the process dies mid-encode, the half-made row is deleted on the next start, and the
  user picks again (a toast is not possible, so the row simply isn't there).

**R6. The owner can always read their own `media` blob.**
- §2.2 lists who can read: `dm:` participants and `grp:` members (current, or active since the
  upload). It doesn't list the **owner**, unlike §12.6. A sender who has left a group then can't
  fetch their own photo on their other device or after a restore (R8 / v1.10).
- Required: add "the owner (uploader), always, for the blob's TTL" as the first rule in §2.2.

**R7. Gallery save on Android 8–9: use the system file picker, with no storage permission.**
- §7 Receiving 5 says "through MediaStore". Writing to `Pictures/` through MediaStore without a
  permission works from API 29 only.
- Required wording: "MediaStore (`RELATIVE_PATH = Pictures/RisiMe`, `IS_PENDING`) on API 29+; the
  system Save dialog (`ACTION_CREATE_DOCUMENT`, `image/jpeg`) on API 26–28".
- So the app never declares `WRITE_EXTERNAL_STORAGE`, and the manifest stays permission-free for
  storage on every version (answers open point 5).

**R8. Image messages must be restorable from the envelope alone (interaction with v1.10).**
- The v1.10 reinstall work is meant to bring back a user's own sent messages after a reinstall.
  Today's release note says those messages are lost.
- For images to come back through it, the **sender's own row must hold the same envelope as a
  receiver's**: blob ref, key, nonce, mime, `w`/`h`, thumb and caption. It must not hold only a
  local file path.
- Required (in §7 Sending 4): "the sender stores the complete envelope it sends; the local
  ciphertext file is a cache of the blob".
- Consequences to state:
  - a restored image re-downloads (owner read, R6) for the rest of its 30-day TTL;
  - after that, only the thumbnail survives unless v1.10's backup carries image bytes. That is a
    v1.10 decision, so flag it there.
- The sender's **other devices** already get the `message` event (§10.3 sender inbox) and download
  like any recipient. No change is needed beyond R6.

## Suggestions (non-blocking)

- **S1. Sender formats.** Say that senders produce `image/jpeg` (q85) and use `image/png` only for
  sources with alpha whose PNG is ≤ 4 MiB; otherwise they flatten onto white and use JPEG. Android
  won't send WebP (lossy WebP `compress` is API 30+ only). Receivers still render all three.
  Animated GIF/WebP → first frame (ImageDecoder does this by default).
- **S2. A sender-side byte target.** If the q85 JPEG is over 6 MiB (noisy 2048 px images), step to
  q75 and then q65. This keeps the typical upload ≤ 2 MiB, the quota meaningful and the encrypt
  memory small. Normative only as "senders should".
- **S3. `client_blob_id` replay with a different body.** If the same id comes back with a different
  `Content-Length` or `conversation_id`, prefer `409 blob_id_conflict` over returning the old blob.
  The client would detect the mismatch anyway (sha256), but an explicit error makes the bug visible.
  The app never re-encrypts under the same id: the ciphertext is persisted before the first
  attempt.
- **S4. AAD binding `blob_id`.** Against (crypto's call). The sender would have to reserve an id
  before encrypting, an extra round trip that breaks the "encrypt once, then idempotent upload"
  flow. The MLS-protected envelope already binds key ↔ blob ref.
- **S5. Download concurrency.** Clients use at most **3** concurrent blob downloads, well under the
  server's 8, so a fast scroll never earns a `429`. Honour `Retry-After` on downloads too.
- **S6. `images_ready` freshness.** It isn't pushed. The client refetches
  `GET /mls/groups/{id}` on chat open, on `mls_membership` for that conversation, and when the
  disabled attach button is tapped. So "Kamal updated" shows within one tap. No event is needed.
- **S7. `missing_images` with my own devices.** The census includes the caller's own instances.
  Use the text "Your other phone needs to update to receive photos" when the missing `user_id` is
  me.
- **S8. Group icon** (§3.2): Android takes it in a later chunk, after images are live. Members cache
  the **ciphertext** as for images, and decrypt into a small in-memory avatar cache.
- **S9. Learning log / behaviour log.** The local `BehaviourLog` records "image sent" with byte
  size and dimensions only, never content or caption. This is noted to keep it on-device as now.
- **S10. Examples.** Add `image_payload_png.json` (alpha), and a malformed envelope example
  (`image_payload_bad_key.json`, 31-byte key) so both sides test the R3 drop.

## Answers to the android open points

**1. Outbox order and WorkManager.**
- Text isn't held back, and image rows are skipped by the outbox until their blob ref is stored
  (R5).
- **Pipeline.** Pick → (in-process, `Dispatchers.Default`) decode, orient, scale, sRGB, re-encode,
  thumbnail → encrypt to `noBackupFilesDir/media/<client_msg_id>.enc` → one Room transaction. That
  transaction inserts:
  - the `messages` row (`kind = "image"`, `status = PENDING`, `body` = caption);
  - the `media` row (state `encrypted`, sealed key, `client_blob_id`).
- **Upload.** `MediaUploadWorker` is unique work per `client_msg_id` (`ExistingWorkPolicy.KEEP`),
  set up like `InboxSyncWorker`:
  - expedited with `RUN_AS_NON_EXPEDITED_WORK_REQUEST`, and `getForegroundInfo` (a progress
    notification) for API < 31;
  - constraint `NetworkType.CONNECTED`;
  - backoff from WorkManager, and §2.1's schedule for `429`/`5xx` inside one run.
- **After the upload.** The worker stores the blob ref, checking `size` and `sha256` (a mismatch
  means a new `client_blob_id` and another attempt). Then it calls the same sync path as
  `InboxSyncWorker`: connect, then `flushOutbox`. So the `msg:send` goes out even if the app was
  killed, encrypted at send time (`stale_epoch` handling unchanged, same `client_msg_id`).
- **Survives process death:** yes. The source URI isn't needed after the first step.
- **Cancel / delete** of an uploading bubble cancels the work. If a blob was already created, the
  app calls `DELETE /blobs/{id}` (§2.4).

**2. Ciphertext-only cache and decrypt-on-display.**
- **Agree**, with R1 (sealed key) and R4 (eviction).
- **Cost.** AES-GCM over 1–2 MiB on ARMv8 crypto extensions is about 2–5 ms. The cost is the
  decode, which happens anyway.
- **Memory.**
  - A `LruCache<String, Bitmap>` sized at 1/8 of the heap holds bubble-sized bitmaps (decoded with
    `inSampleSize` to about the slot width, e.g. 720 px).
  - Thumbnails are decoded from the sealed DB bytes into a small separate LRU.
  - The full-resolution bitmap exists only in the viewer.
  - Decrypt and decode run on a dispatcher limited to 2 threads, cancelled when the item scrolls
    away.
- **Never written in plaintext:**
  - no image library with a disk cache. **Coil/Glide are not added**: their disk caches would
    write plaintext, and a custom loader is about 150 lines;
  - no `cacheDir` temp files;
  - the viewer shares nothing through `FileProvider` in v1.11.
- **16 MiB worst case (another client's maximum).**
  - Encrypt on send streams from the encoded bytes to the file with `CipherOutputStream`.
  - Decrypt reads the file into one `ByteArray` and calls `doFinal`. Conscrypt's GCM buffers until
    the tag anyway, so streaming wouldn't save memory. Peak is about 2 × 16 MiB plus the sampled
    bitmap, which is fine on the pilot's phones without `largeHeap`.
  - The chunked `alg` for video is the right later fix. Agree with crypto's single-shot now.
- **Downloads** stream to `<blob_id>.part` (no `ByteArray`), resume with `Range` + `If-Range`, and
  verify size + SHA-256 by streaming over the file **before** decrypting. A `404` sets state `gone`
  ("This photo is no longer available", thumbnail stays). A digest or GCM failure gets one
  re-download, then state `corrupt`.

**3. Auto-download policy.**
- **Unmetered network** (Wi-Fi/Ethernet, `NET_CAPABILITY_NOT_METERED`): download in the background
  right after the message is stored, as a `MediaDownloadWorker` with
  `NetworkType.UNMETERED`, at most 3 at a time, newest first.
- **Metered (mobile data):** download only images **visible in an open chat**, never in the
  background.
- **Data Saver on** (`RESTRICT_BACKGROUND_STATUS_ENABLED`) or **roaming:** tap to download only.
- **The 30-day TTL makes "tap only" lossy.** So a pending download on metered is also queued as an
  unmetered background job, and a photo gets fetched the next time the phone is on Wi-Fi.
- **Later setting** (Settings → Storage and data): "Auto-download photos: Wi-Fi only (default) /
  Wi-Fi and mobile data / Never". "Never" still downloads on tap.

**4. Group `images_ready` UX.**
- **Agree with the proposal:** in groups, allow sending with a one-line notice; in DMs, disable
  until ready.
- In a group, blocking every send because of one stale phone would make photos unusable in a
  20-person group.
- **Additions:**
  - **Where the notice appears:** above the composer only when an image is attached (not
    permanently). Group info lists the members who need to update, from `missing_images`.
  - **DM text:** "<name> needs to update the app to receive photos", or S7 for my own phone.
  - **Plaintext DM** (§6): the attach button is disabled with the §6 text, and the e2ee upgrade
    attempt that opening the chat already triggers runs again.
- **Advertising `images`:** the app does so only in the build where **receive and render** are
  complete (chunk 6 below). A build that can show images but not yet send them still advertises it
  correctly.

**5. Gallery save on Android 8–9.**
- Use `ACTION_CREATE_DOCUMENT` on API 26–28 and MediaStore on API 29+ (R7). There is no
  `WRITE_EXTERNAL_STORAGE`, not even with `maxSdkVersion="28"`.
- The saved bytes are the decrypted, already metadata-free re-encode, with
  `DISPLAY_NAME = RisiMe_<yyyyMMdd_HHmmss>.jpg`.
- `DATE_TAKEN` is not set, because the original capture time was stripped on purpose.

**Other items from the review brief.**
- **Photo picker.** `ActivityResultContracts.PickVisualMedia(ImageOnly)`, single image in v1.11.
  - On API 26–29 without the Play-services backport, AndroidX falls back to
    `ACTION_OPEN_DOCUMENT`. Either way no permission is needed, and there is no `READ_MEDIA_*`.
  - Camera capture comes later (`TakePicture` into an app-private `FileProvider` URI, also no
    permission).
- **Orientation and HEIC.**
  - **API 28+:** `ImageDecoder` applies EXIF orientation itself and decodes HEIF (and AVIF from
    API 31) with `setTargetSize`.
  - **API 26–27:** `BitmapFactory` with `inSampleSize`, then a `Matrix` rotate or flip from
    `androidx.exifinterface` (an AndroidX library inside the stack; a one-line note in the chunk's
    decision).
  - **HEIC on API 26–27** can't be decoded. Such phones don't produce HEIC, but a forwarded
    file could be one: "This photo format isn't supported on this phone".
  - **Quality** is specified (JPEG q85, thumbnail q60 → 50 → 40 → 96 px → 64 px). Good.
- **Room v5 → v6** (additive, no table rebuild):
  - `messages.kind` gains the value `"image"`. `body` holds the caption (or `""`), so search, Copy
    and the existing `LastMessage` keep working.
  - **New table `media`**, keyed by `client_msg_id` (the same key as `messages`, deleted with it):
    - **identity:** `conversation_id`, `direction` (`out`/`in`);
    - **state:** `encrypted | uploading | uploaded | failed | none | downloading | cached | gone |
      corrupt`;
    - **blob:** `blob_id`, `blob_size`, `blob_sha256`, `client_blob_id`;
    - **sealed:** `sealed_enc` (key, nonce and alg, sealed per R1), `sealed_thumb`;
    - **image:** `mime`, `w`, `h`;
    - **cache:** `file_path`, `bytes_have` (for `Range`);
    - **bookkeeping:** `expires_at_est`, `last_access`, `attempts`, `next_at`, `fail_reason`.
  - Indices on `(state, next_at)`, `last_access` and `conversation_id`.
  - Tests: `Migration5To6Test` and the `SchemaMigrationsTest` chain. `pendingOutbox` excludes
    `kind = 'image'` rows whose media state isn't `uploaded`.
- **Notifications and chat list:**
  - `preview()` maps `kind = image` to "📷 Photo" or "📷 <caption>";
  - reaction lines read "reacted 👍 to: 📷 Photo";
  - no image in notifications, no `BigPictureStyle`;
  - TalkBack label: "Photo from <name>" plus the caption.

## Tests

**Unit / Robolectric (in `testDebugUnitTest`):**
- `image_crypto_vector.json` round trip with `javax.crypto` AES/GCM: ciphertext‖tag, SHA-256 and
  AAD.
- The envelope:
  - encode/decode of every new example;
  - the R3 drops (bad key length, `w` = 0, unknown `alg` → "Couldn't open");
  - the 22 KiB bound: a 16 KiB caption sets `thumb: null`;
  - the caption limits (`Graphemes`).
- **Re-encode** (`@GraphicsMode(NATIVE)`), from fixture JPEGs that have EXIF orientation 6, GPS, XMP
  and a P3 ICC:
  - the output's dimensions are rotated and its longest side is ≤ 2048;
  - the output bytes contain no APP1/APP2/MPF segments (R2);
  - a PNG with alpha stays PNG; a large PNG is flattened to JPEG;
  - the thumbnail ladder fits in 4096 bytes.
  - (`ImageDecoder` coverage in Robolectric is partial. The API 26–27 `BitmapFactory` path is
    tested there, and the `ImageDecoder` path in the on-device check.)
- **Upload state machine** (fake HTTP):
  - `201`;
  - a lost reply followed by a retry → `200` with the same blob;
  - a sha mismatch → new `client_blob_id`;
  - `413 quota_exceeded` / `too_large` → FAILED with the §7 texts;
  - `429` + `Retry-After`;
  - `507` → retry no more than hourly;
  - cancel → `DELETE`.
- **Outbox:** text typed during an upload is sent first; the image row doesn't block; the image is
  sent after the blob ref is stored; `stale_epoch` re-encrypts the same envelope under the same
  `client_msg_id`.
- **Download:**
  - `Range` resume from `.part` (`206`), and an `If-Range` mismatch → full refetch;
  - the digest is checked before decrypting;
  - a GCM failure → one retry → `corrupt`;
  - `404` → `gone`.
- **LRU (R4):** it never evicts outgoing unsent images or images past `expires_at_est`; it evicts
  the oldest-accessed live ones first.
- **Receive transaction:** the envelope is persisted in the same transaction as the cursor; no
  network call happens inside it (asserted with a fake that fails if called).
- **Compose UI:**
  - bubble states (blurred thumbnail, progress, failed with Retry/Delete, gone);
  - DM attach disabled (not ready / plaintext);
  - the group notice;
  - the viewer with its caption;
  - 320 dp width and 2× font, dark and light.
- **Notifications:** the preview strings.

**Live interop** (`LiveE2eeInteropTest` / `LiveGroupInteropTest`, real MLS core, the
`risime_interop` store):
1. **DM, end to end.** A uploads `media`, then a repeat with the same `client_blob_id` → `200` with
   the same `blob_id`. A sends the `image` envelope over MLS. B decrypts the envelope, downloads,
   verifies the digest, decrypts, and gets the same bytes.
2. **Range.** `GET` with `Range: bytes=100-` → `206`, and `Content-Range` stitched with the first
   100 bytes equals the full blob.
3. **Refusals.** A plaintext DM gets `409 not_e2ee`. Wrong `Content-Type` → `415`. A missing
   `client_blob_id` → `400`. A non-participant gets `404` on upload and download.
4. **Group membership rules.**
   - Members on 3 devices download the same blob.
   - A member removed **after** the upload can still read it; one removed **before** gets `404`.
   - A `pending_add` user gets `404`.
   - The **owner, after leaving**, can read their own (R6).
5. **The sender's other device** gets the `message` event, decrypts it and downloads.
6. **`images_ready`.**
   - `false` with `missing_images` while one instance advertises only `["groups"]`;
   - `true` after it re-PUTs `["groups","images"]`.
7. **Usage and limits.** `GET /blobs/usage` reflects the upload. `too_large` and `quota_exceeded`
   come back from `Content-Length` alone, against a lowered interop config, so the test sends no
   16 MiB bodies.
8. **On-device (manual, Harsha's phones):**
   - a HEIC from a Pixel/Samsung camera;
   - an Ultra HDR photo (API 34+): the received file has no gain map;
   - a P3 photo shows correct colours;
   - save to gallery on Android 14 and on an Android 8/9 device (or emulator);
   - kill the app mid-upload: the photo is sent after the relaunch, or after the next push wake.

## Proposed android chunk order
Each chunk ends with a green `./gradlew assembleDebug testDebugUnitTest` and is committed on its own.
1. **Protocol models and envelope.** `MlsPayload.Decoded.Image` with the R3 validation, the
   encoder with the 22 KiB bound, the new error codes, `images_ready`/`missing_images`, usage, the
   crypto vector test, and parsing every new example.
2. **Room v6.** The `media` table, `kind = "image"`, sealed key/thumb (R1), the `pendingOutbox`
   exclusion, and the migration tests.
3. **Image codec.** Decode, orient, bound and scale, sRGB, no gain map, re-encode, thumbnail
   ladder (R2), plus the byte-level metadata tests. Pure functions, no UI.
4. **Blob client.**
   - `media` upload: file body, progress, `client_blob_id`, retry schedule;
   - streaming ranged download with digest-before-decrypt;
   - `DELETE` and usage;
   - fake-server tests.
5. **Receive path.**
   - pipeline → `messages` + `media` in the same transaction;
   - chat list, notification and reaction previews;
   - the image bubble (blurred thumbnail, aspect ratio, states);
   - the download manager (policy §3, workers, LRU per R4, memory caches).
6. **Viewer and save.** Full-screen pinch-zoom with the caption, and save per R7. **The `images`
   capability is advertised from this build.**
7. **Send path.**
   - picker → in-process encode/encrypt/persist (R5) → `MediaUploadWorker` → outbox;
   - failure texts with Retry/Delete, cancel;
   - DM/group `images_ready` UX and the plaintext-DM state.
8. **Live interop** cases 1–7, the on-device checks, and `docs/status/android.md` READY for v1.11.
9. **Later, separate:** group icon (§3.2), camera capture, the auto-download setting and storage
   screen.
