# Crypto review: contract proposal v1.12 (delete messages and chats)

**Reviewer:** crypto role, 2026-10-06. **Proposal:** `contract/proposals/2026-10-06-delete-v1.12.md`,
decision 047 (proposed). Read against PROTOCOL v1.11 §10, §12, §14 and `crypto/risime-mls{,-ffi}`
(OpenMLS 0.9.0).

**Verdict:** the design is sound. The delete is an ordinary MLS application message, so it is
exactly as authentic as a message, and receivers authorise it again. No new signature is needed.
Merge after **R1–R6**. Most of them are about precision: which identity is compared, where
"admin at epoch `e`" comes from, and the one place where the proposal lets an unauthorised
delete act (the hidden tombstone, R3). R5 is a core configuration change. Calls (v1.13) need it
too.

---

## What the core gives today (facts the review relies on)
- `Client::process` → `Incoming::Application { sender: DeviceId, plaintext, epoch }`. `sender`
  is parsed from the **credential of the sender's leaf in the message's epoch**. OpenMLS keeps
  the leaves of each retained past epoch (`MessageSecretsStore::secrets_and_leaves_for_epoch`).
  So a delete encrypted at `e` and decrypted at `e+2` still names the leaf as it was at `e`. That
  leaf was attested when it was added (`check_leaf`). The FramedContent signature and the AEAD
  are verified before `process` returns.
- `epoch` is the PrivateMessage's epoch. It is authenticated: it is part of the AEAD's
  content-encryption AAD and of the FramedContentTBS.
- The leaf index (`Sender::Member`) is **not** exposed, and neither is `authenticated_data`.
  OpenMLS has both (`ProcessedMessage::aad()`, `MlsGroup::set_aad()`).
- `group_meta(gid)` returns the **current** epoch's meta only. OpenMLS keeps no GroupContext
  extensions for past epochs, only message secrets and leaves. So "admins at a past epoch" can't
  be read back from OpenMLS. Someone has to record it at merge time (R2).
- The sender ratchet uses the OpenMLS default `SenderRatchetConfiguration::new(5, 1000)`:
  - `out_of_order_tolerance` 5;
  - `maximum_forward_distance` 1000 (no `sender_ratchet_configuration` is set in `lib.rs` /
    `group.rs`).

  `padding_size` is 0.
- **C4 answered:** the core keeps **no application plaintext**. OpenMLS stores group state, the
  secret tree and past-epoch secrets/leaves, and `process` hands the plaintext back without
  persisting it. A consumed generation key is deleted, so the core can't re-decrypt a deleted
  message's ciphertext either. What remains on the device is all app-side (R6).

## Required changes (blocking)

**R1. "Deleter = original sender" compares the attested `user_id`, never the leaf or the device.**

§4.2/§4.3 say "the authenticated `user_id` of the control's sender leaf". Make the rule
normative in §4.3 step 3:
- `D` = the `user_id` part of the credential identity `"<user_id>/<device_id>"` that the core
  returned for the delete (`Incoming::Application.sender.user_id`). It must also equal the
  event's `from`, and `from_device` must equal `sender.device_id`, per §10.3. A mismatch drops
  the whole control.
- `S` = the `from` user stored with the target row. For E2EE that value was checked against the
  same kind of credential when the target was decrypted (§10.3). Clients **must** store `from` as
  the verified user id, never as a leaf index. Leaf indices are reused after a removal: index 3
  at `e` and index 3 at `e+5` can be different users.
- **Same user, another device:** `D = S` compares user ids only. A delete from my laptop of a
  message sent from my phone is allowed, and so is a delete after a `rejoin`, an `evict` or a
  re-add of the same device id (P0 fix 7f99b13). This matches the server rule (`sender_id` =
  caller, a user id). Say so explicitly, so the android implementation doesn't compare
  `from_device`.
- An agent (from 0.5) is `D = S` for its own messages and is never an admin (R2).

**R2. "Admin at epoch `e`" is answered by the core, not by the app (C1).**

The core already evaluates `group_meta.admins` at the source epoch of every staged commit
(`check_staged_policy`). The delete check is the same question, so it belongs next to that code.
1. The core records the admin list **per epoch** in its own KV namespace, written in the same
   transaction as each merge, on **every** path that produces an epoch:
   - `create_group_with_meta` → `commit_accepted`;
   - `join_from_welcome`;
   - `process` (peer commit);
   - `process_commits` (catch-up; record **each** intermediate epoch, not only the last one);
   - `commit_accepted` of our own `update_group_meta`/membership commits.

   Key `risime/admins/<gid>/<epoch>`. Prune with the past-epoch secrets: keep the current epoch
   plus `MAX_PAST_EPOCHS` (3). An application message from an older epoch fails to decrypt
   anyway (`WrongEpoch`), so no longer history is ever needed. A group joined at `e` has no record
   below `e`, which is correct: nothing below `e` can be decrypted.
2. `Incoming::Application` gains **`sender_is_admin: Option<bool>`**: `None` for DM groups, and
   `Some(is_admin(sender.user_id))` evaluated on the admins recorded **for the message's epoch**,
   with the same `is_admin` as `policy.rs` (agents are never admins). If the record is missing in
   a `grp:` group, the core returns `Malformed`, not `false`, so a core bug fails loudly in tests.
3. Optionally also `admins_at_epoch(gid, epoch) -> Option<Vec<String>>` for the UI and tests.

The app does **not** keep its own per-epoch list (decision 047's "Consequences" line for android
goes away). Two copies of the same history in two languages would drift. The app only reads
`sender_is_admin` from the same `process` call that decrypts the delete, which is also the same
transaction.

**Is "admin at `e`" the right rule (C1, second half)? Yes, and only that.** The result of a delete
must be a **function of the event stream**, identical on every member's device. "Admin at `e`" is
fixed by the authenticated message itself. "Admin at `e` *and* still admin at my current epoch"
depends on how far each device has caught up when it processes the delete:
- a device that processes it in order (current = `e`) applies it;
- a device that caught up through `process_commits` past a later demotion refuses it.

The same chat then shows different histories. It also buys nothing: the demoted admin really was
an admin when they authored the delete, and the server accepted it under that role (C2 below).

**R3. A hidden tombstone must not suppress a message it isn't authorised to delete.**

§5.3 stores `(conversation_id, message_id, deleted_by)` when a delete names a target the device
doesn't hold and §4.4 shows nothing (null server metadata). It then drops the message if it
arrives later. In that branch nothing was authorised: `S` is unknown, so §4.3 could not run.
- **Attack:** a malicious server, or an honest server racing with a buggy client, delivers a
  delete from a non-admin member `D` that names message `X` from user `Y`. The server marks `X`
  as `gone` (null metadata), and `X` is still to come on this device (parked at a newer epoch,
  live-push race, or replay). The device then silently drops `Y`'s real message.
- **The current text lets any member censor any not-yet-received message on another device.**

Fix (normative in §5.3): the hidden tombstone also stores `deleter_is_admin` (from R2, at the
delete's epoch) and the delete's `server_ts`. When a `message` with that id arrives, the device
decrypts it (it must in any case, to advance the ratchet and learn `S`), then re-runs §4.3 step 3:
- **allowed** (`D = S` and within 48 h + 5 min of the message's `server_ts`, or
  `deleter_is_admin`): store it as a tombstone, unnotified and not unread;
- **otherwise:** store and show it normally, drop the hidden tombstone, and log
  `delete_unauthorised`.

The same applies to a **reaction** that arrives for a hidden-tombstoned target: drop it only if
the hidden tombstone turned out to be authorised. Until then, park it with the target.

**R4. The sending device's own copy: OwnEcho, not a decrypt.**

A device can't decrypt its own PrivateMessage: OpenMLS returns `OwnPrivateMessage`, which the
core reports as `Incoming::OwnEcho`. §5.4 step 3 handles the normal case (skip by
`from_device`). Specify the crash case: the device sent `msg:delete`, the server stored the event,
and the device died before the reply. On restart the outbox row is still there.
- The delete event with `from_device` = self and the outbox's `client_msg_id` completes that
  row: purge the `deleted` and `gone` targets **from the outbox row's own target list**.
- If no outbox row matches (lost local state), apply the event's cleartext targets only where the
  local row's `from` is this user, or the group's **current** `group_meta` names this user as
  admin. The server's word is enough here, because the action is this user's own.

**R5. Raise `maximum_forward_distance`; make generation gaps an explicit, bounded design input.**

v1.12 adds three ways for one recipient device to never see some generations of a sender leaf:
- target events removed from every inbox (§7.3 step 4);
- `scope: "me"` and **`chat:clear`**, which remove events from **my user's** partition, which my
  *other* devices may not have fetched yet (§1.3, §6);
- v1.11 apps that skip the `delete` kind.

v1.13 adds expiring call signals (see the calls review). OpenMLS refuses a message more than
**1000 generations** ahead of the receiver's head for that sender with `TooDistantInTheFuture`.
The core maps it to `DecryptionFailed`, and the message shows as undecryptable. Example: Clear
chat on my phone in a busy group removes 1 500 messages of one sender that my offline tablet
hasn't fetched. The tablet then can't read that sender's next message. Fix:
- In the core, set `SenderRatchetConfiguration::new(out_of_order_tolerance, 20_000)` (see S4 for
  the tolerance) in the create, join and Welcome configs.
- Apply it to **existing** stored groups once, on load (`MlsGroup::set_configuration`), with a
  core test that a group created under the old config accepts a 5 000-generation jump.
- Skipping costs one HKDF-Expand per skipped generation (≈ tens of ms for 20 000 on a phone). Only
  the head moves; skipped keys aren't stored beyond the out-of-order window, so memory doesn't
  grow. A member can already force this work on peers; the cap stays as the DoS bound.
- `chat:clear` should also say in §6 that it can remove events that the caller's other devices
  haven't fetched yet. With R5 that is harmless to MLS: those devices just never see the
  messages, which is what Clear chat means.

**R6. Purge list for the tombstone, app side (answers C4 and A5 from the crypto side).**

The core holds no plaintext (above). In §5.2, the one transaction must drop:
- the body/caption;
- the image envelope, **including the content key `K`**, the `sha256` and the thumbnail;
- the cached blob ciphertext file. Delete it after the transaction commits; a crash leaves an
  orphan file without a key, which a startup sweep removes;
- the parked ciphertext of the target in `mls_pending`, if it is still parked;
- the search index;
- the notification text.

Two Android-specific leaks:
- **SQLite keeps deleted cells in free pages and in the WAL** until they are overwritten. Set
  `PRAGMA secure_delete = ON` on the messages database (cost: zero-filling on delete), and
  checkpoint the WAL after a delete transaction (`wal_checkpoint(TRUNCATE)`, best effort, off the
  UI thread).
- Clear chat and Delete chat must do the same for every row they remove. Neither touches MLS state
  (correct: the group's secrets are not message content).

## Suggestions (non-blocking)

**S1. Bind the targets into MLS `authenticated_data` now (C3). Recommended for v1.12, because it
can't be added cheaply later.**

The receiver-side binding (§4.3 step 1) is already secure. The AAD adds one thing: the **server
can verify the binding**, so a mismatched control is refused with `bad_request` before any
server copy is deleted. With envelope-only binding, a buggy client produces exactly the bad
state the proposal wants to avoid: server copies gone, every device dropping the control, and
the message still visible everywhere.
- **Core:** `encrypt_with_aad(gid, plaintext, aad)` (`MlsGroup::set_aad` before
  `create_message`; OpenMLS resets it after the call). `Incoming::Application` gains
  `authenticated_data: Vec<u8>` (`ProcessedMessage::aad()`).
- **Encoding (binary, canonical):** `0x01 'D'` followed by the targets as 16-byte UUIDs,
  **sorted ascending, distinct**, at most 100 entries (≤ 1 602 bytes).
- **Signing coverage:** AAD sits in cleartext in the PrivateMessage. It is covered by the sender's
  FramedContentTBS signature and by the content AEAD, so a server can neither alter nor strip it
  without failing decryption. It reveals nothing new: the targets are already cleartext request
  fields.
- **Server:** it parses the PrivateMessage header (`group_id`, `epoch`, `content_type`,
  `authenticated_data`), which §10.3 already says it *should* do for group id and epoch. It then
  refuses a request whose AAD set ≠ the request's `targets` set, as `bad_request`.
- **Receiver:** requires AAD set = envelope set = event set; otherwise it drops the control. The
  envelope keeps `targets`, so the JSON stays self-describing and v1.12 needs no second format.
- Every other application message sends an **empty** AAD. Receivers drop a non-delete message
  with non-empty AAD. That keeps AAD from becoming a side channel nobody checks.

If the server role doesn't want an MLS parser in v1.12, ship without S1. The receiver binding is
enough for safety; S1 only adds consistency.

**S2. Placement metadata from the server is presentation, not authentication (§4.4).**

For a target the device never stored, `S` and `server_ts` come from the server. With R1–R3 the
worst a malicious server can do with an honest `D`'s delete is place a content-free "This message
was deleted" line at a chosen position with a chosen sender name, for an id `D` really named.
- Render such server-placed tombstones **without a sender attribution** unless `S = D` (then the
  attribution is authenticated by `D`'s own signature).
- Or accept the limit and document it in §10 Privacy. Either is fine; say which.

**S3. Server-side admin truth vs `group_meta` (C2 corollary).**

The server's role table follows the **op** that a `role` commit completes. Receivers follow the
**`group_meta` actually committed**. The core checks that only admins change `group_meta`, but
nothing checks that the new admin list equals "old list ± the op's user". A buggy or rogue admin
client could commit a different list.
- The server then says "admin" where members say "not admin": the delete is accepted, server
  copies are gone, and devices refuse it. That is consistent but ugly.
- In the opposite case it fails closed.

Cheap guard: when a `meta_changed` commit completes a `role` op (the client knows the op from
`group_op`/`group_event`), the receiving client checks `new.admins = old.admins ± op.user_ids`
and logs `admin_list_mismatch` (telemetry only, no reject: rejecting would fork the group).

**S4. Ordering inside one sender's ratchet.** `out_of_order_tolerance` is 5. If one device's
ciphertexts reach the server out of generation order by more than 5, the earlier ones become
undecryptable for everyone. For example: a delete encrypted in the outbox, then several messages
encrypted and pushed before it, then the delete pushed on a retry with the *same* ciphertext.
- Make "encrypt and push" a single ordered lane per group on the client, and **re-encrypt**
  (never resend the old ciphertext) when anything later from this device has already been sent.
- Raising the tolerance to 32 is a reasonable belt-and-braces measure. It keeps 32 message keys
  per sender per epoch, a small forward-secrecy cost within an epoch. Decide together with the
  calls review, which needs the same lane.

**S5. Length padding.** `padding_size` is 0, so ciphertext length = plaintext length + constant.
For deletes that reveals nothing new (the target count is cleartext), but texts leak their
length. Consider `padding_size(64)` or Padmé-style buckets for all application messages in a
later core release. This is not specific to v1.12.

## Answers to the crypto open points

- **C1:** OpenMLS can't give `group_meta` of a past epoch: only secrets and leaves are retained.
  The **core** records admins per epoch at every merge and returns `sender_is_admin` with the
  decrypted message (R2). "Admin at `e`" is the right rule, without "still admin now" (R2,
  determinism).
- **C2:** no gap for an honest server, **provided** §7.3's critical section really covers the
  `stale_epoch` check, the role read and the event append together, and the role read uses the
  **landed** role (never a pending `role` op). Then:
  - a delete accepted at `e` is ordered before the commit `e → e+1` in every inbox;
  - the server's "admin now" equals `group_meta.admins` at `e`;
  - receivers processing in order evaluate "admin at `e`" = "admin at current".

  Write this dependency into §4.1. A malicious server can at most *delay* a genuine delete
  (still authorised at `e`) or drop it. It can't make a demoted admin's post-demotion delete
  pass, because that delete would be encrypted at `e+1`, where the user isn't an admin. The
  per-epoch record (R2) is needed only for catch-up through `process_commits` and parked
  messages, and that is exactly where it is correct.
- **C3:** yes. The core can set AAD (`MlsGroup::set_aad`) and read it (`ProcessedMessage::aad`).
  Recommended now (S1), with the canonical encoding above. It's not required for receiver
  safety.
- **C4:** confirmed: the core keeps no application plaintext, and consumed generation keys are
  deleted. The leftovers are app-side, see R6 (including `secure_delete` and the WAL).
- **Replay:**
  - Byte replay of the delete's ciphertext to the same device fails: the generation key is
    consumed (OpenMLS `SecretReuseError` → `DecryptionFailed`). The app must treat a failed
    decrypt of a **`delete`** event as a silent skip, never as an "undecryptable message" line.
  - Replay into another conversation fails the core's group-id check.
  - A fresh install can't decrypt pre-install deletes (§5.5).
  - The tombstone itself is idempotent by `message_id`.

  With R3, a replayed or reordered delete can no longer suppress a later message.
- **Cleartext vs encrypted list:** the set equality in §4.3 step 1 is correct and sufficient on
  the receiver. Make it **set** equality on lowercase canonical UUIDs (order and case don't
  matter; duplicates are malformed). A mismatch drops the whole control (as written). S1 moves
  the same check to the server as well.

|---|---|---|

Core tests to add:
- a delete decrypted at `e+2` after a demotion at `e+1` → `sender_is_admin = true`;
- the same author at `e+1` → `false`;
- a catch-up over 3 commits records each intermediate epoch;
- the pruning bound;
- a 5 000-generation jump decrypts after the config migration;
- AAD round-trip, including tampered AAD → `DecryptionFailed` (if S1).
