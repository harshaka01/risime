# Proposal: PROTOCOL v1.12 — delete messages and chats (WhatsApp-like)

**Status:** merged into `contract/v1` as **v1.12** on 2026-10-06, after review by the server,
android and crypto roles (`reviews/2026-10-06-delete-v1.12-{server,android,crypto}.md`). **The
contract text is PROTOCOL §15**; where this proposal differs (notably: no `required` update, the
`deletes` capability, AAD binding, per-recipient target metadata, re-checked hidden tombstones,
`message_refs` for plaintext reactions only), §15 wins. Rationale and conflict resolutions in
decision 047 (accepted). Additive to v1.11.

### How the server review was resolved
- **R1** no `required` update: a normal update, the receive side first; what a ≤ v1.11 app shows is
  §15.11; the dialog small print comes from the `deletes` capability (§15.1).
- **R2** crash recovery re-runs steps 1 and 3–6 with the claim's `message_id`/`server_ts`,
  re-authorising untombstoned targets against the claim's time; the finishing Oban job is enqueued
  right after the claim (§15.8).
- **R3** the rate limit before any per-target read (§15.2 order of checks).
- **R4** per-recipient `from`/`server_ts`, null for users who never had the target (§15.5).
- **R5** every `message_index` reader treats a tombstone as absent (acks, reactions, receipts,
  resend); the job evicts the `GroupReceipts` cache and timer; scheduled ~15 s after the commit
  point; `get_message/1` returns `deleted_at` (§15.8).
- **R6** the index tombstone is written `USING TTL <remaining>` (must) (§15.8).
- **R7** the `delete` event gets its own `message_index` row (`kind = 'delete'`); `sent_dedupe`
  gains `kind`, so a `msg:send` `client_msg_id` reused for `msg:delete` is `bad_request` (§15.2,
  §15.8).
- **R8** blob mismatches are skipped and logged, never `bad_request`; senders of `gone`-because-
  tombstoned targets count (§15.2).
- **R9** `scope: "me"` deletes only `message`/`reaction` rows of the named conversation (§15.2).
- **R10** deletion is logical: removed from every API response at once, physically purged by the
  30-day TTL windows, backups keep the bytes for up to 14 days; in the privacy note (§15.10).
- **Suggestions adopted:** `message_refs` for plaintext reactions only, written before the event;
  the `inbox_events.conversation_id` column for `chat:clear`, streamed pages and an Oban-unique
  job; one unlogged batch per partition; the `failures` reply path; the `deletes` capability;
  `gc_grace_seconds = 86400` on `inbox_events`, `message_refs` and `group_receipts`. **S4 (lock):**
  no lock across the fan-out, but the `stale_epoch` check, the landed-role read and the event id
  planning share the short per-conversation critical section, which crypto's C2 answer depends on
  (§15.4). S2, S3, S5, S6 as answered (S6: always push).

### How the android review was resolved
- **R1** receive-first rollout with the send UI behind a flag; the "stays for good on a device that
  skipped the event" residual is in §15.11; dialog small print "People on older app versions may
  still see it" while not `deletes_ready`.
- **R2** a never-pushed pending message is cancelled locally; a pushed one finishes sending with
  the same `client_msg_id`, then is deleted for everyone (also for "Delete for me") (§15.7).
- **R3** the `cleared_upto` watermark (the global cursor, compared as TimeUUID time) suppresses the
  visible effect of every event at or before it, including parked replays (§15.7, §15.9).
- **R4** Clear/Delete chat never cancel a pending delete-for-everyone (§15.7).
- **R5** control events never create §13.3 markers or undecryptable lines (§15.6).
- **R6** one serial encrypt-and-push lane per conversation; re-encrypt, never resend, after a later
  push (§15.7).
- **R7** silent rebuild (`setOnlyAlertOnce`, `setSilent`) of every posted chat notification,
  summary cancel, in the foreground too; always push (§15.6).
- **R8** the server-clock offset from every join/sync reply; admins from `groups.my_role` in the UI
  and the core's `sender_is_admin` on receive; no per-epoch admin table in the app (§15.4, §15.7).
- **R9** `del:<message_id>` local ids positioned at the target's `server_ts`; `from_device` in the
  e2ee DM event (`event_delete_dm_e2ee.json`) (§15.5).
- **R10** files unlinked after the commit, a start-up orphan sweep, uploads cancelled and blobs
  `DELETE`d; targets without a stored envelope name no blob (§15.6, §15.10).
- **Answers:** A1 "You deleted this message" on the deleter's devices; A2 a separate hidden-
  tombstone store; A3 hide "for everyone" for mixed selections; A4 the `deletes` capability; A5
  the purge list in §15.6; A6 local for v1.12, noted in §15.10. **Suggestions:** S-a, S-b, S-c,
  S-d, S-f adopted (S-a/S-b as implementation notes); S-e not adopted (admin wording unchanged);
  **S-g (one-time catch-up) deferred**.

### How the crypto review was resolved
- **R1** `D` is the attested `user_id`; `D = S` compares user ids only, never devices or leaf
  indices (§15.4).
- **R2** the core records admins per epoch at every merge and returns `sender_is_admin`; the rule
  is "admin at `e`", not "and still admin now" (§15.4).
- **R3** a hidden tombstone is re-checked when the message arrives (decrypt, then judge); no blind
  suppression (§15.6).
- **R4** own-echo crash completion from the outbox row's own target list (§15.6).
- **R5** `maximum_forward_distance` 20 000 in every config, plus a one-time migration of stored
  groups (§15.10).
- **R6** the purge list, `PRAGMA secure_delete = ON` and a WAL checkpoint (§15.6).
- **S1 adopted now:** the targets bound into MLS `authenticated_data` (`0x01 'D'` + sorted 16-byte
  UUIDs), checked by the server (`bad_request`) and by receivers; empty AAD on every other
  application message (§15.3). **S2:** server-placed tombstones carry no sender attribution unless
  `S = D` (§15.5). **S3:** `admin_list_mismatch` telemetry (§15.4). **S4:** the serial lane is
  required (android R6); `out_of_order_tolerance` 32 is decided with v1.13. **S5** (padding)
  deferred to a later core release.

Harsha's requirements, in short: long-press → **Delete for me** (local, any message) or **Delete
for everyone** (own messages within 48 h; group admins on any message of their group); an
encrypted, sender-authenticated control message in E2EE chats and a server-authorised plaintext
kind in legacy chats; every device shows **"This message was deleted"**; the server removes its
stored copies; multi-select; **Clear chat** and **Delete chat**; no learning-log entries.

## 0. Principles
- **Two scopes.** `me` touches only the caller's own devices' view and the caller's **own inbox
  partition**. `everyone` touches every member's devices and every server copy.
- **The server acts only on cleartext metadata it already has.** It never reads an E2EE body. The
  client names the targets (`message_id`s) and any image `blob_id`s in cleartext request fields;
  the server authorises them against what it stored at send time (`message_index.sender_id`,
  `conversation_id`, the TimeUUID time, group roles). It never needs the ciphertext to decide.
- **Receivers authorise again, end to end.** In E2EE chats the targets also travel inside an MLS
  application message, whose sender the MLS core authenticates (leaf signature + attested leaf
  identity, §10.0/§10.3). A receiver applies a target only if the authenticated deleter is the
  target's authenticated original sender (within 48 h) or a group admin in `group_meta.admins` at
  the control message's epoch (§4). The server can drop a delete, but it can't make a device
  delete another member's message.
- **A tombstone, not a gap.** Deleted-for-everyone messages become a local tombstone row: the same
  `message_id`, `client_msg_id`, sender and `server_ts` (position), no body, caption, image
  envelope, key, thumbnail, cached ciphertext, reactions or receipts.
- **Server copies are removed, not rewritten.** The inbox rows of the target message are deleted
  (point deletes: a message event's `event_id` equals its `message_id`), and so are its status,
  receipt and plaintext-reaction rows and its image blob. Only a content-free tombstone stays in
  `message_index` (for idempotency, acks and `unknown_target`) until the original row's TTL.
- **Idempotent everywhere.** Every target that is already deleted, expired or unknown is reported
  as `gone` and counts as success. A retry with the same `client_msg_id` returns the first reply.
- **No new capability.** Deletion degrades safely on old apps (they keep the message); rollout is a
  `required` update as for v1.7/v1.9/v1.11.

## 1. The push `msg:delete` (client → server)
One new push for both scopes and every conversation type. `conversation_id` is used for DMs too
(`dm:…`), unlike `msg:send`.

### 1.1 Delete for everyone, E2EE (DM or group) — `msg_delete_everyone_group.json`
```json
{"client_msg_id": "5d1e2f3a-4b5c-4d6e-8f70-81920a1b2c3d",
 "conversation_id": "grp:5a6b7c8d-9e0f-4a1b-8c2d-3e4f5a6b7c8d",
 "scope": "everyone",
 "targets": ["c1a2b3e1-a0b1-11f0-8000-0242ac120002", "c1a2b3f0-a0b1-11f0-8000-0242ac120002"],
 "blob_ids": ["8e7d6c5b-4a39-4281-9706-f5e4d3c2b1a0"],
 "ciphertext": "cGxhY2Vob2xkZXItZGVsZXRlLWNvbnRyb2w=",
 "generation": 1, "epoch": 4,
 "client_ts": "2026-10-06T09:00:00.000Z"}
```
- `targets`: 1–**100** distinct TimeUUID `message_id`s of this conversation. Duplicates are
  removed by the server; 0 or more than 100 is `bad_request`.
- `blob_ids`: 0–100 `media` blob ids referenced by image targets (§14.4 `blob.blob_id`); may be
  omitted (= `[]`).
- `ciphertext`, `generation`, `epoch`: the MLS PrivateMessage carrying the `delete` envelope
  (§3), with the §10.3 rules (`stale_epoch`, 24 KiB cap). Required in an e2ee conversation
  (otherwise `e2ee_required`), forbidden in a plaintext one (`bad_request`).

### 1.2 Delete for everyone, plaintext legacy DM — `msg_delete_everyone_dm.json`
```json
{"client_msg_id": "6e2f3a4b-5c6d-4e7f-8091-a2b3c4d5e6f7",
 "conversation_id": "dm:0b9d7e8a-1c2f-4a3b-8d4e-5f6a7b8c9d0e_7e3f1a2b-9c8d-4e5f-a6b7-c8d9e0f1a2b3",
 "scope": "everyone",
 "targets": ["c1a2b3c4-a0b1-11f0-8000-0242ac120002"],
 "client_ts": "2026-10-06T09:00:00.000Z"}
```
No `ciphertext`; the server's authorisation is the only check that matters (plaintext chats trust
the server anyway), and receivers still apply §4.3 with the event's metadata. Plaintext DMs carry
no images (§14.0), so `blob_ids` is empty or absent.

### 1.3 Delete for me — `msg_delete_me.json`
```json
{"client_msg_id": "7f3a4b5c-6d7e-4f80-91a2-b3c4d5e6f708",
 "conversation_id": "grp:5a6b7c8d-9e0f-4a1b-8c2d-3e4f5a6b7c8d",
 "scope": "me",
 "targets": ["c1a2b3e1-a0b1-11f0-8000-0242ac120002"]}
```
- Any message of the conversation, any age, any sender. No `ciphertext`, no `blob_ids` (a blob is
  never deleted for "me": other members still need it), no event, no push.
- The server deletes, **from the caller's own inbox partition only**, the event
  `(user_id = me, event_id = target)` if its payload's `conversation_id` matches, plus the caller's
  own refs rows for it (status, `group_receipt` and plaintext reaction events, §7.2). Other users'
  inboxes and the caller's other devices are untouched (§10, open point A6).
- The caller may still be a removed group member (a former member can tidy their own copies):
  `not_member` is **not** checked for `scope: "me"`.

### 1.4 Reply ok — `msg_delete_reply.json`
```json
{"message_id": "d2b3c4d5-a0b2-11f0-8000-0242ac120002",
 "conversation_id": "grp:5a6b7c8d-9e0f-4a1b-8c2d-3e4f5a6b7c8d",
 "server_ts": "2026-10-06T09:00:00.512Z",
 "deleted": ["c1a2b3e1-a0b1-11f0-8000-0242ac120002"],
 "gone": ["c1a2b3f0-a0b1-11f0-8000-0242ac120002"]}
```
- `deleted`: targets removed by this request. `gone`: targets already deleted, expired, unknown,
  or not a normal message of this conversation (a reaction, a delete, another conversation's
  message). **`gone` is success** (decision 047 §3): it makes retries and races idempotent and
  never reveals whether a `message_id` exists elsewhere.
- `message_id`/`server_ts` name the stored `delete` event (§2) for `scope: "everyone"`. For
  `scope: "me"` they are `null`.
- **When every target is `gone`** for `scope: "everyone"`, no event is stored and `message_id` is
  `null`: nothing is left to announce (the earlier delete already was).

### 1.5 Errors (reply error)
All-or-nothing: if any target fails authorisation, nothing is deleted and nothing is stored.
`{"reason": "<reason of the first failure>", "failures": [{"target": "…", "reason": "…"}, …]}`
(`error_delete_too_old.json`):
```json
{"reason": "too_old",
 "failures": [{"target": "c1a2b3e1-a0b1-11f0-8000-0242ac120002", "reason": "too_old"},
              {"target": "c1a2b3f0-a0b1-11f0-8000-0242ac120002", "reason": "not_admin"}]}
```
Clients that read only `reason` still work; v1.12 clients drop the failing targets from the
selection and offer "Delete for me" for them.

| reason | when |
|---|---|
| **`not_sender`** (new) | DM, `everyone`: the target was sent by the other user (`error_not_sender.json`) |
| **`too_old`** (new) | `everyone`: own target whose TimeUUID time is more than **48 h** before the server's clock now, and the caller isn't an admin of this group |
| `not_admin` (reused) | group, `everyone`: another member's message and the caller isn't an active admin |
| `not_member` | group, `everyone`: the caller isn't an active member (also for unknown groups, §12.9) |
| `e2ee_required` | `everyone` without `ciphertext` in an e2ee conversation |
| `stale_epoch`, `too_long` | as §10.3 for the ciphertext |
| `rate_limited` | shares the 20-per-10-s send limit; one request counts once |
| `bad_request` | malformed; 0 or > 100 targets; unknown `scope`; `ciphertext` in a plaintext conversation; a `blob_id` that isn't a `media` blob of this conversation owned by the sender of one of the `deleted` targets |

A DM participant can always delete their own messages for everyone: `not_friends` and blocks are
**not** checked (deleting only removes data; open point S5).

**Order of checks** (`everyone`): idempotent resend (`sent_dedupe`) → `not_member` (groups) /
participant (DMs; a non-participant gets `not_member` too, so nothing is revealed) → e2ee checks →
`bad_request` shape → per-target authorisation (§4.1) → blob checks → rate limit → delete + store.

## 2. The event kind `delete` (server → client, stored, cursor-ordered)
Written to **every member user's inbox, the deleter included**, with the same `event_id`
(= its `message_id`), in the order of §13.1 (the deleter's copy first). DM: both users. Group:
current active members (as a group message, §12.7). It wakes the other users by the normal
data-only push (§8.2), so a shown notification can be withdrawn; it never creates a visible
notification. The deleter's own copy is never pushed.

E2EE (group) — `event_delete_group.json`:
```json
{"event_id": "d2b3c4d5-a0b2-11f0-8000-0242ac120002", "kind": "delete",
 "data": {"message_id": "d2b3c4d5-a0b2-11f0-8000-0242ac120002",
          "client_msg_id": "5d1e2f3a-4b5c-4d6e-8f70-81920a1b2c3d",
          "conversation_id": "grp:5a6b7c8d-9e0f-4a1b-8c2d-3e4f5a6b7c8d",
          "from": "7e3f1a2b-9c8d-4e5f-a6b7-c8d9e0f1a2b3",
          "from_device": "c0a80101-0000-4000-8000-000000000001",
          "targets": [
            {"message_id": "c1a2b3e1-a0b1-11f0-8000-0242ac120002",
             "from": "0b9d7e8a-1c2f-4a3b-8d4e-5f6a7b8c9d0e",
             "server_ts": "2026-10-06T08:15:30.456Z"},
            {"message_id": "c1a2b3f0-a0b1-11f0-8000-0242ac120002",
             "from": null, "server_ts": null}],
          "ciphertext": "cGxhY2Vob2xkZXItZGVsZXRlLWNvbnRyb2w=",
          "generation": 1, "epoch": 4,
          "server_ts": "2026-10-06T09:00:00.512Z"}}
```
Plaintext DM — `event_delete_dm.json`: the same with `"to": "<other user>"`, no `from_device`,
`ciphertext`, `generation` or `epoch`. An e2ee DM has `to` and the e2ee fields.

- `targets` lists **every requested target** in request order, with the server's metadata for the
  `deleted` ones (`from` = stored sender, `server_ts` = the target's TimeUUID time) and nulls for
  the `gone` ones. Receivers use this metadata **only** for targets they never stored (§4.4).
- No `status`, receipts or acks for `delete` events: `msg:ack` naming one is silently ignored, and
  a `delete` is never a reaction or delete target (`gone` / `unknown_target`).
- Apps before v1.12 ignore the unknown kind (§0). Skipping one MLS application message is safe for
  their MLS state (the secret tree tolerates a skipped generation).

## 3. The `delete` envelope (MLS application message) — `delete_payload.json`
```json
{"v": 1, "type": "delete",
 "targets": ["c1a2b3e1-a0b1-11f0-8000-0242ac120002", "c1a2b3f0-a0b1-11f0-8000-0242ac120002"]}
```
- `targets`: 1–100 distinct lowercase TimeUUIDs, **the same set** as the request's `targets`.
  Nothing else: no bodies, no reasons, no blob ids (receivers find blobs in their own stored
  envelopes).
- Sent only inside `msg:delete` (§1.1), never with `msg:send`. A `delete` envelope that arrives as
  a `message` event is dropped and logged (a v1.12 server never produces one).
- Validated strictly, like `image` (§14.4): `v` = 1, `targets` a non-empty array of at most 100
  distinct TimeUUID strings; otherwise the whole control is dropped as malformed and logged. Unknown
  fields are ignored.

## 4. Authorisation

### 4.1 Server (per target, `scope: "everyone"`)
Read `message_index` by `message_id` (§7.1 Q3).
1. Absent, already tombstoned (`deleted_at` set), `kind` = `reaction` or `delete`, or another
   `conversation_id` → **`gone`** (no further check).
2. `sender_id` = caller → allowed if `now − time(message_id) ≤ 48 h`; else allowed only if the
   caller is an active **admin** of this group; else **`too_old`**.
3. `sender_id` ≠ caller → DM: **`not_sender`**; group: allowed if the caller is an active admin
   now (`group_members.role = 'admin'`, `state = 'active'`), else **`not_admin`**. Admins have no
   age limit inside the 30-day retention.

`time(message_id)` is the TimeUUID timestamp, which is the message's `server_ts` (both are taken
from one clock read at send). 48 h = 172 800 000 ms, compared on the server clock at the moment of
the check. The server's role table and `group_meta.admins` change together when a `role` commit
lands (§12.3), so both sides agree except for a commit in flight (open point C2).

**Blobs:** each `blob_id` must be a `media` blob with this `conversation_id` whose `owner` is the
`sender_id` of a `deleted` target (else `bad_request`); an already deleted or expired blob is
silently skipped. The server can't link a blob to a message (it never reads envelopes), so this
binds it to the right person and chat; an admin could name another image of the same sender,
which they could delete as admin anyway.

### 4.2 Sender authentication ("signed") in E2EE chats
An MLS PrivateMessage carries a `FramedContent` signed with the sender leaf's Ed25519 key and
encrypted under the epoch's keys (RFC 9420 §6.1–§6.3). The MLS core verifies the signature and the
membership tag/AEAD on decrypt; the client checks the leaf credential identity
`"<user_id>/<device_id>"` = the event's `from`/`from_device` and the attestation (§10.0, §10.3).
So **the deleter `D` = the authenticated `user_id` of the control's sender leaf**, and the epoch
`e` = the control's epoch from the MLS framing (equal to the event's `epoch`). Nothing new is
signed; the delete is exactly as authentic as a message.

### 4.3 Receiver (per target, E2EE and plaintext)
After decrypting (E2EE) or reading (plaintext) the `delete` event:
1. **Binding:** E2EE: the envelope's `targets` set must equal the event's `targets[].message_id`
   set, else drop the whole control (malformed, logged). This stops a client from having the
   server authorise one set while members act on another.
2. **Original sender `S`:** the local row's `from` if the target is stored locally (for E2EE this
   came from the original message's authenticated leaf); otherwise the event's `targets[].from`
   (server metadata, §4.4). A local `conversation_id` different from the event's → ignore the
   target.
3. **Allowed** if `D = S` and `delete.server_ts − target.server_ts ≤ 48 h + 5 min` (the grace
   absorbs the gap between the server's check and its `server_ts`), **or** the conversation is a
   group and `D ∈ group_meta.admins` **at epoch `e`**. Otherwise ignore the target and log.
4. Apply the tombstone (§5.2). By-admin when `D ≠ S`.

**Admin at epoch `e`:** the receiver processes a group's events in `event_id` order (§10.3), but a
control encrypted at `e` may land after the commit to `e+1` (the server's `stale_epoch` check and
the commit CAS aren't one critical section). Clients therefore keep `admins` per epoch for at least
the past epochs whose secrets they keep (≥ 3, §10.0), from the core's staged-commit view of
`group_meta` (open point C1). Plaintext DMs have no admins; plaintext receivers apply steps 2–4
with the event's metadata only (they trust the server, as for any plaintext).

### 4.4 Targets the device never stored
The server removed the message's inbox rows, so a device that was offline (cursor before the
message) sees only the `delete` event.
- If `targets[].from` and `server_ts` are non-null and §4.3 allows it (with `S` from the event),
  insert a tombstone row at that position, so the chat shows "This message was deleted" where the
  message would have been, never notified or unread.
- **Except inside the history gap:** if `history_before` is non-null and the target's `server_ts <
  history_before` and the conversation is e2ee, insert nothing (§13.3's marker already covers it).
- Null metadata (`gone` on the server) → a **hidden** tombstone only (§5.3).

## 5. Client behaviour (android)

### 5.1 Long-press and multi-select
- Long-press a message → the existing sheet (§11.3) gains **Delete**. Long-press then tap more
  bubbles = multi-select; the action bar shows a bin icon.
- Delete opens a dialog: **"Delete for me"**, **"Delete for everyone"** (only when every selected
  message is allowed by §4.1 as the client sees it), Cancel. With some ineligible messages selected
  the dialog offers only "Delete for me" (as WhatsApp).
- Client eligibility uses `server_ts` and the server clock offset (`server_time` from the join
  reply), hiding "for everyone" 1 minute before 48 h; admins (from `GET /groups/{id}` and
  `group_meta`) see it on any message with a `message_id` in their group.
- Messages without a `message_id` (pending in the outbox): both options just cancel the send
  locally (and `DELETE` an uploaded but unsent blob, §14.2). A message whose `msg:send` is in
  flight waits for its reply, then proceeds.
- More than 100 selected: the client splits into requests of ≤ 100 (each its own
  `client_msg_id` and, for E2EE, its own envelope).
- System rows (history marker, undecryptable line, `group_event` lines, tombstones) offer only
  "Delete for me" (local only, no request).

### 5.2 Tombstone row
- Keep: `message_id`, `client_msg_id`, `conversation_id`, `from`, `server_ts`/local order,
  direction. Add: `deleted_at`, `deleted_by` (user id), `deleted_by_admin` (bool).
- Drop **in one transaction with the cursor**: body, caption, image envelope, sealed key and
  thumbnail, cached ciphertext file (§14.7 Receiving 6), reaction rows on it, receipt rows,
  pending downloads/uploads, search-index entries.
- Text: **"This message was deleted"**; by an admin: **"This message was deleted by an admin"**.
  (On the deleter's own devices the client may say "You deleted this message"; open point A1.)
- Not unread (an unread target decrements the unread count), never notified, no ticks, no
  reactions, no long-press except "Delete for me". The chat list preview shows the tombstone text
  if it is the latest row.
- Tombstones never revert. A target is processed once; repeats are no-ops (idempotent by
  `message_id`).

### 5.3 Delete before message (hidden tombstone)
A `delete` for a target the device doesn't hold (and §4.4 shows nothing) stores a **hidden
tombstone** `(conversation_id, message_id, deleted_by)`, kept for 30 days. A `message` (or
reaction) event that later arrives with that `message_id` is dropped before it is stored or
notified (it still advances the cursor; no ack is sent, and the server would ignore one). This
covers live-push races, parked MLS messages replayed after the delete, and replays across a
partial server cleanup.

### 5.4 Sending a delete for everyone
1. Mark the rows **deleting** at once (rendered as the tombstone) but keep their content until the
   reply.
2. The outbox sends `msg:delete` (encrypting the envelope at send time; `stale_epoch` → re-encrypt
   with the same `client_msg_id`, as §10.4).
3. Reply ok → purge as §5.2 for `deleted` and `gone`. The sending device skips its own copy of the
   `delete` event by `from_device` (E2EE) or `client_msg_id` (plaintext).
4. Reply error → restore the rows and show "Couldn't delete for everyone" (`too_old`: "You can only
   delete messages for everyone within 48 hours"); offer "Delete for me". `bad_request` and
   unknown reasons are permanent (§2.2). Network errors retry with the same `client_msg_id`.
- Offline: the request waits in the outbox; the 48 h limit is judged when the server receives it.

### 5.5 Receiving a delete
- Process in the group's `event_id` order like any message (parked at a newer epoch, replayed
  after its commit, §10.3). Apply §4.3, then §5.2 per allowed target, in **one transaction with
  the cursor**.
- **Notifications:** cancel any notification that shows only deleted messages; rebuild a grouped
  (MessagingStyle) notification without them; if nothing is left in it, cancel it. A reaction
  notification about a deleted message is cancelled too.
- **Reactions** that arrive for a tombstoned (or hidden-tombstoned) target are dropped and never
  notified.
- **Quotes/replies:** none exist yet. A later "reply" feature must render a quote of a deleted
  message as "This message was deleted" and must never keep a copy of its body.
- **Pre-install** `delete` events (§13.3 rules 1/2, undecryptable) are skipped silently: they add
  no history marker on their own (they're not messages) and create no tombstone. Plaintext
  `delete` events replay normally on a fresh install and create tombstones from their metadata.
- A delete whose target is a reaction, a system row or another delete is ignored.

### 5.6 Delete for me (local)
Remove the rows (or tombstones) as §5.2 drops content, with no tombstone; the bubble disappears.
Then send `msg:delete` `scope: "me"` (outbox, retried; failures are logged, never shown). Keep a
hidden tombstone (§5.3) so a replay can't bring the message back on this device.

### 5.7 Clear chat and Delete chat
- **Clear chat** (chat menu and chat-list long-press): removes every row of the conversation
  (messages, tombstones, system lines, reactions, receipts, image keys and cached ciphertext) and
  keeps the conversation in the list with an empty preview.
- **Delete chat** (chat-list long-press): the same, and hides the conversation from the list. It
  **reappears** when a new `message` (or for a group, a notifying `group_event`, §12.7) arrives.
  For a group the user stays a member; leaving is separate (§12.3).
- Neither touches MLS state, `mls_pending`, the cursor, group membership, mute settings, or other
  members' copies; both cancel the conversation's notifications and its unsent outbox rows.
- **Both also remove the server copies in my own inbox** (recommended and specified): the client
  sends **`chat:clear`** (§6) with `upto` = the newest `event_id` it has processed. So a
  reinstall doesn't bring the chat back; my other devices keep their copies (open point A6).

## 6. The push `chat:clear` (client → server) — `chat_clear.json`
```json
{"conversation_id": "dm:0b9d7e8a-1c2f-4a3b-8d4e-5f6a7b8c9d0e_7e3f1a2b-9c8d-4e5f-a6b7-c8d9e0f1a2b3",
 "upto": "d2b3c4d5-a0b2-11f0-8000-0242ac120002"}
```
→ reply ok `{}`; errors: `bad_request` (malformed, `upto` not a TimeUUID), `rate_limited`
(at most 10 per user per minute).
- Removes from **the caller's own inbox partition** every event with `event_id ≤ upto` whose kind
  is `message`, `reaction`, `status`, `group_receipt` or `delete` and whose payload
  `conversation_id` matches, plus the caller's refs rows (§7.2) for those messages.
- **Never** removes `mls_commit`, `mls_welcome`, `mls_membership`, `group_event`, `group_op` or
  `friend`-type events: MLS state and group lifecycle must still replay (open point S3).
- Runs as a background job (Oban, retried, idempotent); the reply only means "accepted". Membership
  isn't checked (a former member may clear their copies). There is no "clear for everyone".
- `msg:delete` `scope: "me"` and `chat:clear` affect only the caller's user; the server never tells
  the caller's other devices.

## 7. Server storage
Postgres is unchanged except the blob delete (§14.8 `deleted_at`). Cassandra, queries first
(CLAUDE.md), no `ALLOW FILTERING`, no secondary index:

### 7.1 Queries
| Q | Query | Table |
|---|---|---|
| Q3 | `SELECT … FROM message_index WHERE message_id = ?` (authorise; recipients) | `message_index` (existing) |
| Q3d | `UPDATE message_index SET deleted_at = ?, deleted_by = ? WHERE message_id = ?` | `message_index` (+2 columns) |
| Q1d | `DELETE FROM inbox_events WHERE user_id = ? AND event_id = ?` — the target's own event (`event_id = message_id`) in each recipient partition | `inbox_events` (existing) |
| Q7 | `SELECT user_id, event_id, kind, ref_id FROM message_refs WHERE message_id = ?` — the rows that hang off a message (status, receipt, plaintext reaction events) | **`message_refs`** (new) |
| Q7u | `SELECT … FROM message_refs WHERE message_id = ? AND user_id = ?` (scope `me`) | `message_refs` |
| Q8 | `INSERT INTO message_refs …` whenever a status, `group_receipt` or plaintext `reaction` event is appended | `message_refs` |
| Q5d | `DELETE FROM group_receipts WHERE message_id = ?` (whole partition) | `group_receipts` (existing) |
| Q1s | `SELECT event_id, kind, payload FROM inbox_events WHERE user_id = ? AND event_id <= ?` paged (only for `chat:clear`, one partition, filtered in the app) | `inbox_events` |

**Where the inbox partitions come from:** the target's `message_index` row already holds them:
`sender_id` plus `recipient_id` (DM) or `recipients` (group, members at send time). Its own event
is at `event_id = message_id` in each of those partitions (§13.1), so no lookup table is needed for
the message itself; only the rows with other `event_id`s need `message_refs`.

### 7.2 New table and columns (`004_delete.cql`)
```sql
-- Q7/Q7u/Q8: the inbox rows that reference a message (v1.12 §7). One partition per message.
CREATE TABLE IF NOT EXISTS message_refs (
  message_id timeuuid,   -- the referenced (target) message
  user_id uuid,          -- the inbox partition holding the row
  event_id timeuuid,     -- the referencing event's id in that partition
  kind text,             -- 'status' | 'group_receipt' | 'reaction'
  ref_id timeuuid,       -- the reaction's own message_id (its message_index row); null otherwise
  PRIMARY KEY ((message_id), user_id, event_id)
) WITH default_time_to_live = 2592000
  AND compaction = {'class': 'TimeWindowCompactionStrategy',
                    'compaction_window_unit': 'DAYS', 'compaction_window_size': 1};

-- Q3d: a content-free tombstone (keeps sender/recipients for idempotent retries and acks).
ALTER TABLE message_index ADD deleted_at timestamp;
ALTER TABLE message_index ADD deleted_by uuid;
```
- A refs row is written in the same request as the event it describes, with the same TTL. Rows of
  events written before v1.12 don't exist; those `status`/`group_receipt` events (no content, only
  ids and ticks) stay until their TTL, and clients ignore them for tombstones. No backfill.
- E2EE reactions are opaque to the server (`kind` null in `message_index`), so they get no refs
  row. Their ciphertext stays until the 30-day TTL; it reveals nothing new, and every receiver
  drops a reaction to a tombstone (§5.5). Known limit, open point S2.
- `UPDATE … SET deleted_at` writes new cells with the default TTL; the row's older cells keep
  their own, so the tombstone outlives the original by at most the time between send and delete
  (≤ 30 days). Fine for idempotency; the server may write it `USING TTL <remaining>` instead.

### 7.3 Steps of `scope: "everyone"` (behind `RisiMe.Messaging.Store`)
Inside the conversation's critical section (the one used for group sends/commits):
1. Q3 for each target; authorise (§4.1); blob checks.
2. Claim `sent_dedupe` for `(caller, client_msg_id)` with the planned `message_id` and
   `server_ts` of the `delete` event.
3. Q3d tombstone each `deleted` target with `deleted_by` = caller and `deleted_at` = that
   `server_ts` (the commit point).
4. Q1d delete each target's event in every partition (sender + recipients), one unlogged batch per
   partition.
5. Append the `delete` event to every member inbox (§2) under the planned `event_id`, publish,
   push; reply.
6. **Then, as an idempotent Oban job:** Q7 → delete each referenced inbox row (Q1d) and tombstone
   each plaintext reaction's `message_index` row (Q3d) → Q5d → delete the `message_refs`
   partition → `DELETE` each blob (§14.2 semantics: file removed now, row kept until expiry, so a
   replayed `client_blob_id` gets `404`).
- **Crash recovery:** a retry with the same `client_msg_id` that finds the claim treats the targets
  tombstoned with `deleted_by` = caller and `deleted_at` = the claim's `server_ts` as `deleted` by
  this request, re-runs steps 3–6 (all idempotent; the event is rewritten under the same
  `event_id`, as the §13.1 resend) and returns the same reply. So members always learn of a delete
  whose server copies are gone.
- An idempotent resend of the **original** message's `client_msg_id` (within 24 h) sees the
  tombstoned index row and returns its original reply **without re-delivering** (§13.1).
- Acks naming a tombstoned message are ignored; plaintext reactions to it get `unknown_target`;
  `GET /groups/{id}/messages/{id}/receipts` returns `404`.
- Members removed from a group after the message was sent lose their server copies (step 4) but
  get no `delete` event (no `grp:` traffic after removal, §12.3): their device keeps what it had,
  as with MLS removal (§14.9).

### 7.4 Tombstones in a TWCS table
Point deletes in `inbox_events` (TWCS, 30-day TTL) create row tombstones that live
`gc_grace_seconds` (default 10 days). A join with `since: null` scans over them; `chat:clear` can
create many in one partition. Pilot volumes are far below `tombstone_warn_threshold` (1000
tombstones scanned per read). Proposed: `gc_grace_seconds = 86400` on `inbox_events` and
`message_refs` (single node, no repair to protect; revisit with a multi-node cluster). Open point S1.

## 8. Groups (summary)
- The same rules; admins may delete any message of their group for everyone, any age within
  retention. Members see **"This message was deleted by an admin"**.
- The admin check is "admin now" on the server and "admin at epoch `e`" on receivers (§4.3).
- An admin's delete of another member's image deletes that member's blob (the server checks the
  blob's owner against the target's sender).
- Former members: §7.3 last bullet.

## 9. Rollout and old apps
- v1.11 apps ignore `delete` events and keep the message (and can still open its image until the
  blob is deleted, then "This photo is no longer available"). The server still removes its copies.
- Rollout: deploy the server, then a `required` app update, then announce. No capability or
  readiness flag (decision 047 §5; open point A4).

## 10. Privacy and the learning log
- The server learns which messages were deleted, by whom and when (it already knew sender and
  time). It keeps a content-free tombstone (ids, sender, recipients, `deleted_at`, `deleted_by`)
  until the original's 30-day TTL. Logs carry counts and ids only.
- **Learning log: none.** No model call is involved. The on-device behaviour log records nothing
  about deletes in v1.12.
- Deletion is best-effort, as everywhere: a recipient may have read, screenshotted or (later)
  forwarded the message; old apps and removed members keep their copies. The dialog says
  "Recipients may have already seen it" in small print (informative).

## Open points for review
**Server**
- **S1** `gc_grace_seconds = 86400` on `inbox_events`/`message_refs` (§7.4), or keep the default
  and accept the tombstone scan cost for the pilot?
- **S2** E2EE reaction ciphertext to a deleted message stays until TTL (§7.2). Acceptable, or
  should the client list the reaction `message_id`s it knows (the server could check they're
  `kind` null rows in the same conversation, but can't prove they are reactions to the target)?
- **S3** `chat:clear` scans one inbox partition with an app-side filter (Q1s) instead of a new
  `(user_id, conversation_id)` index table. OK at pilot size (≤ 30 days per user), or add the table
  now, with one more write per inbox append?
- **S4** Is the conversation critical section (§7.3) the right lock for DMs too, or is the
  per-target `message_index` tombstone (a lightweight transaction `IF deleted_at = null`) enough?
- **S5** Deleting own messages after a block/unfriend: allowed (no `not_friends` check). Agree?
- **S6** Push for `delete` events (§2): always a data-only push to the other members, or only when
  a target was undelivered/unread (needs a receipt lookup)?

**Android**
- **A1** Wording on the deleter's own devices: "You deleted this message" (WhatsApp) or the same
  "This message was deleted" everywhere (Harsha's wording)?
- **A2** Hidden tombstones (§5.3): a separate table, or tombstone rows with a `hidden` flag?
- **A3** Multi-select UX with mixed eligibility: hide "for everyone" (proposed) or offer it for the
  eligible subset and "for me" for the rest?
- **A4** No capability: is a `required` update before announcing enough, or do we want a
  `deletes_ready` hint like `images_ready` to warn "<name> needs to update to see deletions"?
- **A5** Search index and any other derived stores must be purged in the same transaction: list
  them in the review.
- **A6** "Delete for me" and Clear chat don't sync to my other devices (Harsha: local). WhatsApp
  multi-device syncs them. Later proposal (an own-inbox-only `delete` event with `scope: "me"`)?

**Crypto**
- **C1** "Admin at epoch `e`": can the core expose `group_meta` of a retained past epoch, or must
  the client record `admins` per epoch when it merges each commit? Is "admin at `e`" the right
  rule, versus "admin at `e` and still admin at the receiver's current epoch"?
- **C2** A `role` commit in flight: the server checks "admin now", receivers "admin at `e`". A
  member demoted at `e+1` whose delete is encrypted at `e` and accepted by the server after the
  demotion lands is refused by the server (good); one encrypted at `e` and accepted before the
  demotion is honoured by receivers (also consistent). Any gap?
- **C3** Bind the cleartext targets into MLS `authenticated_data` (RFC 9420 PrivateMessage AAD,
  cleartext but covered by the AEAD and signature)? Not needed for receivers (§4.3 step 1 already
  binds them) but it would let the server check the ciphertext's declared targets; does the core
  API allow setting AAD?
- **C4** Tombstones must remove the image key and thumbnail from the sealed store and any MLS-core
  retained plaintext; confirm the core keeps no application plaintext after decrypt.
