# Proposal: PROTOCOL v1.7 — end-to-end encryption with MLS (Release 0.3)

**Status:** proposed by root on 2026-10-06. Rationale in decisions 012 and 032. It needs review by
the **crypto**, **server** and **android** roles before merge. It is **additive**: apps without MLS
keep working, and a conversation upgrades only when every device in it supports MLS.

## 0. Principles
- **The server stores only ciphertext** for E2EE conversations. It never sees bodies, and it can't
  add or remove members by itself. It does route, order (epoch compare-and-set) and store opaque
  MLS messages.
- **One MLS group per conversation; each device is a leaf** (decision 032). A DM's MLS group id
  is the UTF-8 bytes of its `conversation_id`.
- **Server attestation** (decision 032): the server signs each device's MLS signature key binding.
  Clients verify the attestation of every leaf they add or accept, against the server attestation
  key pinned in the app (and published below).
- **Upgrade, never downgrade:** a conversation becomes `e2ee` when all current devices of all
  members are MLS-capable and the group is created. From then on, plaintext `msg:send` for it is
  refused with `e2ee_required`.
- **Ciphersuite** `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (0x0001). Every binary field is
  standard base64.

## 1. Devices and attestation (REST)
- **`PUT /api/v1/me/devices/{device_id}`** (v1.5) gains the optional fields
  `"mls": {"signature_key": "<b64 Ed25519 public key>", "credential": "<b64 MLS credential>"}`.
  - The response becomes `200 {"attestation": "<JWS>"}` when `mls` is present; otherwise it stays
    `204`.
  - The JWS is EdDSA, with `kid` = the server attestation key id, over
    `{"user_id", "device_id", "signature_key", "iat"}`.
  - The credential identity is `"<user_id>/<device_id>"` (never the phone).
- **`GET /api/v1/mls/attestation_keys`** (no auth) → `{"keys": [JWK, ...]}`. Clients also pin
  the current key in the app; this endpoint serves rotation.
- **`POST /api/v1/me/devices/{device_id}/key_packages`**
  `{"key_packages": ["<b64>", ...], "last_resort": "<b64>" | null}` → `204`.
  - At most 100 stored per device; each is consumed once on claim.
  - The `last_resort` package is reused only when the others run out. Clients top up when
    `GET …/key_packages/count` → `{"count": n}` falls below 20.

## 2. Groups (REST)
- **`POST /api/v1/mls/key_packages/claim`** `{"user_ids": ["uuid", ...]}`
  → `{"devices": [{"user_id", "device_id", "attestation", "key_package": "<b64>" | null}]}`.
  - It is **friends only** (`not_friends` otherwise) and atomic: each returned key package is
    deleted.
  - It returns **every** MLS device of each user; a null `key_package` means that device has none
    left.
  - Devices that aren't MLS-capable are listed with `"mls": false`, so the caller knows the
    conversation can't be E2EE yet.
- **`GET /api/v1/mls/groups/{conversation_id}`** →
  `{"e2ee": bool, "epoch": n | null, "devices": [{"user_id", "device_id"}]}`. Only members may
  call it.
- **`POST /api/v1/mls/groups/{conversation_id}/commit`** with body:
  `{"epoch": n, "commit": "<b64>", "welcome": "<b64>" | null, "added": [{"user_id","device_id"}], "removed": [{"user_id","device_id"}], "group_info": "<b64>" | null}`
  - **Compare-and-set on `epoch`:**
    - `200 {"epoch": n + 1}`;
    - **`409 epoch_conflict {"epoch": current}`**: fetch and process the missing commits, then
      retry.
  - The first commit (`epoch` 0, creating the group) marks the conversation **e2ee**.
  - The server checks that `added` devices are current devices of the conversation's members, and
    that the members are still friends.
  - Fan-out goes through the inbox:
    - kind `mls_commit` to every existing member device;
    - kind `mls_welcome` to the added devices.
- **Device changes:**
  - When a member registers a new MLS device, or one is removed (logout, `DELETE /me/devices`),
    the server emits a `mls_membership` event to the other members.
  - Any member device then adds or removes it, through a commit as above. The first commit to
    land wins.

## 3. Messages (Realtime)
- **`msg:send`** for an e2ee conversation:
  `{"client_msg_id", "to", "ciphertext": "<b64 MLS PrivateMessage>", "epoch": n, "client_ts"}`.
  There is **no `body`**.
  - The reply is unchanged: `{"message_id", "conversation_id", "server_ts"}`.
  - Errors: **`e2ee_required`** (plaintext sent to an e2ee conversation); **`stale_epoch`**
    (`epoch` is behind, so process pending commits first); `not_friends` as in v1.6.
- **Event kind `message`** for e2ee conversations carries
  `{"message_id", "client_msg_id", "conversation_id", "from", "to", "from_device", "ciphertext", "epoch", "server_ts"}`
  with **no `body`**.
  - **Only MLS-capable apps receive these**, because the conversation upgrades only when every
    device is MLS-capable.
  - Status events and acks are unchanged; they carry no content.
- **New event kinds** (in the inbox, so they're cursor-ordered and delivered offline):
  - `mls_commit` `{"conversation_id", "epoch", "commit", "from_device", "to_device"}`;
  - `mls_welcome` `{"conversation_id", "epoch", "welcome", "to_device"}`;
  - `mls_membership` `{"conversation_id", "user_id", "device_id", "change": "added" | "removed"}`.

  `to_device` targets one device: other devices of the same user ignore it. Apps before v1.7
  ignore these kinds; v1.7 apps must ignore unknown kinds.
- **Typing and presence stay metadata**, unencrypted, as today. That is documented, not hidden.

## 4. Upgrade and UI
- A v1.7 app keeps its key packages topped up. When it opens or sends to a conversation that isn't
  e2ee yet, it calls `GET /mls/groups/{id}`:
  - if every member device is MLS-capable, it creates the group (claim → commit at epoch 0 with a
    Welcome) and sends encrypted from then on;
  - otherwise it keeps sending plaintext and shows "Not end-to-end encrypted yet: <name> needs to
    update".
- E2EE conversations show a lock and "End-to-end encrypted".
- **The dev banner is removed** (decision 012) only when all of these hold:
  - every conversation of the user is e2ee;
  - the app no longer offers plaintext;
  - the rollout decision is recorded;
  - the live interop gate covers E2EE.

## 5. Server storage
- **Postgres:**
  - `mls_devices` (`device_id`, `user_id`, `signature_key`, `credential`, `attested_at`);
  - `mls_key_packages` (`device_id`, `key_package`, `last_resort`);
  - `mls_groups` (`conversation_id`, `epoch`, `e2ee_since`);
  - `mls_group_devices`.
- Ciphertext lives in the existing Cassandra inbox payloads. No plaintext body is stored for e2ee
  conversations.
- **The attestation key:** an Ed25519 key outside git, at `~/risime-keys/attestation_ed25519.jwk`
  (mode 600), with `kid` rotation.

## Open points for review
- **Crypto:**
  - the API additions needed in `risime-mls`: persistent storage via a callback storage provider;
    last-resort key packages; exporting GroupInfo; processing a Welcome for a known group id;
  - whether a commit needs `group_info` for external joins (we don't plan external joins);
  - verifying attestation inside a credential-validation callback versus in Kotlin.
- **Server:** epoch compare-and-set under concurrency, fan-out cost, and the device-change triggers.
- **Android:** the `mls.db` design (decision 012 §6); ordering commits versus messages on sync; how
  the "needs to update" UX works.
