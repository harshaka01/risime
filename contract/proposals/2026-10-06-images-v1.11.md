# Proposal: PROTOCOL v1.11 — encrypted images

**Status:** merged into `contract/v1` as **v1.11** on 2026-10-06, after review by the crypto,
server and android roles (`reviews/2026-10-06-images-v1.11-{crypto,server,android}.md`). **The
contract text is PROTOCOL §14**; where this proposal differs (notably the blob format: no
single-shot `A256GCM`, no `enc.nonce`), §14 wins. Rationale and conflict resolutions in decision 042
(accepted). Additive to v1.10; no new event kinds.

### How the crypto review was resolved
- **R1** the segmented `A256GCM-S64K` format (HKDF payload key, STREAM nonces with a final flag,
  AAD `risime-media-v1`, no header, `enc = {alg, key, plain_size}`), in the Rust core (§14.3).
- **R2** Padmé padding inside the format (§14.3).
- **R3** keys generated inside the core only, no caller keys, the stored ciphertext is the retry
  unit, local size/digest in the envelope (§14.2, §14.3).
- **R4** strict envelope validation, decode order, sniffed allowlisted decoders, header bounds
  before allocation, software bitmaps (§14.4, §14.7).
- **R5** thumbnails from the re-encoded pixels; a byte-level metadata test; save to gallery
  re-encodes (§14.7).
- **R6** `contract/v1/media_vectors.json` (5 positive, 9 negative), byte-identical from the crypto
  core's generator and the independent reference `scripts/gen-media-vectors` (§14.3).
- **Suggestions:** S3 (forwarding re-encrypts), S4 (crypto-shredding on delete), S6 (metadata in
  the privacy note) and S7 (sha256 is not the boundary) are in §14. Deferred: S1 (MLS padding, a
  separate core change), S2 (key commitment, with abuse reporting), S5 (device removal revokes
  the token; noted for server/root), S8 (progressive display, with video).

### How the server review was resolved
- **R1** streamed uploads, pre-body checks with `Connection: close`, idempotency cases
  (mismatch `400`, deleted `404`) (§14.2).
- **R2** a server-configured free-space guard and global `media` cap; defaults in decision 042
  (§14.5).
- **R3** `group_member_intervals` in Postgres, per-purpose readers, no `(blob, user)` cache (§14.2,
  §14.8).
- **R4** the `dm:` upload and read branches (§14.2).
- **R5** single range incl. the suffix form, `Accept-Ranges`, strong ETag, `If-Range`, `304`,
  `416 bytes */size`, the Caddy edge test (§14.2, §14.10).
- **R6** concurrency bound to the request process (§14.8).
- **R7** nullable `expires_at`, `deleted_at`, indexes, batched sweep, orphan pass (§14.8).
- **R8** incremental blob backups: recorded in §14.8 and decision 042; `scripts/backup` is a root
  chunk before `media` ships.
- **R9** the `mls` byte cap shipped in v1.10 (§13.4) at 256 MiB.
- **Suggestions:** S2 (only accepted uploads count), S3 (`nosniff`, `attachment`), S4 (icons
  3/h), S6, S7 are in §14. Deferred to root/infra: S1 (Caddy `request_body` limits, dropping
  `:multipart`), S3's `scripts/blob-purge`, S5 (dropping the query from Caddy's blob access log;
  until then the trail is documented in §14.9).

### How the android review was resolved
- **R1** keys and thumbnails sealed with the database key; captions in the clear stated in §14.9.
- **R2** software sRGB 8-bit bitmaps, no gain map, the byte-level metadata rule (§14.7).
- **R3** envelope validation before storing; decode bounds — the stricter crypto bound (2048 px
  and the envelope `w`/`h`) replaces 4096 px / 16 MP (§14.4, §14.7).
- **R4** eviction never destroys the last copy; fetchable until `server_ts + 29 d` (§14.5, §14.7).
- **R5** image rows never block the outbox; encode/encrypt/persist in-process (§14.7).
- **R6** the owner always reads (§14.2).
- **R7** MediaStore on API 29+, `ACTION_CREATE_DOCUMENT` on 26–28, no storage permission (§14.7).
- **R8** the sender stores the full envelope; images are restorable via §13 while the blob lives.
- **Suggestions:** S1, S2, S5, S6, S7, S9 and S10 (`image_payload_png.json`,
  `image_payload_bad_key.json`) are in §14. S3 resolved as `400 bad_request` for a mismatched
  `client_blob_id` (no new code). S8 (icons later) is android's chunk order.

## 0. Principles
- **E2EE-only.** Images are sent only in conversations that are e2ee: DMs after their upgrade
  (§10) and every group (§12). **Plaintext (legacy) DMs refuse images** (§6 below); there is no
  plaintext fallback. This keeps the banner rule simple: no image ever travels unencrypted, so
  images never delay removing the dev banner.
- **Two layers, one key per image.**
  - The image bytes are encrypted on the sender's device with **AES-256-GCM and a fresh random
    key per image**, and uploaded as an opaque blob (§12.6, extended).
  - The **key, digest, metadata, caption and thumbnail** travel in an ordinary MLS application
    message (the `image` envelope type), so only the conversation's MLS members can ever read
    them.
- **The server never sees plaintext, the real MIME type, dimensions, caption or thumbnail.** It
  stores `application/octet-stream` blobs and learns only sizes, timing and who uploads and
  downloads in which conversation (§9).
- **Privacy by re-encoding.** The sender always decodes and re-encodes: longest side at most
  **2048 px**, orientation applied to the pixels, **no EXIF, GPS, XMP or ICC metadata** written.
  The original file never leaves the device.
- **One upload serves every recipient.** A group image is uploaded once; each member downloads the
  same ciphertext.
- **Additive.** §12.6 `purpose=mls` (commits and Welcomes) is unchanged. Reactions (§11) and
  receipts / "Read by" (§12.7) work on image messages unchanged: an image message is a normal
  message with a `message_id`.

## 1. Capability and readiness
- A v1.11 app advertises **`"images"`** with its MLS device:
  `PUT /me/devices/{device_id}` `"mls": {"signature_key", "capabilities": ["groups", "images"]}`.
- **`GET /api/v1/mls/groups/{conversation_id}`** gains **`"images_ready": bool`** (absent = false):
  the conversation is e2ee **and** every app instance of every member user seen in the last 30 days
  (the §10.1 census) advertises `images`. `missing_images: [{"user_id", "device_id" | null}]` names
  the instances that don't (empty when ready).
- The server does **not** enforce `images_ready` (it can't see message types). It is a client hint:
  - **DMs:** the attach button is disabled until `images_ready` ("<name> needs to update the app
    to receive photos").
  - **Groups:** sending is allowed; while not ready the composer shows one line, "Some members need
    to update to see photos". (A pre-v1.11 app silently ignores the envelope.)
- Rollout as for v1.7/v1.9: a `required` app update precedes announcing images to the pilot.

## 2. REST changes (extends §12.6)

### 2.1 Upload
**`POST /api/v1/blobs?purpose=media&conversation_id=<dm:…|grp:…>&client_blob_id=<uuid-v4>`**,
raw bytes as the body, `Content-Type: application/octet-stream`, `Content-Length` required →
`201 {"blob_id", "size", "sha256", "expires_at"}` (same shape as `blob_upload_reply.json`;
`blob_upload_media_reply.json`).
- **Who may upload:**
  - `dm:` — the caller is one of the two users, they are friends with no block, and the
    conversation is e2ee (has an MLS group). Otherwise `404 not_found` (not a participant), or
    **`409 not_e2ee`** (`error_not_e2ee.json`) for a plaintext DM.
  - `grp:` — the caller is an **active** member (`404 not_found` otherwise, as in §12.6).
- **Single request, not resumable.** Images are at most 16 MiB of ciphertext and typically
  0.3–2 MiB after the 2048 px re-encode, so a single request with retry is the simplest thing that
  works on mobile. Chunked or tus-style resumable upload is deferred until video.
- **Idempotent by `client_blob_id`** (required for `media` and `icon`, optional for `mls`):
  - a repeat from the same user with the same id after a **completed** upload returns the same
    blob with `200`, without reading the body further than needed;
  - an interrupted upload stores nothing (the server writes to a temp file and renames only after
    the full body and its SHA-256 are in hand), so the client simply retries the whole request.
  - Clients retry with backoff (1 s, 2 s, 4 s … capped at 60 s) on network errors, `5xx` and `429`
    (honouring `Retry-After`); never on `4xx` other than `429`.
- **The server computes** `size` and `sha256` (base64, of the bytes it received). The client
  compares them with its own; a mismatch means a corrupted upload, and the client retries with a
  **new** `client_blob_id`.
- **Content-Type** is always `application/octet-stream`; any other value is `415 bad_media_type`.

### 2.2 Download
**`GET /api/v1/blobs/{blob_id}`** (unchanged path) → `200` with the bytes,
`Content-Type: application/octet-stream`, `ETag: "<sha256 hex>"`,
`Cache-Control: private, max-age=86400, immutable`.
- **Range support: a single range** (`Range: bytes=a-b` or `bytes=a-`) → `206` with
  `Content-Range`; multi-range or unsatisfiable → `416`. Clients use it to resume an interrupted
  download (`If-Range` with the ETag). Integrity is still checked over the whole file (§7).
- **Read authorisation for `media`** (decision 042):
  - `dm:` — either of the two users (always; a later unfriend or block doesn't revoke a
    ciphertext they may already hold the key for).
  - `grp:` — a user who is an **active member now**, **or who was an active member at any moment
    from the blob's upload until now** (membership interval overlapping `[uploaded_at, now]`).
    - So a **member removed after an image was sent can still download it** for its remaining
      TTL. They received the message (and its key) while they were a member; refusing the bytes
      would only break images they legitimately received but hadn't downloaded yet. They learn
      nothing new: without the key the blob is noise, and they never receive keys of later
      messages (removal rotates MLS keys).
    - A member removed **before** the upload can't download (they could only have the key by
      someone leaking it, and then they could leak the image too).
    - A user who joins after the upload but before the message is sent is an active member, so
      they can read it (they get the message at the new epoch).
    - `pending_add` users can't read `media` blobs (they aren't leaves yet).
  - Every other case, including expiry and deletion, is `404 not_found`.
- **Rate limit:** 600 downloads per user per minute, at most 8 concurrent per user (`429`).

### 2.3 Usage
**`GET /api/v1/blobs/usage`** → `{"media": {"used": n, "limit": n, "uploads_last_hour": n, "hourly_limit": n}}`
(`blob_usage_reply.json`). `used` counts the caller's live (unexpired, undeleted) `media` bytes.

### 2.4 Delete
`DELETE /api/v1/blobs/{blob_id}` is unchanged (owner only, idempotent). Clients don't call it for
sent images in v1.11 (there is no "delete for everyone" yet); it exists for cancelled sends: if the
user cancels after the upload and before `msg:send`, the client deletes the blob so it stops
counting against their quota.

### 2.5 Purposes, caps and limits
| | `mls` (v1.9, unchanged) | **`media`** | **`icon`** |
|---|---|---|---|
| Conversations | `grp:` | `dm:` (e2ee) and `grp:` | `grp:` only |
| Max size | 2 MiB | **16 MiB** (16 777 216 B) | **512 KiB** |
| TTL | 30 days | **30 days** | **none while current** (below) |
| Readers | §12.6 | §2.2 above | active and `pending_add` members |
| Upload rate | 60 / h | **120 / h and 1000 / day** | 10 / h |
| Concurrent uploads | — | **3 per user** | shared with `media` |
| Quota | — | **2 GiB live per user** | not counted |

- **Quota:** the sum of the caller's live `media` blob sizes. An upload that would take `used`
  over the limit gets **`413 quota_exceeded {"used": n, "limit": n}`**
  (`error_quota_exceeded.json`), checked from `Content-Length` before reading the body. Space comes
  back as blobs expire (30 days) or are deleted. 2 GiB is about 1500 photos a month at the typical
  1.3 MiB, far above a normal pilot user; it is a backstop against abuse, not a product limit.
- **Too large:** over the purpose's cap → `413 too_large` (as in §12.6), also from
  `Content-Length` (and enforced while streaming, in case the header lies).
- **Rate and concurrency:** `429 rate_limited` with `Retry-After` (as in §7.1). A 4th concurrent
  upload is `429` with `Retry-After: 2`.
- **Server-wide guard:** if `BLOB_DIR` has less than **10 GiB** free, `media` uploads get
  **`507 storage_full`** (`mls` and `icon` keep working until 1 GiB free). Clients show "Couldn't
  send the photo. Try again later." and retry no more than hourly.
- **Group icons (`icon`):** a blob holding the encrypted group icon referenced from `group_meta`
  (§3.2). Only admins may upload (`403 not_admin`). At most **one current icon per group**: a new
  `icon` upload makes it current, and the previous one is deleted **7 days** later (so members
  still on the old epoch can fetch it). The current icon never expires; it is deleted with the
  group. Removed members lose read access at once (the icon isn't history).

## 3. Payload envelope (MLS application message)

### 3.1 Type `image` (`image_payload.json`)
```json
{
  "v": 1,
  "type": "image",
  "blob": {"blob_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f", "size": 1048593, "sha256": "<b64 SHA-256 of the ciphertext>"},
  "enc": {"alg": "A256GCM", "key": "<b64 32 bytes>", "nonce": "<b64 12 bytes>"},
  "mime": "image/jpeg",
  "w": 2048,
  "h": 1536,
  "thumb": {"mime": "image/jpeg", "w": 128, "h": 96, "data": "<b64, at most 4096 bytes decoded>"},
  "caption": "Site visit, level 3"
}
```
- **`blob`** is a §12.6 reference: `size` is the **ciphertext** size, `sha256` the SHA-256 of the
  **ciphertext** (exactly the bytes served), as returned by the upload.
- **No plaintext digest.** AES-GCM's tag already authenticates the plaintext under a key that only
  members have, so a plaintext hash adds no integrity. It would only add a stable cross-chat
  fingerprint of the photo (the same photo sent twice would get the same hash in two envelopes),
  which we don't want for a future forwarded or leaked envelope.
- **`enc`:** `alg` is `"A256GCM"` (the only value in v1.11; a receiver that sees another value
  shows "Couldn't open this photo"). `key` is 32 fresh random bytes per image from a CSPRNG, never
  reused; `nonce` is 12 random bytes. The **blob is `ciphertext ‖ tag`** (16-byte tag, no prefix),
  so `size` = plaintext length + 16. AAD is the ASCII string `risime-image-v1`.
- **`mime`:** `image/jpeg` (the default re-encode, quality 85), or `image/png` only when the source
  has transparency and the PNG is under the cap, or `image/webp`. Receivers must render all three.
  Animated images are sent as their first frame in v1.11.
- **`w`, `h`:** pixel size after orientation and scaling (1–2048 each; longest side ≤ 2048).
- **`thumb`** is the inline thumbnail, or `null`.
  - JPEG (or WebP), longest side **at most 128 px**, at most **4096 bytes** decoded (about 5.5 KiB
    of base64). It needs no second encryption layer: it lives inside the MLS ciphertext, which is
    already end-to-end encrypted with the conversation's keys, the same as the caption.
  - Senders start at quality 60 and step down (50, 40, then 96 px, then 64 px) until it fits.
  - **Size bound of the whole envelope:** the UTF-8 JSON of the envelope (serialised without
    escaping non-ASCII, §10.3) must be **at most 22 KiB** (22 528 bytes), leaving 2 KiB for MLS
    framing, signature and padding under the 24 KiB ciphertext cap. If a long caption pushes it
    over, the sender sets `thumb` to `null` (the caption wins). The worst case, a 16 KiB caption
    plus a 4 KiB thumbnail plus about 600 bytes of fields, is 21.6 KiB.
- **`caption`** is optional (absent or omitted when empty). When present it follows §11.1: 1–4096
  grapheme clusters, at most 16 KiB of UTF-8, not whitespace-only. The server can't check it, so
  senders enforce it; receivers render what they get, cut at 4096 graphemes.
- **Receivers ignore unknown fields** (later: `blurhash`, album grouping, view-once, reply).
- An `image` envelope with a missing or malformed required field (`blob`, `enc`, `mime`, `w`, `h`)
  is dropped as unknown and logged, as for an unknown type.

### 3.2 Group icon in `group_meta` (`group_meta_icon.json`)
`group_meta.icon` (§12.2, `null` until now) becomes:
```json
{"blob": {"blob_id": "…", "size": 61456, "sha256": "<b64>"}, "enc": {"alg": "A256GCM", "key": "<b64>", "nonce": "<b64>"}, "mime": "image/jpeg", "w": 512, "h": 512}
```
- Square, 512×512, JPEG quality 85, metadata stripped as for images; uploaded with
  `purpose=icon`. No thumbnail (members download the icon once and cache it).
- Set or changed by the existing `meta_changed` commit (§12.4); `null` removes the icon. A fresh
  key per icon version.
- Receivers that can't fetch it (`404`) show the default group avatar; it's never an
  unrecoverable state (unlike a `commit_ref`).
- v1.9 apps already ignore unknown `group_meta` content they don't use; they keep showing the
  default avatar.

## 4. Events
**None new.** An image is an ordinary e2ee `message` event (§10.3) or group `message` event
(§12.7) whose decrypted envelope has `type: "image"`. Push wake-ups, acks, `status`,
`group_receipt`, reactions (§11.2, `target` = the image's `message_id`) and the "Read by" sheet are
unchanged.

## 5. Errors
| Code | HTTP | When |
|---|---|---|
| **`not_e2ee`** | 409 | `media` upload for a DM that isn't e2ee yet |
| **`quota_exceeded`** | 413 | upload would exceed the per-user `media` quota; body `{"used", "limit"}` in `error` |
| `too_large` | 413 | over the purpose's size cap (§12.6 code, new caps) |
| **`bad_media_type`** | 415 | `Content-Type` isn't `application/octet-stream` |
| `rate_limited` | 429 | hourly / daily / concurrent upload or download limits, with `Retry-After` |
| **`storage_full`** | 507 | `BLOB_DIR` below the free-space guard |
| `not_admin` | 403 | non-admin `icon` upload |
| `not_found` | 404 | not a participant / not allowed to read / expired / deleted |
| `bad_request` | 400 | unknown `purpose`, missing `client_blob_id` for `media`/`icon`, `icon` for a `dm:` |

## 6. Plaintext (legacy) chats
- **Refused.** The upload is `409 not_e2ee`, and a plaintext `msg:send` has no image field at all
  (`body`/`reaction`/`ciphertext` stay the only content fields, §11.2).
- **UI:** in a DM that isn't e2ee, the attach button is shown disabled; tapping it shows
  "Photos need end-to-end encryption. They'll work once <name> updates the app." If `not_e2ee`
  comes back anyway (a race), the message fails with "Couldn't send: this chat isn't end-to-end
  encrypted yet."
- Why: a plaintext fallback would put photos on the server in the clear (or under a key the server
  routes), contradicting the encryption banner work, and would need a second code path that dies
  when E2EE is everywhere. Every pilot chat is e2ee after the v1.7 rollout anyway.

## 7. Client behaviour (android)
**Sending**
1. Pick with the system Photo Picker (no storage permission). Camera capture is a later chunk.
2. Decode with `ImageDecoder` (or `BitmapFactory` with EXIF orientation read and applied to the
   pixels), downscale so the longest side ≤ 2048 px (never upscale), re-encode JPEG quality 85.
   `Bitmap.compress` writes no EXIF, so GPS and camera data are gone. Make the thumbnail (§3.1).
3. Generate key and nonce (`SecureRandom`), encrypt with AES/GCM/NoPadding and the AAD, compute the
   SHA-256 of the ciphertext.
4. Store the encrypted file and the envelope (with key) locally first, so a restart resumes.
   Upload with `client_blob_id` and retries (§2.1); check the returned `size`/`sha256`.
5. Hand the envelope to the outbox as an e2ee `msg:send` (it encrypts at send time, `stale_epoch`
   handling unchanged). The bubble shows the local image with upload progress, then the normal
   ticks. **Text sent while an image uploads isn't held back**; the image takes its order when its
   `msg:send` is accepted.
6. Failures: `quota_exceeded` → "You've reached your photo storage limit. Older photos free up
   space after 30 days."; `too_large` (can't happen after re-encode, defensive) → "This photo is too
   large"; `not_e2ee` (§6); `storage_full` → "Couldn't send the photo. Try again later." Each failed
   bubble offers Retry / Delete.

**Receiving**
1. Decrypt the MLS message as usual; persist the envelope (key included) and show the thumbnail
   (blurred, at the `w`×`h` aspect ratio) inside the same transaction. Nothing is fetched inside it.
2. **Download** outside the transaction: automatically when the chat is shown or on Wi-Fi, otherwise
   on tap (a setting later). Resume with `Range`. Check `size` and the ciphertext `sha256` **before**
   decrypting; then AES-GCM decrypt (tag check), then decode.
3. **Cache:** keep the **ciphertext** in app-private storage and decrypt into memory when shown, so
   no plaintext image sits on disk; the key lives in the encrypted database (§10.4). LRU cap
   about 500 MiB; evicted images are fetched again while the blob lives.
4. Errors: `404` → "This photo is no longer available" (thumbnail stays); digest mismatch or GCM
   failure → "Couldn't open this photo" (retry the download once, then give up; logged).
5. **Full-screen view** on tap (pinch-zoom, caption below). **Save to gallery** from the viewer
   menu writes the decrypted bytes (already metadata-free) to `Pictures/RisiMe` through MediaStore;
   it's the only path by which plaintext leaves the app, and only on user action.
6. **Notifications:** "📷 Photo" or "📷 <caption>"; the chat list preview the same. No image in
   notifications.
7. **Reactions, "Read by", long-press** work as for text; Copy copies the caption.

**Group icon:** an admin picks an image → square crop 512 px → `icon` upload → `meta_changed`
commit with the new `group_meta.icon`. Members fetch and cache it when the commit or Welcome is
processed.

## 8. Server storage
- `blobs` (§12.10) gains `client_blob_id` (unique per owner), `uploaded_at` and
  `deleted_at`; `purpose` gains `media` and `icon`. Bytes stay in `BLOB_DIR/<2 hex>/<uuid>` as in
  v1.9, written to a temp file and renamed after the SHA-256 is computed.
- **Membership history for the read rule:** `group_member_intervals(group_id, user_id, active_from,
  active_until | null)`, written when a member becomes active and when they turn `pending_remove`
  (the moment their delivery stops). Read check: an interval with `active_from ≤ now` and
  (`active_until` null or ≥ the blob's `uploaded_at`).
- Quota: `SUM(size)` over the owner's live `media` blobs (an index on `(owner, purpose)`); rates via
  the existing rate limiter (decision 001); concurrency via a per-user counter.
- **Expiry:** the existing Oban sweep deletes expired `media` blobs and superseded `icon` blobs
  after their 7-day grace (rows and files). Group deletion deletes its `icon` blobs.
- **Backups:** blobs are already archived by `scripts/backup --blobs` (decision 025, PROD.md). No
  Cassandra change: image messages are ordinary ciphertext rows.

## 9. Privacy and learning log
- The server learns: blob sizes (so roughly the image's byte size), upload and download times, who
  uploaded and who downloaded, and in which conversation; the `purpose` (`media` vs `icon`); counts
  per user for quotas. It does **not** learn the content, MIME type, dimensions, caption, thumbnail,
  or which `message_id` an image belongs to (it can guess from timing).
- No server-side model ever sees an image. The learning log (CLAUDE.md) records model calls only;
  images enter it never on the server, and on the device only under the on-device rules (later).
- This is documented in the app's privacy note together with typing and presence metadata (§10.0).

## Open points for review
- **Crypto:**
  - AES-256-GCM single-shot over up to 16 MiB in memory on Android (fine on today's phones), versus
    a chunked AEAD (e.g. STREAM / per-64 KiB segments) that would allow streaming decrypt and true
    ranged display. Proposed: single-shot now, `alg` reserved for a chunked mode with video.
  - Random 12-byte nonce with a fresh key per image (a fixed nonce would also be safe; random costs
    nothing). AAD `risime-image-v1`: should it also bind `blob_id` (only known after upload, so the
    sender would encrypt after reserving an id)?
  - No plaintext digest (§3.1): agree?
  - Inline thumbnail protected by MLS only, no second layer: agree?
- **Server:**
  - Streaming a 16 MiB body to disk under Plug/Bandit (no `Plug.Parsers` buffering); Caddy's
    `request_body max_size` must allow 16 MiB + headroom on `/api/v1/blobs`.
  - `group_member_intervals` versus extending `group_members` with history; the read check cost on
    every download (cache per `(blob, user)`).
  - Quota and rate numbers (2 GiB live, 120/h, 1000/day, 3 concurrent, 507 at 10 GiB free) against

  - Group `images_ready` UX (send anyway with a notice) versus disabling like DMs.
