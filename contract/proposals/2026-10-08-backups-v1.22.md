# Proposal: encrypted backups (contract v1.22)
Date: 2026-10-08. Author: root session (P0-2, disappearing chats). Decision 059.
**Status: merged** into PROTOCOL §22 as v1.22 (2026-10-08), with the review changes below.

## Problem (P0-2 findings 1 and 2)
Testers uninstall and reinstall when the in-app update fails; `allowBackup` is false (§10.4) and
MLS state can't be restored anyway, so every reinstall loses all chats. History sharing (§17) needs
another device that still holds them: 29 requests on the pilot, 7 done, 11 unavailable, 11 waiting
for a member. §17.14 promised a client-encrypted backup that reuses the §17.7 bundle.

## Proposal (normative text: PROTOCOL.md §22)
1. **A backup is a §17.7 bundle with `origin: "backup"`** for every conversation, plus conversation
   (chat state, `cleared_upto`, group metadata), tombstone, group-event and contact lines; restored
   through the §17.7 import (dedupe, deletes win), not bound to the gap index or 30 days. Never MLS
   state, cursor, device id, HPKE keys, tokens, behaviour log. Restore = messages only; the device
   rejoins as a new leaf.
2. **Keys:** per-account `BK` (local in `mls_kv`, Keystore-wrapped DB key; recovery copy wrapped
   under Argon2id(m 64 MiB, t 3, p 1) of a 120-bit recovery key and optionally a passphrase with a
   floor, AAD "risime-backup-v1" ‖ user_id ‖ kind ‖ bk_id); per-backup `DEK`; AES-256-GCM STREAM
   with 64 KiB chunks, chunk index and last flag in nonce and AAD, header hash bound into every
   chunk; raw DEFLATE + Padmé.
3. **One file format** (`RISIMEBK` v1) for server, local and exported backups; the header carries
   the key record so a file restores with the recovery secret alone.
4. **Server:** blob purpose `backup` (owner-only, parts of 32 MiB, ≤ 16 parts / 512 MiB, newest 2
   current, replaced 7 days, 1.5 GiB live, 6 backups/day); `POST/GET/DELETE /api/v1/backups`,
   `PUT/GET /api/v1/backup_key`; `auth/config` `backup` switch; four error codes.
5. **Client schedule:** server backup daily; local backups daily, before every in-app update and
   before any confirmed wipe; no server backup from a fresh install before restore or skip.
6. **Vectors:** `contract/v1/backup_vectors.json`, generated by crypto.

## Version split
v1.21 (rejoin without reset, §12.12) is small, urgent and needs no crypto work, so it merged first
and can ship at once; v1.22 needs a core release (Argon2id, the stream, the FFI) before Android can
use it. Both are merged on 2026-10-08.

## Alternatives considered
- **Android Auto Backup / Google Drive** (`allowBackup`): would copy the database and its key
  material to Google; the Keystore-wrapped DB key doesn't survive a reinstall anyway, and MLS state
  must never be restored. Rejected (decision 033 stands).
- **Server-side key escrow** (the server can decrypt with a key it holds): breaks "the server stores
  only ciphertext". Rejected.
- **A new format for backups:** two import paths would drift. The §17.7 entry is the unit.
- **Including full-size images:** 16 MiB each would dominate size and quota; v1 keeps images by
  reference with the thumbnail and key (the original blob is readable for 30 days). A later schema
  can add media parts.
- **Silently-on server backups:** impossible without the user keeping a secret; a backup only the
  lost phone could open is useless. The app asks once and keeps a card until set up or dismissed.
