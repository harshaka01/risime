# Proposal: PROTOCOL v1.10 — sender copy and history gap marker (reinstall history)

**Status:** draft for review by the server and android roles. Rationale in decision 042
(proposed). It is additive: v1.9 apps keep working, ignore the new reply field, and already
handle the new copy correctly (§1.3).

## 0. The bug and its cause
After a reinstall, a chat showed only the other person's messages.
- A fresh install has no cursor, so its first join is `since: null`. The server then replays the
  user's **whole inbox partition**, every event still inside the 30-day TTL, acked or not
  (`inbox_events`, `default_time_to_live = 2592000`; acks never delete events).
- **Plaintext DMs:** the `message` event is written **only to the recipient's inbox**
  (`server/lib/risime/messaging.ex:327-332`). The sender's text lived only in the old install's
  Room database, so it's gone. Received plaintext comes back.
- **E2EE DMs and groups** already write the same event to the sender's inbox (§10.3, §12.7). But
  a new install is a new device (a new `device_id` and a new leaf). It can't decrypt anything
  encrypted before it joined (§10.0, decision 032). Today these events are parked with no group,
  then dropped after the Welcome, only logged (`MlsPipeline.kt:132-134`, `151-153`). The user
  sees nothing: **no gap, no hint.** That is a silent half-history, and it hits both sides of an
  E2EE chat.

This proposal fixes the plaintext half and makes the E2EE half visible. Restoring E2EE history
needs encrypted backup (§4), which is out of scope here.

## 1. Sender copy for plaintext DMs (server)
### 1.1 Rule
- A plaintext `message` event (`body`) is written to the **recipient's and the sender's inboxes,
  with the same `event_id`** (= `message_id`). This is the rule that §10.3 (e2ee DMs), §11.2
  (reactions) and §12.7 (groups) already follow; v1.10 makes it universal:
  **every stored `message` and `reaction` event goes to every member user, the sender included.**
- The payload is unchanged (`from`, `to`, `body`, …). There's no new kind and no flag: a copy is
  recognised by `from` = the inbox owner.
- **Never pushed.** The sender's copy is written with no push (as in §10.3), so the sender's
  phone is never woken by its own message.
- **Same TTL** as every inbox event (30 days). The copy expires with the recipient's.
- **Idempotency:** the copy is written in the same `deliver` step as the recipient's event. An
  idempotent resend that re-delivers (the message index is missing) writes both again under the
  same `event_id`, which overwrites the same Cassandra row (no duplicate). Clients dedupe by
  `event_id`, `message_id` and `client_msg_id` as today (§2.3).
- **Ordering:** the sender's copy uses `event_id = message_id`, which is earlier than any
  `status` event for that message (those get fresh TimeUUIDs). A device that replays the sender's
  inbox therefore stores the message before its ticks arrive.

### 1.2 Receipts and ticks on own copies
- An own copy is **outgoing**. It must never count as delivered or read by the peer.
  - Clients **never `msg:ack`** a message whose `from` is themselves. The server already ignores
    such acks: DMs advance only for `recipient_id = caller`, and group acks from the sender must
    be ignored too (the server review confirms `GroupReceipts.ack` skips `user_id = sender`).
  - Its initial state is `sent` (✓). `delivered`/`read` come **only** from `status` events
    (DMs) or `group_receipt` events (groups), which are already stored in the sender's inbox and
    replay after the copy.
- A sender's other device that is online shows the message as its own at once. That's the
  multi-device behaviour E2EE chats already have.

### 1.3 Old apps (v1.9 and earlier)
- **The sending device:** its outbox row has the `client_msg_id`, so the copy is a duplicate and
  is skipped (`ChatEngine.applyMessage` checks `byClientMsgId`). The live copy can arrive before
  the `msg:send` reply. The outbox row exists before the push, so it is still skipped.
- **Another device or a reinstall** stores it as outgoing `sent` and needs no change
  (`applyMessage` sets `outgoing = from == me` and acks only incoming).
- So the server change can ship before any app update.

### 1.4 Backfill (server, one-off, optional)
Plaintext DMs sent before v1.10 have no sender copy, but their recipient's event is still inside
the TTL. A one-off release task may copy each plaintext `message` event from the recipient's
partition into the sender's partition:
- the same `event_id` and payload;
- `USING TTL` = the source row's remaining `TTL(payload)`, so nothing outlives the original;
- a paged full scan, no `ALLOW FILTERING`, idempotent (it rewrites the same row).
- Because `event_id = message_id`, the copy lands at its original time. Devices whose cursor is
  already past it never see it, and they don't need it. A fresh install replays it in place.
- It covers only messages still inside the 30 days. It restores **plaintext only**. E2EE events
  already have their copies.

## 2. History boundary hint (server)
- The inbox **join reply and every `sync` reply** gain
  **`"history_before": "<ISO-8601 ms>" | null`**: the server time at which this `device_id` was
  **first seen** for this user (the §10.1 census).
  - Null when the socket sent no `device_id`.
  - It is the same value on every page, so clients may read it from any reply.
  - The server stores it as `app_instances.first_seen_at`: set on insert and never updated by
    later connects. Existing rows are backfilled with `last_seen_at`. That is a conservative
    late value: it only makes fewer messages count as "before this install".
- Meaning: an **e2ee** message with `server_ts < history_before` was encrypted before this
  install existed, so this device can **never** decrypt it.
- Plaintext events are unaffected and shown normally.
- Example: `inbox_join_reply_v110.json`
  `{"events": [], "has_more": false, "server_time": "…", "history_before": "2026-10-06T08:15:30.123Z"}`.

## 3. The history gap marker (client)
### 3.1 What counts as "before this install"
An e2ee `message` event (DM or `grp:`) is **pre-install** if either of these holds:
1. `server_ts < history_before`. This is known at once, even with no local group.
2. This device joined the group from a Welcome at `(generation g, epoch e)`, and the message has
   `generation == g` and `epoch < e`. This covers messages sent between the first connect and the
   Welcome.

The old install's own sends (`from` = me, `from_device` = the old device) fall under the same
rules. They are the half the user noticed missing, and they need no special case. Undecryptable
reaction envelopes count the same way, because the client can't tell them apart before
decrypting.

Pre-install messages are **not parked** in `mls_pending`; rule 1 decides at once. Under rule 2
they are resolved when the parked event is replayed after the Welcome. They are not decrypted,
not stored as messages and not acked, and they still advance the cursor.

**Not covered:** any other decrypt failure on a device that should hold the key (a real bug, or
tampering). It stays `Dropped` and logged, as §10.3 says today. See open point A3.

### 3.2 What the client shows
- **One system line per conversation:** **"Earlier messages are on your previous install"**.
  - It's a local row (`kind = system`), never sent, never acked, never notified, never unread.
  - It isn't counted as the chat's last message for the chat list preview.
  - Its id is deterministic: `client_msg_id = "sys:history:<conversation_id>"` (an upsert), so
    there is **one line per chat, not one per message**, across syncs, replays and restarts.
- **Position:** its `server_ts` is the **latest** pre-install message's `server_ts`. Each further
  pre-install message for that chat moves it later, never earlier. So it sits just above the
  first message the device can read, and below any older plaintext (pre-E2EE) messages, which are
  shown normally.
- **No gaps without the line.** If a chat has at least one pre-install message, it shows the
  line, even if nothing else is readable. A chat that would otherwise be empty is listed with the
  line, so it doesn't vanish.
- **Groups (§12):** the same rule and the same line, keyed by the `grp:` id.
  - `group_event` system lines (created, added, …) are plaintext metadata. They replay and show
    normally around the marker.
  - A **new member** (not a new device) has no earlier events in their inbox (§12.0, no history
    for new members). They get no marker, which is correct: there's nothing they missed.
  - §12.8 "Encryption was reset; some messages may be missing" is unchanged and separate.
- **Plaintext chats** show the restored messages from both sides (§1). No marker is needed.
  Messages older than the 30-day TTL are gone for everyone. That's the existing retention, not a
  gap, so there's no marker.

### 3.3 Old apps
- An app before v1.10 ignores `history_before` (§0: unknown fields).
- It keeps today's behaviour (silent drop) until it updates.
- The marker is client-only, so there's no wire change beyond the reply field.

## 4. Out of scope: encrypted backup and restore (next step)
The real fix for E2EE history across reinstalls and new devices is a **client-encrypted
backup**. It covers the message history (Room) and, optionally, the MLS state, sealed under a key
the user holds: a recovery code or passphrase, or a key wrapped by a second device. The server or
a cloud drive stores it only as an opaque blob (the §12.6 blob store is a candidate), and the
server can never read it. A restore imports the history before the first sync. Multi-device
history then follows from the same building block: a new device restores, or receives an
encrypted history transfer from an existing device of the same user. It needs its own proposal,
product decisions (key custody, recovery UX, what happens on a lost code) and a crypto review.
**Until it ships, testers must not uninstall** (decision 042).

## 5. Examples (new)
- `inbox_join_reply_v110.json`: a join reply with `history_before`.
- `event_message_sender_copy.json`: a plaintext `message` as it appears in the sender's own inbox
  (`from` = the inbox owner).
- Both test suites parse them. The server tests cover the copy (both inboxes, the same
  `event_id`, no push), an ignored self-ack, and `history_before` (first seen, stable across
  connects, null without a `device_id`).

## 6. Changelog line (on merge)
- **v1.10**: the sender copy for plaintext DMs (every `message`/`reaction` event goes to every
  member user, the sender included, with no push), `history_before` on join/sync replies, and the
  client history gap marker. An additive change.

## Open points for review
**Server**
- S1. Confirm `GroupReceipts.ack` ignores the sender's own ack (add a test if it doesn't).
- S2. Backfill (§1.4): run it on the pilot, or only prospectively? Time the scan on the pilot
  partition sizes, since dev holds about 2.3M events from load tests.
- S3. `first_seen_at` on `app_instances` vs `devices.inserted_at`. The census row exists for
  every app instance; the `devices` row only for push/MLS-registered ones. The census pruning
  window resets it. Is that acceptable?
- S4. Sender-copy write cost: one extra Cassandra write per plaintext DM. It has no push, and the
  load-test headroom should be checked.

**Android**
- A1. Implement §3.1 in `MlsPipeline`: a new `MlsResult.BeforeInstall(conversationId, serverTs)`
  instead of `Dropped`/park, and the upsert of the line in the same transaction as the cursor.
- A2. Wording for a second device that isn't a reinstall: keep "previous install", or say "on
  your other device" when the user has other current devices?
- A3. Should a non-pre-install decrypt failure also get a (different, deduplicated) line, for
  example "A message couldn't be decrypted"? This proposal keeps today's silent drop for it.
- A4. Room migration for the marker (it reuses `KIND_SYSTEM` and `system_json`), and the
  chat-list handling of a chat whose only row is the marker.
