# Proposal: Calendar v2 — honest footer, real titles on the phone, one row per thing, Risi as the guide (2026-10-14)

**Status:** proposal for root/Harsha, to be applied as **§44** (after §42 send-for-me and §43 permission fix-it).
Amends §25.3, §26.2, §27.6, §28.5, §29.7, §29.12, §34.1, §34.4, §43. Nothing in PROTOCOL.md changes until root
applies it. Built behind the server switch **`RISI_CALENDAR_V2`** (`off | canary | on`, `RisiMe.Agents.Flags`,
default `canary` = `RISI_DEV_USERS`), told to the phone by the **`/me` field `calendar_v2: true`** (absent
otherwise, so `off` is byte-identical). The app never hard-codes who is in the canary.

## Why (P1, Harsha's Honor phone, 14 Oct 10:55–11:47 SLT)
RisiMe's calendar permission granted, Android "Sync Calendar" on for his three Google accounts. Risi read the
phone's events, but:
1. **"Not checked: Phone calendar (sync is off)"** under events that were read from the phone calendar.
2. Phone events listed as **"Busy"** with no title, time-only.
3. **"Free up calendar on 18th Oct whole day" three times:** a reminder Sat 23:45, a Risi Calendar entry Sun
   00:00–01:00 and "Your promise" Sun 00:00.
4. "Whole day" became 00:00–01:00; the reminder came 15 min before midnight.
5. Risi says "can't access" instead of guiding.

### Root causes
- **Stale footer and "Busy" are one bug.** The phone's `calendar_check` reports `phone_provider` with
  `read_ok: false, reason: "sync_off"` whenever **Android's account auto-sync** says off for every account with
  a calendar: `ContentResolver.getMasterSyncAutomatically()` (the phone-wide "Auto-sync data" switch, off by
  default on several Honor/Huawei builds and in battery-saver modes) or `getSyncAutomatically(account,
  "com.android.calendar")`. It still sends the calendars it read and their busy blocks (v1.32 §29.7: "sync_off
  … never as a read"). The server therefore (a) put the phone under "Not checked: Phone calendar (sync is
  off)" even though the events in the same answer came from it, and (b) did not send `local_events` (only a
  `read_ok: true` phone read does), so the phone could not list the events with their titles, and the server
  listed the bare blocks as "Busy (phone calendar)". The "sync" is **Android's account auto-sync**, not
  RisiMe's and not the Google account's Calendar toggle, and it says nothing about whether the read happened.
- **Three rows** come from three separate stores for one promise: the ledger item (due 00:00 as a *timed* due:
  the model gave `due_local: "2026-10-18T00:00"` for "whole day"), the §28.5 "Remind me?" reminder (due − 15
  min = Sat 23:45) and the §29.12 Risi Calendar event (due + the 1-h default). The listing (server text and the
  phone's "Your events") showed each store as its own row.

## 44.0 Principles
1. **The footer says what THIS request read**, never a cached flag, in plain words: "From: your phone calendars
   (codegen.net, risicloud.ai, gmail.com) · Risi". No "Checked / Not checked".
2. **Phone calendars that were read are read**, whatever Android's auto-sync says. Auto-sync is a setup hint
   (§44.7 step c), never a "not checked".
3. **Event titles stay on the phone.** The server sends a range (and refs); the phone fills in title, time and
   calendar name when it shows Risi's answer. Titles reach the server only after the user says **Yes** to "Let
   Risi read meeting titles to help plan your day?" (default **Only times**).
4. **One row per real thing**, with small tags (`promise · reminder`) instead of separate rows.
5. **Whole day means all day.** Durations are parsed (whole day, morning, afternoon, evening, "2 hours", …, in
   en/si/ta/Singlish); unclear → ask.
6. **Sensible reminders:** an all-day block → the day before at 18:00 (or the user's own time); a meeting → 15
   min before (or the user's learned lead).
7. **Risi is the guide** (builds on §43): one sentence, one fix-it button, re-check by itself, retry the
   original request, confirm.

## 44.1 Switch, `/me`, capability
- **`RISI_CALENDAR_V2`** = `off | canary | on` (runtime; default `canary`).
- **`GET /me`** (User, §1): `calendar_v2: true` while the switch applies to the user; absent otherwise.
- **Device capability `risi_calendar_v2`** (`mls.capabilities`, kept only with `risi_tools`): the phone renders
  §44.3–§44.6 and sends `read_ok` per §44.2. The server's own parts (§44.2 read rule, footer text, merged
  server list, all-day parsing, reminders) need no capability.

## 44.2 What counts as a read (amends §29.7)
- A `phone_provider` source with at least one calendar is **a read**, with `read_ok: true` **or** with
  `read_ok: false, reason: "sync_off"` (an old phone). The server treats both the same: the answer lists the
  phone's events (`local_events`) and the footer names "your phone calendars".
- A `risi_calendar_v2` phone sends `read_ok: true, reason: null` whenever it read calendars (auto-sync is not a
  read failure). `sync_off` stays valid on the wire for old phones; nothing else changes in the result shape
  (`blocks` keep exactly `start, end, busy, all_day`: **no titles**, ever, in `calendar_check`).
- Not a read: no permission, no calendars, a query error, a timeout. Those go to §44.7 (the guide) or one
  plain sentence ("I couldn't read your phone calendar: it didn't answer in time.").

## 44.3 The footer (`answer.footer`, the asker's Risi chat; replaces the "Checked:" line under the switch)
Body text (last paragraph): **"From: your phone calendars · Risi"**. Only sources read in this request, in this
order: `your phone calendars`, `Google Calendar` (a v1.31 link that was read), `Risi` (Risi Calendar and/or
Risi's items). A connected source that could not be read gets one plain sentence above the footer, e.g. "I
couldn't reach Google Calendar (needs reconnecting)." — never "Not checked".
```
risi.footer: {"v": 1,
  "read": ["phone_provider" | "google_api" | "risi_calendar" | "risi_items", …],   what this request read
  "phone_calendars": int | null,   how many phone calendars were read (null: no phone read)
  "first_read": bool}              §44.4
```
The `calendar_v2` phone shows the footer as **"From: your phone calendars (codegen.net, risicloud.ai,
gmail.com) · Risi"**: the account domains are the part after "@" of its own calendar accounts' names (a local
account: "this phone"); they never leave the phone. An old phone shows the body text.

## 44.4 First read after the permission
The first successful phone read for a user (and the first after the phone reported the calendar permission
`denied` or answered `permission_granted`) puts one line first: **"✓ I can see your calendars now."** with
`footer.first_read: true`; the phone shows "✓ I can see your calendars now: codegen.net, risicloud.ai,
gmail.com." Once per grant (server `risi_calendar_prefs.first_read_at`).

## 44.5 Phone events with real titles (amends §29.7 "Your events", §34.1)
- The answer carries `local_events: {from, to}` (unchanged shape) whenever the phone was read (§44.2). These are
  the event refs: the range; the phone fills in each event's **title, time and calendar name** from its own
  provider when it renders the message.
- **With `local_events`, the server's text does not list** phone events, Risi Calendar events or Risi's items:
  the head line only ("Tomorrow, Thu 15 Oct:"), so nothing is listed twice. The phone's "Your events" is the one
  list. Without `local_events` (no phone read), the server lists Risi's own things, merged (§44.6).
- A row: `Thu 15 Oct · 10:00–11:00 · Design review · Work`. A row of a calendar the user can only see as
  free/busy (`CALENDAR_ACCESS_LEVEL` ≤ `CAL_ACCESS_FREEBUSY`), with no title: **"Busy (shared calendar, no
  details)"**. An own event with an empty title stays "(No title)". "Busy" is never shown for an event that has
  details.
- **Titles consent:** `risi_calendar_prefs.titles` = `"times"` (default) | `"titles"`. Risi asks **once**, only
  when an answer needs titles (meeting prep: "prepare me for tomorrow's meetings"): `answer` "Let Risi read
  meeting titles to help plan your day?" with `next_actions` `[{"label": "Yes", "action": "calendar_titles",
  "target": "titles"}, {"label": "Only times", "action": "calendar_titles", "target": "times"}]`; the tap
  sends `risi_action` `{"action": "calendar_titles", "target": "titles" | "times"}` (`edit: null`). While
  `times`, no title reaches the server (the §29.2 result validation rejects a block with any key beyond
  `start, end, busy, all_day`). `titles` only lets the phone add the titles to Risi's planning prompt in a later
  phase (not in this proposal's wire); Settings → Risi skills → Calendar shows the choice.

## 44.6 One row per real thing (amends §34.1, §34.4)
- **Group key:** Risi's items get `"group"`: the ledger item id they come from (a promise / follow-up: its own
  id; a Risi Calendar event: `source.item_id`; a reminder: the item of the §28.5 offer it came from), else
  null. `GET /risi/items` items carry `group` under the switch (additive).
- **Merge:** rows with the same `group`, or (no group) the same normalized title on the same local day, are one
  row. The row keeps the most specific time (an all-day block beats a timed due; a timed event beats a due),
  and lists its sources as tags in this order: `Risi Calendar · promise · follow-up · reminder · message`.
  Server text: `Sun 18 Oct · all day · Free up calendar (promise · reminder Sat 18:00)`. The phone does the
  same for "Your events".
- **Conflict:** an all-day block on a day that also holds timed events adds one line: **"18 Oct already has 2
  meetings. Move them, or keep both?"** (`next_actions`: "Open calendar" `open settings.risi_calendar`, "Keep
  both" = no-op chip). Also posted once when the block is created and the day already has Risi Calendar
  events.

## 44.7 Durations and all-day blocks (amends §27.3, §29.8, §29.12)
- **Day parts** (deterministic, `RisiMe.Agent.DayPart`; en/si/ta/Singlish): whole day / all day / full day /
  "mulu dawasama" / "මුළු දවසම" / "நாள் முழுவதும்" → **all day**; morning 08:00–12:00; afternoon 12:00–17:00;
  evening 17:00–21:00; night 19:00–22:00; "N hours" / "N mins" / "half an hour" / "an hour" → a duration from
  the start. Both a day part and a different duration in one phrase, or a part on a day without a date →
  `clarify` ("All day on Sun 18 Oct, or just the morning?").
- A ledger / voice item whose text or `due_text` says whole day is **all day** (date-only due), whatever the
  model's `due_local` time. A `risi_calendar_add` whose request says whole day is `all_day: true`.
- **An all-day block item** (an item that says whole day and blocks time: "free up", "block", "keep … free",
  "off", "leave", "holiday") gets **one all-day Risi Calendar event** (the §29.12 offer, `all_day: true`) and no
  §28.5 15-min reminder card.

## 44.8 Reminders at sensible times (amends §27.6, §28.5)
| what | reminder |
|---|---|
| all-day item / block | the day before at `risi_calendar_prefs.allday_remind_at` (default **18:00**), not 09:00 |
| timed meeting (§28.5 "Remind me?") | **15 min** before, or the user's learned lead |
- **Learned lead (L1 preference memory):** when the user edits an offered reminder's time, the lead (event −
  reminder, 0–1440 min) is recorded; with ≥ 3 samples the median is the user's lead. Never from anyone else's
  data.

## 44.9 Risi as the guide (builds on §43)
- `needs_permission` gains **`step`** (optional; old phones ignore it): `"permission"` (the §43 prompt) |
  `"account"` (no calendars on the phone) | `"auto_sync"` (reserved: the phone decides it itself) | `null`.
  The server sends `step: "account"` when the phone answered `no_calendars` (a `risi_fixit` +
  `risi_calendar_v2` phone); the request resumes on `permission_granted` as in §43.
- `permission` adds `contacts`, `microphone` and `location` to the server's skill map (the card was already
  defined for them).
- **The phone's guide** (one step at a time; after each step the user comes back to RisiMe and the phone
  re-checks by itself, `ON_RESUME`):
  a) "Let me see your calendar" **[Allow]** → the Android prompt (or the app's permission page, hint "Tap
     Calendar → Allow");
  b) no calendars → "Your Google calendar isn't on this phone yet" **[Open account settings]**
     (`Settings.ACTION_SYNC_SETTINGS`; no Google account at all: `Settings.ACTION_ADD_ACCOUNT` with
     `account_types = com.google`), hint "Tap your Google account → Account sync → turn on Calendar";
  c) auto-sync off → **[Turn on]** (`ContentResolver.setMasterSyncAutomatically(true)`, needs the normal
     permission `WRITE_SYNC_SETTINGS`; on failure `Settings.ACTION_SYNC_SETTINGS`), hint "Turn on Auto-sync
     data"; this step never blocks the answer (the events were read);
  d) done → "✓ I can see 3 calendars. Want me to show tomorrow?" with the "Ask me each time" / "Allowed"
     choice; then `permission_granted` (the original request runs again: "✓ Here's tomorrow").
  The same pattern serves contacts, notifications, microphone, battery optimisation
  (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, so reminders aren't killed) and the Google account.
- **Declined:** §43's "OK, I won't use your calendar. You can change this in Risi skills." Asked again only on
  the next request that needs it (never twice for one request, never from the background).
- **Started by Risi** in the Risi chat (any calendar request on a phone that can't read), and from Settings →
  Risi skills → Calendar (one line, one button: "Risi can't see your calendar yet." [Allow calendar]).

## 44.10 Storage (server, additive migration)
`risi_calendar_prefs` (user_id PK, `titles` text default `times`, `titles_asked_at`, `first_read_at`,
`allday_remind_at` time default 18:00, `lead_samples` int[] (last 5), `updated_at`). No titles, no event data.

## 44.11 Gate
- Server: a sync-off phone read lists `local_events` and the footer "From: your phone calendars · Risi" (no
  "Not checked"); a granted permission mid-conversation → the next reply has no "not checked"; "free up 18 Oct
  whole day" → one all-day block, one reminder Sat 17 Oct 18:00, one listing row tagged; two declines → one
  sentence each, no third card; no title reaches the server while `times`; no calendars → `step: "account"`.
- Android (JVM): the footer with domains; merged rows with tags; "Busy (shared calendar, no details)" only for a
  free/busy calendar; the guide's step order; `read_ok: true` despite auto-sync off.
- Device: `scripts/calendar-guide-test` (redroid): a fresh install → "what's on my calendar tomorrow?" → the
  guide (pm grant stands in for the dialog) → the answer with titles and the plain footer; no-Google-account
  path; screenshots of today / tomorrow / this week.

## 44.12 What ships where
- **Server only (fast lane):** §44.2 read rule (fixes the footer and "Busy" on today's APK: `local_events` makes
  the current phone list its events with titles), §44.3 footer text, §44.4, §44.6 server list and `group`,
  §44.7, §44.8, §44.9 `step` and the permission map, `/me calendar_v2`, the prefs table.
- **APK:** `risi_calendar_v2`, `read_ok` per §44.2, footer domains, merged rows with tags, calendar names,
  "Busy (shared calendar, no details)", the guide steps, the titles choice.
