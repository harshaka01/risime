# Proposal: PROTOCOL v1.13 — voice calls (1:1)

**Status:** proposal (root, 2026-10-06), for review by server and android (and crypto for §16.2
and §16.10). Not part of `contract/v1` until merged. Numbered after v1.12 (delete for everyone);
the section numbers below assume v1.12 takes §15, so calls are **§16**. Infra: decision 046
(coturn on spark2). Additive: apps without the `calls` capability never ring and never see call
traffic (§16.1).

## 16.0 Principles
- **1:1 voice first.** WebRTC with Opus, **direct peer-to-peer**, with a **TURN relay on spark2**
  (coturn, decision 046) as the fallback. Group voice comes later through a self-hosted LiveKit
  (§16.12, v1.14).
- **E2EE chats only.** A call is offered only in a DM that is e2ee (§10). Plaintext DMs refuse it
  (`not_e2ee`), exactly like images (§14.0). There is no plaintext signalling path.
- **Signalling is MLS.** Every call message is an MLS application message in the DM's group,
  carried in the §10.3 envelope `{"v":1,"type":"call_…",…}`. The server sees ciphertext, a call id
  and a ring flag (§16.3), never SDP, ICE candidates or IP addresses.
- **Media is authenticated by MLS.** The SDP carries the DTLS-SRTP certificate fingerprint; since
  the SDP arrives inside MLS from an attested leaf, the DTLS handshake is bound to the peer's
  attested device. A TURN server or the RisiMe server can relay packets but can't man-in-the-middle
  the media. Media is DTLS-SRTP end to end, also when relayed.
- **Two transport classes.**
  - **Ephemeral call signals** (offer, answer, ICE, ringing, accepted, busy) go through a new push
    `call:signal` (§16.3): stored in the inbox only briefly (60 s / 120 s TTL), never in history,
    no receipts.
  - **The end of a call is a durable message** (`call_end` through the normal e2ee `msg:send`).
    It's what both users keep as the call-history line ("Missed voice call", "Voice call · 3:12"),
    on every device, after a reinstall (§13) and when a device was offline during the call.
- **The server stores no media and records no audio.** It has no call table: no state machine,
  no "who is in a call" (busy is decided on the devices).
- **No model calls,** so nothing for the learning log (§16.11).

## 16.1 Capability and readiness
- A v1.13 app advertises **`"calls"`** with its MLS device:
  `PUT /me/devices/{device_id}` `"mls": {"signature_key", "capabilities": ["groups", "images", "calls"]}`.
  It advertises it only once it can **ring, answer and play a call** (ConnectionService, full-screen
  UI, WebRTC; §16.9).
- **`GET /api/v1/mls/groups/{conversation_id}`** (DMs only) gains **`"calls_ready": bool`** (absent
  = false) and **`"missing_calls": [{"user_id", "device_id" | null}]`**, computed like
  `images_ready` (§14.1): the DM is e2ee and every app instance of both users seen in the last
  30 days advertises `calls`.
- **Delivery filter (server).** `call_signal` events (§16.3) are pushed live only to sockets whose
  device advertises `calls`, and are left out of join/sync replies to other sockets (as §12.1 does
  for groups). Older apps would ignore the unknown kind anyway; the filter also keeps their MLS
  ratchets from seeing gaps they would log as errors.
- **UI:** the call button in a DM header is disabled until ready: "<name> needs to update the app
  to receive calls" ("Your other phone needs to update…" when the missing user is me). For a
  plaintext DM: "Calls need an end-to-end encrypted chat." (§14.1 style). In groups the button is
  absent until v1.14.

## 16.2 The call envelopes (MLS application messages)
All are UTF-8 JSON in the §10.3 envelope, serialised without escaping non-ASCII. Receivers ignore
unknown fields; an unknown `type` is ignored as before (§10.3). **`call_id`** is a UUIDv4 made by
the caller, one per call attempt. `from`/`from_device` come from the MLS sender (verified leaf,
§10.3), never from the JSON.

**Ephemeral (sent with `call:signal`, §16.3):**

`call_offer` (`ring: true`), caller → the callee's devices (and, by the sender copy, the caller's
other devices, which ignore it):
```json
{"v": 1, "type": "call_offer", "call_id": "4b7e1c1e-3c0e-4b55-9f43-0b8f8a1f2d10",
 "media": "audio", "sdp": "v=0\r\no=- 46117317 2 IN IP4 127.0.0.1\r\n…", "restart": false}
```
- `media` is `"audio"` in v1.13 (`"video"` reserved). `sdp` is the full offer SDP: one Opus audio
  m-line, `a=fingerprint:sha-256 …` required, with the candidates gathered in the first ~1 s
  included (half-trickle); the rest follow as `call_ice`.
- **`restart: true`** = an ICE restart / renegotiation on the same `call_id` (network change); sent
  with `ring: false` and a `to_device` field naming the selected callee device.

`call_ringing`, callee device → caller: `{"v":1,"type":"call_ringing","call_id":"…"}`. Sent when
the device actually rings; the caller shows "Ringing" instead of "Calling".

`call_answer`, callee device → caller (and by the sender copy to the callee's other devices, which
stop ringing at once):
```json
{"v": 1, "type": "call_answer", "call_id": "…", "to_device": "<caller device_id>", "sdp": "v=0\r\n…"}
```

`call_accepted`, caller → callee user (all devices): names the one device that won.
```json
{"v": 1, "type": "call_accepted", "call_id": "…", "device_id": "<winning callee device_id>"}
```

`call_ice`, either way, after the offer:
```json
{"v": 1, "type": "call_ice", "call_id": "…", "to_device": "<device_id>" | null,
 "candidates": [{"candidate": "candidate:1 1 udp 2122260223 192.0.2.10 49203 typ host", "sdp_mid": "0", "sdp_m_line_index": 0}],
 "done": false}
```
- Candidates are **batched**: at most one `call_ice` per 250 ms per call, at most 20 candidates
  each. `done: true` marks end-of-candidates.
- `to_device: null` only for the caller's candidates before `call_accepted` (every ringing callee
  device may use them); otherwise it names the peer device, and other devices ignore it.

`call_busy`, callee device → caller: `{"v":1,"type":"call_busy","call_id":"…"}` (§16.5).

**Durable (sent with the normal e2ee `msg:send`, §10.3; stored 30 days, sender copy §13.1,
inbox push §8):**

`call_end`:
```json
{"v": 1, "type": "call_end", "call_id": "…", "media": "audio",
 "reason": "hangup", "connected_at": "2026-10-06T08:15:30.123Z", "duration_s": 192}
```
- `reason`: `hangup` (connected, then ended by `from`), `cancelled` (the caller stopped before an
  answer), `timeout` (no answer in 45 s), `declined` (a callee device declined), `busy` (§16.5),
  `failed` (no media path: ICE failed, or 20 s without connecting after the answer, or 15 s of
  failed restarts).
- `connected_at` and `duration_s` are set only after a connection (`null` otherwise). They're
  inside MLS: the server sees only when the message is sent.
- **One line per `call_id`:** both sides may send a `call_end` (e.g. both hang up at once);
  receivers keep the first by event order and ignore later ones for the same `call_id`.
- A `call_end` from a client that never saw the call (offline throughout) is still rendered
  (§16.6), so missed calls survive offline periods, other devices and reinstalls.
- Example files: `call_offer_payload.json`, `call_answer_payload.json`,
  `call_accepted_payload.json`, `call_ice_payload.json`, `call_ringing_payload.json`,
  `call_busy_payload.json`, `call_end_payload.json`, `call_end_missed_payload.json`,
  `call_signal_push.json`, `call_signal_event.json`, `calls_turn_reply.json`,
  `push_call.json`.
- **Bound:** every call envelope is at most **20 480 bytes** (under the 24 KiB ciphertext cap,
  §10.3). An Opus-only offer is 2–4 KiB; a sender that exceeds the bound drops candidates from the
  SDP and sends them as `call_ice`.
- **Strict validation** before anything rings: `call_id` is a UUID, `media` is `audio`, the SDP is
  at most 16 KiB, has exactly one audio m-line, a sha-256 `a=fingerprint` and no video/data
  m-lines; otherwise the envelope is dropped and logged (§10.3 unknown-type handling).

## 16.3 Realtime: `call:signal` and the `call_signal` event
**`call:signal`** (client → server, on the inbox topic):
```json
{"client_msg_id": "uuid-v4", "to": "<user uuid>", "call_id": "uuid-v4", "ring": true,
 "ciphertext": "<b64 PrivateMessage>", "generation": 1, "epoch": 7, "client_ts": "…"}
```
- reply ok: `{"message_id": "timeuuid", "server_ts": "…"}`.
- reply error: `not_friends` | `unknown_recipient` | **`not_e2ee`** (the DM isn't e2ee) |
  `stale_epoch` | `too_long` (ciphertext > 24 KiB decoded) | `rate_limited` | `bad_request`
  (malformed, a `grp:` target, `ring` not a boolean).
- **Order of checks:** idempotent resend (same `client_msg_id` within 5 min returns the original
  reply) → `not_friends` → e2ee (`not_e2ee`, `stale_epoch`) → rate limit → store.
- **Rate limits** (per user): 60 `call:signal` per 10 s (ICE bursts), of which at most 6 with
  `ring: true` per minute and 1 `ring: true` per callee per 5 s. They don't count against the
  20-per-10-s message limit (§4).
- **Clients use `msg:send` only for `call_end`.** The server can't tell a `call_end` from a text.

**Inbox event kind `call_signal`** (cursor-ordered like every event):
`{"message_id", "conversation_id", "from", "to", "from_device", "call_id", "ring", "ciphertext", "generation", "epoch", "server_ts"}`
- Written to the **recipient's and the sender's** inboxes with the same `event_id` (the sender's
  other devices need answers and ICE of their own user; the sending device skips it by
  `from_device`).
- **TTL:** 60 s when `ring: true`, 120 s otherwise (Cassandra `USING TTL`, TWCS as today). No
  `status` events; `msg:ack` entries naming a `call_signal` are ignored. Not counted in
  `history_before` and never backfilled.
- **Clients process it in event order with the group's other events** (§10.3): it advances the MLS
  secret tree like any application message, inside the same transaction as the cursor. A
  `call_signal` at a newer epoch is held as pending like a message. Expired signals simply never
  arrive; the gap is within MLS's forward tolerance (≤ 1000 generations).
- **Staleness:** a device rings only if `server_time − server_ts < 45 s`, using the join reply's
  `server_time` to correct its own clock. Older offers are not rung; if no `call_end` follows,
  nothing is shown (the caller's `call_end` brings the missed-call line).

## 16.4 Call flow, timeouts and multi-device
1. **Caller:** fetches TURN credentials (§16.7), creates the `RTCPeerConnection`, sends
   `call_offer` (`ring: true`). UI "Calling…".
2. **Every MLS device of the callee with `calls`** rings (live socket or push wake-up, §16.8) and
   sends `call_ringing`. The caller's other devices ignore offers from their own user.
3. **First answer wins.** A callee device that answers sends `call_answer` (`to_device` = the
   offer's `from_device`). Its sibling devices see it through the sender copy and stop ringing
   ("Answered on another device"). The caller applies the **first `call_answer` in its event
   order**, sends `call_accepted` naming that device, and ignores later answers. A device that
   answered but isn't named in `call_accepted` tears down quietly.
4. ICE (`call_ice`) flows between the selected pair; media connects; both show the in-call UI.
5. **End:** whoever hangs up closes the connection and sends `call_end` (durable).

| Timer | Value | Action |
|---|---|---|
| Ring timeout (caller) | 45 s after the offer | `call_end` `timeout` |
| Ring validity (callee) | `server_ts + 45 s` | stop ringing; wait for the `call_end` |
| Connect timeout | 20 s after `call_accepted` without ICE `connected` | `call_end` `failed` |
| Reconnect | ICE `disconnected` → ICE restart (`restart: true`) for up to 15 s | then `call_end` `failed` |
| Max call length | 4 h | `call_end` `hangup` (protects relay quotas) |

A caller that loses its app mid-ring (crash, killed) sends no `call_end`; the callee stops at 45 s
and shows nothing more until the next sync brings one (or not).

## 16.5 Glare, busy and decline
- **Glare** (A and B call each other at once): a device with an outgoing ringing call to X that
  receives a `call_offer` from X compares the two `call_id`s as lowercase strings. **The lower
  `call_id` wins.** The device whose own call has the higher id drops its outgoing call silently
  (no `call_end`; it never connected) and **answers the winning offer automatically** (both users
  asked for this call). The other side keeps waiting for its answer. Ties are impossible (UUIDv4).
- **Busy:** a device already in a RisiMe call (connected or ringing out), or in a cellular call
  reported by Telecom, that receives an offer from another user replies `call_busy` and doesn't
  ring. Through the sender copy the callee's other devices see the `call_busy` and don't ring
  either (the user is busy, not the device). The caller shows "<name> is on another call" and sends
  `call_end` `busy`; the callee gets a "Missed voice call" line. (Call waiting comes later.)
- **Decline:** a callee device's Decline sends `call_end` `declined` (durable); siblings stop via
  the sender copy; the caller shows "Call declined" briefly, then the history line.

## 16.6 Call-history lines (client)
From one `call_end` per `call_id`, rendered as a centred system line in the DM, in the caller's and
the callee's own perspective:

| reason | Caller sees | Callee sees |
|---|---|---|
| `hangup` | "Voice call · 3:12" | "Voice call · 3:12" |
| `cancelled`, `timeout`, `busy` | "Voice call · No answer" | **"Missed voice call"** + a notification "Missed call from <name>" |
| `declined` | "Voice call · Declined" | "Declined voice call" |
| `failed` | "Voice call · Couldn't connect" | "Voice call · Couldn't connect" (if it rang: "Missed voice call") |

- Tapping a line offers "Call back". Lines sort by `server_ts` like messages and appear in the
  chat list preview ("📞 Missed voice call"). They take no reactions (no long-press menu);
  receipts are sent as for any message (they are messages).
- A **Calls tab/log** later reads the same lines; there is no server call log.

## 16.7 TURN credentials: `GET /api/v1/calls/turn`
Auth required (`Authorization: Bearer`), no body → `200` (`calls_turn_reply.json`):
```json
{"ice_servers": [
   {"urls": ["stun:risime.risicloud.ai:3478"]},
   {"urls": ["turn:risime.risicloud.ai:3478?transport=udp",
             "turn:risime.risicloud.ai:3478?transport=tcp",
             "turns:risime.risicloud.ai:5349?transport=tcp"],
    "username": "1791391295:6f1c0e9a2b7d4c31",
    "credential": "<b64 HMAC-SHA1>"}],
 "ttl": 3600, "expires_at": "2026-10-06T09:15:30.000Z"}
```
- **TURN REST (coturn `use-auth-secret`):** `username = "<unix expiry>:<16 random hex>"`,
  `credential = base64(HMAC-SHA1(TURN_SECRET, username))`, TTL 3600 s. The username carries **no
  user id or phone** (coturn logs it); the server may log the mapping at debug level only.
- `turns:` is listed only when the server's config says TLS is live (decision 046: later). The
  URL list is server configuration (`TURN_URLS`), not protocol; clients use whatever comes back.
- **Errors:** `401` (auth), `429 rate_limited` with `Retry-After` (**20 per user per hour**),
  **`503 calls_unavailable`** (no `TURN_SECRET` configured; clients then call with STUN only and
  show nothing special).
- **Clients** fetch it when starting or answering a call, cache it until `expires_at − 5 min`, and
  never persist it to disk.

## 16.8 Push: the call wake-up
- **Payload** (`push_call.json`): `{"type": "call", "v": "1"}` and nothing else, FCM data message,
  **`priority: high`**, **`ttl: 45s`**, `collapse_key: "call"`. Like §8.2 it carries no caller, no
  `call_id`, no content.
- **When:** for every `call_signal` with `ring: true`, to **each device of the recipient that has
  `calls` and no live inbox channel** (device-level, using the §10.1 census, not the user-level
  rule of §8.0). It is **not coalesced** with inbox pushes and not delayed by the 10-s rule.
- No push for other `call_signal`s. `call_end` is a normal message, so it triggers the normal
  `{"type":"inbox"}` push, and a woken device builds "Missed call from <name>" locally.
- **On receipt** the app starts its sync at once (high-priority FCM grants the background start),
  decrypts the offer, and only then shows the ringing UI with the caller's name from its own
  database. If the offer turns out stale, cancelled or busy, nothing rings.
- **What the `call` hint leaks.** Google (FCM) learns that *this app install received a call
  attempt at time T* (as opposed to a message), how often, and whether it's delivered; with
  network-level timing it could correlate calls between two devices it also serves. It learns no
  caller, no content and no duration. Our server knows all of this anyway. **We accept it**: an
  `inbox`-typed push would hide the difference but delay ringing by a sync and would be
  deprioritised by FCM when it doesn't produce a notification fast; a hint-free design is a later
  option if push volume ever pads calls and messages alike.

## 16.9 Android notes (informative; the android review decides)
- **WebRTC library:** `io.getstream:stream-webrtc-android` (maintained prebuilt of upstream
  libwebrtc, arm64-v8a/armeabi-v7a/x86/x86_64, Apache-2.0 + BSD; `org.webrtc` API). Building
  libwebrtc ourselves needs an x86-64 Linux toolchain (depot_tools/gn, not on spark2) and hours per
  update: rejected for now. Google's `org.webrtc:google-webrtc` is unmaintained. **Check before
  choosing** that the build can coexist with LiveKit's Android SDK (v1.14), which bundles its own
  libwebrtc (`io.github.webrtc-sdk`); if not, use that build for 1:1 too, so there is one copy.
  Size: about +5–8 MB per ABI; the release APK carries 4 ABIs (decision 045), so consider ABI
  splits in the updater.
- **Audio:** Opus mono, 48 kHz, ~32 kbit/s, in-band FEC (`useinbandfec=1`), DTX on, 20 ms ptime;
  `JavaAudioDeviceModule` with the hardware AEC/NS when available, `USAGE_VOICE_COMMUNICATION`;
  proximity wake lock on the earpiece.
- **Telecom:** a **self-managed** call through **`androidx.core:core-telecom`** (`CallsManager`,
  min SDK 26; ConnectionService underneath on API 26–33, transactional Telecom on 34+):
  `MANAGE_OWN_CALLS`; the system knows about our call (cellular call interaction, car/watch,
  audio focus, DND). Ringing is ours (a ringtone with `USAGE_NOTIFICATION_RINGTONE`, respecting
  DND/silent via Telecom's show-incoming-UI callback).
- **Audio routing / Bluetooth:** core-telecom's `availableEndpoints` / `requestEndpointChange`
  (earpiece, speaker, wired, Bluetooth), shown as an audio button; `BLUETOOTH_CONNECT` (API 31+,
  runtime) for headset names. Auto-route to a connected BT headset on answer.
- **Notifications:** `NotificationCompat.CallStyle.forIncomingCall(person, decline, answer)` on a
  high-importance "Calls" channel, category `CALL`, with a **full-screen intent** to the incoming
  call activity (`showWhenLocked` + `turnScreenOn`); `CallStyle.forOngoingCall` while connected.
  **Answer from the lock screen** without unlocking (as for phone calls); the rest of the app stays
  behind the lock.
- **`USE_FULL_SCREEN_INTENT` (Android 14+):** a special app access that Google Play limits to
  calling/alarm apps; we're distributed outside Play (decision 016), so on 14+ check
  `NotificationManager.canUseFullScreenIntent()` at sign-in and on the first incoming call; if
  false, explain and open `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`. Without it the call
  is a heads-up notification that keeps ringing.
- **Foreground service** for the call, `foregroundServiceType="phoneCall|microphone"`
  (`FOREGROUND_SERVICE_PHONE_CALL`, `FOREGROUND_SERVICE_MICROPHONE`), started from the answer
  action or the outgoing call button (user interaction, so the while-in-use microphone rule is
  met). Permissions: `RECORD_AUDIO` (asked at the first call), `POST_NOTIFICATIONS` (33+).
- **Battery/Doze:** ringing relies on high-priority FCM; ask for no battery optimisation only if
  the pilot shows missed rings.

## 16.10 Privacy and security
- **The server learns:** who calls whom (DM participants, devices), when a call rings (`ring:
  true`), the timing and number of signals (answer timing, so "answered or not"), and when a
  `call_end` is sent, hence roughly the duration. It doesn't learn the reason or the duration
  field, SDP, ICE candidates or IPs (all inside MLS).
- **coturn (spark2) learns**, for relayed calls only: both public IPs and ports, allocation start
  and end, bytes relayed. Usernames are random (§16.7). Logs to stdout, no packet logs (decision
  046).
- **The peers learn each other's IP addresses** in a direct call (host and server-reflexive
  candidates), as in every P2P calling app. Calls are only between friends (§9). A later setting
  "Always relay calls" (`iceTransportPolicy = relay`) hides them at a quality cost.
- **Google** learns the push timing (§16.8).
- **Media:** DTLS-SRTP keys are negotiated between the phones; the fingerprint is MLS-authenticated
  (§16.0). The server can't inject a call into an MLS group, and a call from a non-member device
  fails leaf verification and is dropped.
- **Call audio is never recorded** by the app; no audio, transcript or voice feature goes to any
  model in v1.13.
- Goes into the app's privacy note with the typing/presence/images metadata.

## 16.11 Learning log, on-device data
- **Learning log:** none; there are no model calls in calling.
- **On-device behaviour log** (stays on the device): "call placed/received/missed", direction,
  duration, never audio. Twin sync rules apply (off by default).

## 16.12 Group calls with LiveKit — outline for v1.14 (not normative)
- **SFU:** self-hosted LiveKit (`livekit/livekit-server`, multi-arch, arm64 present) on spark2.
  Signalling (7880) on 127.0.0.1 behind Caddy at `wss://risime.risicloud.ai/livekit`; media
  **7881/tcp** (ICE-TCP) and **50000–60000/udp** (decision 046, reserved). LiveKit's embedded TURN
  off; coturn serves both.
- **E2EE:** LiveKit's insertable-streams frame encryption with a **shared key derived from the
  group's MLS exporter**: `MLS-Exporter("risime-call-v1", call_id, 32)`, re-derived on every epoch
  change (a member added or removed mid-call gets a new key; removed members can't decrypt later
  frames). The SFU forwards encrypted frames only.
- **Rooms:** `POST /api/v1/calls/rooms {"conversation_id": "grp:…"}` → a LiveKit access token
  (JWT, short TTL, identity `<user_id>/<device_id>`, a random room name unrelated to the group id),
  for **active members only**. Invitation through the same MLS envelopes (`call_offer` with
  `"mode": "sfu", "room": "…"`, `ring: true` to the group), join/leave lines through `call_end`-
  like durable messages.
- **Limits:** up to 32 participants audio-only at first; video later.
- **Open:** one libwebrtc in the APK (§16.9); exporter key timing on epoch races; server knows
  room participation (who joined, when, from where).

## 16.13 Test coverage (all gates)
- **Server:** `call:signal` happy path and each error with the order of checks; idempotency
  (5 min); both inboxes with the same `event_id`; TTL 60/120 s set on the rows; no status, ack
  ignored; the `calls` delivery filter (live and join/sync); the rate limits incl. 1 ring per
  callee per 5 s; device-level call push only to `calls` devices without a live channel, not
  coalesced; `GET /calls/turn` (credential = HMAC of the username with the test secret, TTL,
  `429`, `503` without a secret); `calls_ready`/`missing_calls`.
- **Android:** encode/decode of every call example and the strict-validation drops; the
  state machine (ring, answer, first-answer-wins, accepted elsewhere, glare both directions, busy,
  decline, cancel, timeout, failed, restart); staleness against `server_time`; the history-line
  table; call push handling; interop: a live call between two emulators/devices through coturn
  with `iceTransportPolicy = relay` (forces the relay path).
- **Infra:** `scripts/turn-smoke` (loopback) and, once public, a relay-only call from mobile data.

## Open points for review
**Server**
- S1. `call:signal` as a new push vs. a flag on `msg:send`: a separate push keeps message paths
  (status, history, sender-copy backfill, 30-day TTL) untouched. Agree?
- S2. Per-row TTL on `inbox_events` (`USING TTL 60/120`) inside TWCS: acceptable, or a separate
  `call_signals` table (one per query)? Join/sync must merge it into the cursor order either way.
