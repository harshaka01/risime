# Brief v1.31 (server): Google Calendar link (PROTOCOL.md §31)

For the **server** role. Contract: `contract/v1/PROTOCOL.md` v1.31 §31 and the "(v1.31)" notes in
§25.3, §29.1 and §29.7. Decision 074. Commit only `server/` and `docs/status/server.md`.
Gate: `mix format --check-formatted && mix compile --warnings-as-errors && mix test`.

**The rule to keep in mind:** the server never sees or stores a Google token, an email, a Google
calendar name or id, or a Google event title or id. The server makes no Google call. Google lives
on the user's Google device. The server only routes `calendar_check` to that device and stores a
small link row.

**Chunk 0 first (the gate is red until it lands):** root added 13 example files to
`contract/v1/examples/`. `test/contract/examples_test.exs` ("every example file is covered") fails
until they are listed. Add `@checked_v1_31` with those 13 files, and
`test/contract/examples_v131_test.exs` that builds each one from real server code and compares it
exactly. Regenerate a file where the real output differs in ids or timestamps only, as in v1.29 and
v1.30. If the shape itself has to differ, stop and write a proposal.

     and `events_on?()`.
   - `auth_controller.ex`: add `google_calendar: "on"` while it is on; the key is absent otherwise

   - `devices.ex` (the capability filter near line 141): keep `google_calendar` only together

   - Tests: the config key on and off; the capability dropped without `risi_events`.
2. **Link storage and REST** (§31.3)
   - Migration `risi_gcal_links`, with exactly the columns and CHECKs of §31.3. The migration
     test asserts the exact column list: no `token`/`email`/`name`/`calendar_id`/`title`.
   - Delete the link with its device: on logout or device removal, in the same transaction.
   - Add a module `RisiMe.Agent.GoogleLink` (`get/1`, `connect/3`, `update/3`, `disconnect/3`,
     `state/1`). `paused` is computed from the Calendar skill state (`RisiMe.Agent.Skills`).
   - Add `RisiGoogleController` with routes `get|put|delete /risi/calendar/google`, next to the
     calendar routes in `router.ex`.
     - Every request needs an `X-Device-Id` that names a `google_calendar` device of the
       caller, else `403 invalid_device`.
     - `503` while the switch is off.
     - `409 not_google_device` (`error_not_google_device.json`) for `connect: false` from a
       device that is not the Google device, or when there is no link.
     - `422` for unknown keys and out-of-range values.
     - Rate limit: 30 writes per user per minute.
   - The stored inbox event `google_calendar_link` (`event_google_calendar_link.json`):
     - Write it on connect, update, disconnect and replace, to the user's `google_calendar`
       devices only, with no push wake.
     - On replace, the old device gets `reason: "replaced"`.
     - `remove_copies` comes from the `DELETE` query (default false).
     - Filter it in `inbox_channel.ex` and the sync replies, the same way as
       `risi_calendar_changed`.
   - Tests: every row of the §31.3 table; replace; delete from a non-Google device; the device
     removed → the link is gone; logs carry ids and state only.
3. **The routed `calendar_check`** (§31.4, amends §25.3)
   - In `client_tools.ex`, `tool_calls.ex` and `calendar_tools.ex`, inside the
     `risi_calendar_check` step:
     - When the link is `connected` and the Calendar skill is not `off`, send `calendar_check`
       with `args.sources: ["google_api"]` and `to_devices: [google_device]`. `device_id` stays
       the asking device.
     - If the Google device is the asking device and the phone check runs anyway, send **one**
       call with `["phone_provider", "google_api"]`. Otherwise send two calls in parallel, in the
       same step.
     - The wake goes to the Google device's token.
   - The result endpoint accepts a result only from the device in `to_devices`.
   - The 15-s deadline: an unanswered Google call becomes the source
     `{read_ok: false, reason: "no_answer"}`, and the turn goes on. A late result gets
     `409 tool_call_expired`.
   - Send no call for a link in `reauth_needed` (source reason `reauth_needed`) or for skill
     `off` (reason `paused`).
   - **Strict schema:** a `google_api` source has `calendars: [{"ref", "events"}]` only. Refuse
     `name` or `account_type` there with `422`. `ref` must match `^[a-z0-9]{1,16}$`; at most 10
     entries. With `args.sources` set, the result's `sources` must be exactly the sources asked
     for. `phone_provider` keeps the v2 shape.
   - The model input: add `"google": {source, read_ok, reason, calendars: <count>, blocks}` to the
     `risi_calendar_check` result. Give it no refs and no names. Google blocks take `c<n>` refs.
   - Tests use a test socket as the Google device, with these cases: answers, never answers
     (`no_answer`), answers late (`409`), the wrong device posts (`404`), a `name` in a
     `google_api` entry (`422`), the asker is also the Google device (one call).
